## 1. 本期目标与裁决

用户确认本期只保证：最终设计的表和字段完整，数据库约束正确，默认 6 个管理员及显式启用的开发客户／工程师账号数据有效，薛能通过一个正式命令完成约定部署、结构校验和初始化，并能安全重复执行。

- 开发测试账号：按**客户 2 个、工程师 2 个**准备验收样例，数量可配置；这是计划默认建议，不是新增固定业务规则。开发数据必须显式启用，与管理员初始化分开授权；正式部署默认不生成。
- “账号可用”指密码能被现有密码算法验证、角色与摘要事实有效、资料及可信归属正确、状态一致；**不以旧登录接口是否已适配为本期门禁**，也不宣称端到端登录已通过。
- 不要求旧 GraphQL／REST 业务接口、页面、API／Worker 全功能和标准业务 core 全部通过，不提前开发模型、同步、导出、备份或恢复执行器。
- 范围收敛不是放弃表、字段和约束质量，也不是授权删除接口、测试或已有实现；既有变更在提交审计时逐项说明，不用删除无关文件制造绿色结果。

本计划替代旧主计划和 S5 方案中的**后续执行范围、退出条件与本期验收门禁**。旧规范仍适用；数据库设计裁决和原始验证记录保留，不把未验证事项改成通过。旧 core 结果仅为历史证据。

## 3. 一键部署契约

### 3.1 前置条件

MySQL 服务已经安装启动；Node/npm与锁文件依赖已准备；数据库和权限按正式工具当前契约由维护者预建。真实配置与账号映射在仓库外，Linux 文件 0600、目录 0700，其他平台说明等价保护。无需启动 API、Worker、Redis或模型服务。

现有正式 CLI 是 `backend` 中的 `npm run database:deploy`；它当前不自动创建 MySQL 数据库。SOP 需明确“预建空库后一个命令”，不承诺自动安装MySQL、建用户或修改系统权限表。

### 3.2 单命令完成范围

执行一次正式命令，应完成目标核验、互斥、迁移、结构核验、所选初始化数据和最终结果。普通结构 init 可不带账号参数；**包含6个管理员的交付演示必须同一命令显式提供映射**，不能结构完成后另跑手工 INSERT。

现有管理员参数真实存在，命令模板为：

```bash
cd backend
npm run database:deploy -- \
  --mode init \
  --config-file <库外私密配置> \
  --database <预建空库> \
  --confirm-database <同一库名> \
  --admin-bootstrap-file <库外管理员映射> \
  --confirm-admin-bootstrap APPLY-ADMIN-BOOTSTRAP
```

尖括号是占位，不可直接执行。开发测试账号如需新增 CLI 选项，在 D2 定稿并同步帮助、测试、模板及SOP；**本计划不把拟新增参数写成已实现命令**。

组织／公司前置必须闭合：空库只有迁移种子时，1／2级管理员及客户／工程师映射所需公司可能不存在。先检查现有能力；采用受控配置中的合法已有公司，或在同一初始化命令中显式受控创建约定公司。公司名、编码和归属不能猜测，不能隐含要求用户中途手工补 SQL。组织不存在或冲突应明确拒绝。

## 4. 账号数据完整性

| 对象       | 目标与必须核对的事实                                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 6 个管理员 | 1级3个、2级3个；SUPER_ADMIN身份、等级、公司与ACTIVE可信成员符合批准方案；密码、角色密文／摘要、资料一致；首次改密标记符合现有契约                                         |
| 客户样例   | 默认建议2个，可配置；角色CUSTOMER，账号／资料／客户公司按当前设计关联；不错误赋予工程师成员资格或资料库权限                                                               |
| 工程师样例 | 默认建议2个，可配置；角色ENGINEER，正常可开发使用的账号状态、资料及ACTIVE成员一致；注册／审批表若为当前有效资格的必要事实，应构造一致的已批准事实，不以缺记录模拟审批完成 |
| 跨公司样例 | 合成环境优先采用两个明确公司，便于后续开发；具体映射由配置决定，不自动把全部账号塞进甲方或生成正式公司                                                                    |

共同要求：

1. 密码严格采用当前项目密码策略、规范化、哈希和验证算法；不得只生成“看起来复杂”的字符串。复用经过允许的实现，不另造不兼容密码方案。检查初始密码长度、字符及禁止项，依据不明确时先读取实际契约，不自行规定。
2. 数据库不能存明文密码；真实初始密码仅通过0600配置和受保护渠道交接。报告不打印密码、完整密码哈希、角色密文或令牌。仓库样例仅有占位符，不提交可直接使用的固定公共密码。
3. account、user_info、identity_hint、access_group、meta_digest、管理员等级、公司／成员、启停与改密字段逐项按真实定义核对。使用真实角色策略及密码验证器离线／数据库定向校验，不以能 INSERT 为“可用”。
4. 由配置定位真实关联；缺失／冲突身份、公司、重复邮箱或登录名失败关闭，不接管异主账号、不自动提权。已存在但事实不完整不能无条件返回UNCHANGED。
5. 重跑相同配置不重复创建、不重置密码、不更改等级／归属。新增账号／资料／必要成员和资格原子一致；故障必须无部分新增。结构DDL和初始化数据事务分别说明，不声称整个部署可事务回滚。
6. 开发样例必须显式启用并确认开发目标，默认关闭；新安装默认6个管理员不等于默认开启客户／工程师样例。管理员仅模板占位，没有真实映射时不能宣称已生成6个可用账号。
7. 不默认创建工单、报告、文件、备份或历史业务数据。仅补使这些账号合法所必需的组织／资格关联，最小化样例。
