### 4.2 采用的最小设计

**分开正常回收与残留恢复。**

正常回收：每个 spec 持有本轮资源清单，造数成功取得数据库生成 ID 后立即登记，写入已知字段/父子关系作为预期归属事实。经业务 API 新建的投稿、版本、附件、审核、正式资料，也在获得结果后及时登记或由已拥有父资源读取并核验后登记。

不能取得 ID 的部分失败，不得靠猜测固定 ID 补登记。确需通过自然键回查时，先核验完整预期字段和关系；无法证明则保留并报错，不能误删。

残留恢复：自然键只能定位候选，不授予删除权。只有完整指纹、父子链及创建身份均匹配的已知测试残留可以回收；不匹配则报告冲突、零删除。不要为保证“每次都能启动”自动接管同名账号/组织。没有可靠残留证明时，安全拒绝比扩大清理范围优先。

资源清单是测试运行内数据，不需要新增业务表、通用清理平台或生产代码测试钩子。

### 4.3 实施步骤

1. 为账号、组织、成员、机型以及投稿/资料链建立本规格拥有资源的显式清单；本轮创建尽量使用自增主键，删除 09/12 直接将 id=43 视为归属的逻辑。
2. 让种子 helper 返回真实创建结果；已有组织/账号被复用前核验指纹，不因编码/登录名相同就改写其成员关系。
3. 清理入口保持物理许可与真实库白名单双门禁，且不可通过直接调用底层公开删除函数绕开。可以由唯一守护入口持有删除步骤，或让可独立调用的破坏性入口自行校验；不要并存可绕过的新路径。
4. 在任何 DELETE 前，对**本次组合清理的全部资源**完成归属和引用闭包预检。不能先删组织链，再检查账号/机型才发现冲突。
5. 对所有相关入向引用核对实际外键：账号的其他业务记录/其他组织成员、组织的外部成员/投稿/资料、来源投稿被其他组织资料引用、机型被范围外业务引用等。范围外引用应拒绝，不扩展为“顺便一起删”。
6. 将“已验证 ID 集合 + 删除次序”交给执行阶段，只允许删除预检通过的精确 ID；不再使用组织编码子查询动态吞入整条未知链，也不直接删除某账号的全部成员关系。
7. 在同一事务/连接内保持预检和删除的一致性，必要时锁定目标；异常回滚已执行删除。仅有事务但无预检不够：已知归属冲突必须在第一条 DELETE 前失败。
8. 将任意 `extraCleanup` 改为可在删除前预检的具体资源步骤，或明确拆出 prepare/validate/execute；只满足本次消费者，不引入通用回调总线。
9. beforeAll 每个成功创建点登记资源；afterAll 只处理已登记/验证资源。保留 cleanup 失败传播、finalize 和 app close 必须执行、原始与附加失败可观测的既有语义。
10. 空集合必须 no-op；未知引用/未知归属失败关闭，错误说明 spec、阶段、资源类别/ID，不泄漏凭据。

## 五、F2 / R03：组织及成员 Seed 碰撞保护

### 5.1 修改范围

- `backend/scripts/seed-mock.ts` 的组织/成员定义、查找、写入及结果校验
- 必要的同目录纯策略/无启动副作用的写函数模块
- `backend/scripts/seed-mock.contract.spec.ts` 或新增同目录 Seed 安全规格
- 相关 schema/交接说明：仅同步实际变化，不修改已有历史回执

### 5.2 默认实现选择

本轮优先采用**保留现有 Seed 固定编号约定，但双键预检后才写入**，减少对现有数量校验、样例和开发账号引用的联动。固定编号只是定位约定，不能作为归属证明。

组织的实际 ID 仍按稳定编码解析：迁移创建的 `CLIENT_DEFAULT` 可能不是 910001，不能把其 ID 改成固定值。对于已经存在的基础甲方组织，复用经核验的身份，不因运行 Mock Seed 强制恢复其真实名称或把 DISABLED 改为 ACTIVE；若不满足试用夹具前提，应明确拒绝并说明，不静默改权限事实。

如果改用自增组织/成员 ID 可以使改动更小，可选择自增，但必须一起调整依赖固定范围的统计、双跑断言和交接材料。不得只改插入不改校验。业务表主键和其他无关 Seed 不随之重构。

### 5.3 实施步骤

1. 组织同时检查预期编码与固定 id 的占用，区分迁移初始化组织、已确认 Seed 组织、异主冲突；任意唯一键冲突都不得由通用 upsert 决定覆盖对象。
2. 成员同时检查固定 id、`(organization_id, account_id)` 唯一键及真实组织/账号归属；主键指向另一组织/账号时拒绝，不更新其 FK 或角色。
3. 允许重复更新的 Mock 字段和不可变归属字段明确列出。不把“把异主改成预期值后计数正好”作为 Seed 成功证明。
4. 归属核验必须发生在对应 INSERT/UPDATE 前；整个 Seed 继续由原事务持有，冲突时回滚本次已进行的其他 Seed 写入，错误传播。
5. 不以预留 ID 区间、账号角色或公司名称单独证明 Mock。保留 F04 真实快照构造和既有显式损坏 Mock 修复边界，不重置真实冻结历史。
6. 将需单测的真实组织/成员逻辑放到可安全导入的窄模块，或采用无副作用工厂；测试不得 import 即启动 seedMockData，也不得只用文本搜索断言有 guard。
7. 为真实脚本提供相同执行路径的测试；字段级校验、业务键解析和写入不能只在测试替身中存在。

### 6.2 实施步骤

1. 不删除组织授权，也不靠将组织查询移出事务假装解决；保持可信组织及投稿主行锁的既有授权语义。

3. 送审读取当前附件同样必须为事务内当前读，不能继续走旧快照；可建立专用 `ForSubmit` 方法要求事务上下文，避免调用方省略后退化成普通查询。
4. 固定锁顺序：先投稿主表，再按流程依次读取所需明细/附件；相同资源路径顺序一致，锁保持到写入/冻结完成提交或回滚。主表锁仍是同投稿所有状态敏感动作的共同互斥点。
5. 补丁仍按 `undefined=保留/null=允许时清空` 合并；草稿宽松校验、送审完整校验、历史快照不可改、仅一份 CURRENT 等规则不变。
6. 防止为了修复共享 loader 给所有只读页面加锁；明确普通读取与写前当前读的调用契约，测试断言锁选项和事务连接。
7. 扫描本次投稿直接写消费者的其他“主表锁后普通读”路径，只修会影响合并、附件选择和冻结事实者；不可变旧 revision 的读取不因同名方法而自动加锁。

确定性要求：W01～W06 不得只用 `Promise.all` 碰运气。两个独立事务均通过实际组织 SELECT 建立 RR 快照；让 A 持主行锁、B 建快照并进入等待，再允许 A 提交，最后让 B 继续。用例级装饰器/测试替身只控制时点，不 mock 掉实际事务、QueryService 的 SQL 或存储；记录 `@@transaction_isolation`。

屏障设置有界等待和 finally 放行，Promise 及时挂拒绝处理；恢复覆盖方法，await 所有请求收敛，不影响后续用例。

**完成门槛：** 两类草稿和送审附件同族全部覆盖，模型红绿及锁契约通过；真实独立连接结果在 F4 验证，不能仅凭新增锁代码关闭 R01。
