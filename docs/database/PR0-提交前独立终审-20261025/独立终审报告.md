## 3. 本 PR 必须修复的问题

### R25-01 [P2] 只有保留账号时生成空 WHERE，异常准备阶段无法完成夹具清理

1. **准确位置**：`backend/test/utils/e2e-scoped-cleanup.ts:499` 的外层分支、`:538`—`:554` 的投稿查询，尤其 `:548`。直接消费者：`backend/test/10-admin-document-database/admin-document-database.e2e-spec.ts:85`、`:104`、`:124`、`:175` 和 `:183`。
2. **方向及最小触发条件**：数据库测试造数/清理、部分失败。`runGuardedSpecCleanup` 获得至少一个指纹完全匹配的 `retainedAccounts`；此时待删除组织和账号集合都为空。实际可发生于 10 组已成功创建 fixture 账号、但尚未成功创建组织就失败，或进程中断后留下这些账号而未留下组织。
3. **当前行为**：外层因 `membershipAccountIds.length > 0` 进入；成员查询已对空条件做保护，但投稿查询没有，生成：

   ```sql
   SELECT id, owner_organization_id, submitted_by_account_id
   FROM content_submission WHERE FOR UPDATE
   ```

   参数为 `[]`。该语句语法无效，清理失败。10 组 afterAll 中下一条 `cleanupAdminDocumentFixtureByIds` 因前一 await 抛错而不执行；下次 beforeAll 预清理也可能重复卡在相同状态。
4. **期望行为与依据**：任务书 S8 的完整回归、T04 管理员原能力无回归；终审工作流“部分造数失败、残留清理、重复运行、异常必传播”的要求；helper 自身 `:947` 附近明确说明 retainedAccounts 仅用于归属核验、不属于本事务删除。无待删根节点时不得生成无条件或空条件查询，应允许相邻 owner 的精确清理继续完成。
5. **影响与定级理由**：真实可达的失败恢复路径失效，造成专属测试夹具残留、重跑阻塞，影响当前 PR 的必要验证与交接可靠性，故为 P2。当前反例的 DELETE 数为 0；**没有证据证明误删、跨组织数据泄漏或生产数据损坏，不上调为 P1/P0**。
6. **本轮最小反例**：加载当前导出的真实 helper，以记录型 DataSource 返回匹配保留账号，拦截实际生成的 SQL。缺少保留账号行的对照组成功；存在保留账号行的实验组生成上述空 WHERE。接入真实 `runE2eTeardown` 后，确认错误向外传播、应用关闭执行，但第二个 fixture cleanup 未被调用。反例未连接 MySQL、未写库、未删除文件。它证明实际代码生成了非法 SQL；**不是实库 ER_PARSE_ERROR 截图**。
7. **现有测试漏检原因**：空集合测试只覆盖“无 owned 且无 residue”；正常删除测试具有组织/账号条件；未覆盖“retained 指纹命中，但没有 owned 组织/账号”的组合。完整成功场景创建了组织，也不会进入这一最小反例。
8. **最小无债修复方向**：按每条查询实际具备的删除归属条件决定是否查询，空集合时明确跳过该子图查询；保留 retained-only 核验语义与原有安全门禁。不把 retained 账号加入可删集合，不省略 WHERE 后全表查，不关闭门禁，不 catch 后假成功，也不重构无关测试域。
9. **必须补的回归**：① 指纹命中、orgIds/accountIds 为空；② retained 指纹未命中的空操作；③ 正常带组织的已有路径；④ 部分账号/业务造数后、组织创建前注入失败，真实 10 组组合收尾能精确清理，应用仍关闭；⑤ 非空隔离库中异主数据不变、连续重跑不受本次残留影响；⑥ 原清理拒绝/失败仍向测试传播。
10. **归属**：当前 PR。helper 是本 PR 新增，10 组调用是本 PR 直接修改，不是后续页面需求。未授权修复，本报告仅记录。
