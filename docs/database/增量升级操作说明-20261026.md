# 既有库增量升级操作说明（14 → 24）

本说明对应 PR0-B Review 修复新增的正式入口 `migration:status` / `migration:run` / `migration:verify`。
入口只执行仓库当前迁移目录中的 pending 迁移：不清表、不运行 Seed、不依赖 `synchronize`、不创建或删除数据库。

> 本候选的验收数字是“旧库 14 条 → 24 条、9 张新表、23 张业务/基础表”。
> 这些数字用于本次验收对照，不应硬编码为未来唯一合法状态；已完整升级的库应能安全空操作。

## 1. 适用范围与禁止项

适用：

- 已经执行过 14 条基线迁移、需要升级到当前 24 条迁移的既有库。
- 目标为 MySQL 8.0+，迁移账号具备目标库的 DDL/DML 权限。

禁止：

- 不要把 `npm run migration:drill:empty-db` / `migration:drill:upgrade` 当作既有库升级命令。演练脚本会**清空目标库**后重建，仅用于验证迁移链本身。
- 不要在升级期间运行 Seed、`synchronize`、手工改表或其他迁移进程。
- 不要通过删除 `migrations` 记录来“制造 pending”，也不要用 `down`、手工 `DROP` 掩盖失败。

## 2. 前置确认

1. **备份**：对目标库做可恢复备份，并实际验证备份可导入（至少在同版本 MySQL 副本上演练一次）。
2. **停写**：停止业务写入、后台任务和其他迁移进程；升级窗口内只允许本入口连接目标库写入。
3. **配置文件**：显式指定一份只用于本次升级的配置文件（不得依赖自动回落）：
   - 必填：`DB_HOST`、`DB_PORT`、`DB_USER`、`DB_NAME`
   - 可选：`DB_PASS`、`DB_TIMEZONE`（默认 `+08:00`）
   - 必须**不包含** `DB_SYNCHRONIZE=true`；入口自身也会强制 `synchronize=false`。
4. **目标核对**：确认配置文件中的 `DB_NAME` 与命令 `--database` 完全一致；入口还会用 `SELECT DATABASE()` 核对实际连接。

## 3. 命令契约

在 `backend` 目录执行。Bash/WSL：

```bash
npm run migration:status -- --config-file env/.env.production --database <目标库>
npm run migration:run -- --config-file env/.env.production --database <目标库> --confirm-database <目标库>
npm run migration:verify -- --config-file env/.env.production --database <目标库>
```

PowerShell：

```powershell
npm run migration:status -- --config-file env/.env.production --database <目标库>
npm run migration:run -- --config-file env/.env.production --database <目标库> --confirm-database <目标库>
npm run migration:verify -- --config-file env/.env.production --database <目标库>
```

参数说明：

- `--config-file`：显式配置文件路径，缺失、为空、缺必填字段、端口非法、`DB_NAME` 与 `--database` 不一致都会立即失败。
- `--database`：目标库名，必须与配置文件一致。
- `--confirm-database`：仅 `migration:run` 必填，必须与 `--database` 完全一致，用于二次确认写目标。
- 只输出脱敏后的 `host:port/database`，不会输出密码。

> **与计划示例的差异**：计划示例使用 `--env-file`。Node 20.6+ 原生支持 `--env-file`，会在脚本启动前拦截该参数（文件缺失时由 Node 直接退出），使本入口的“显式配置校验”不可达，因此正式入口固定使用 `--config-file`。这是刻意规避原生参数冲突，不是回落其他环境文件。

退出码：

- `status` / `verify`：有 issues 时退出码 1，只读且不创建缺失的 `migrations` 表。
- `run`：配置、预检、执行、后验任一失败均非 0；成功（含 0 条 pending）退出 0。

## 4. status：升级前只读检查

`migration:status` 输出：

- 实际目标 `host:port/database` 与 MySQL 版本。
- `migrations` 表是否存在、历史条数、仓库迁移条数、pending 条数与名称。
- issues / warnings。

会失败关闭（非 0）的情况：

- `migrations` 表不存在，或历史不是仓库迁移的完整、有序前缀。
- 历史存在未知迁移、重复记录、时间戳不一致、缺口或顺序错。
- 已记录迁移应当创建的表实际缺失（结构漂移）。
- 关键索引/外键的实际定义与契约不符：同名索引被改列、列序改变、唯一性改变；外键本地列、引用表、引用列或列序改变；关键索引为表达式索引或前缀索引。
- 关键索引/外键在契约中缺少有序列定义、列数组为空或本地列/引用列数量不匹配。
- pending 迁移应创建的表/列/索引/约束已存在但无对应记录（疑似半迁移）。

status 只读，不会补历史、不会建表、不会执行迁移。

## 5. run：执行与后验

`migration:run` 的顺序：

1. 校验双确认与显式配置，核对实际连接目标。
2. 获取目标库连接级互斥锁（`GET_LOCK('lithography:migration:<库名>')`），持有到结束；另一个进程会明确失败，不会并发 DDL。
3. 运行与 status 相同的只读预检；任何 issue 在第一条 DDL/DML 前拒绝。
4. 仅执行 pending 迁移，顺序必须与仓库一致；不重跑已记录迁移。
5. 升级后核验：
   - 历史由 14 条增至 24 条，新增 10 条名称正确；
   - 原 14 张表 + 新增 9 张，共 23 张业务/基础表（`migrations` / `typeorm_metadata` 单独计数）；
   - 关键列、索引唯一性及有序列、外键本地列/引用表/引用列有序列、CHECK；
   - 关键索引不是表达式索引或前缀索引；
   - 旧参考资料 `owner_organization_id` 指向 `CLIENT_DEFAULT`，`ingest_method=ADMIN_DIRECT`，无 NULL/悬空；
   - 旧账号/机型/资料业务字段、正文、文件引用、软删事实、关联与创建信息保留。
6. 再次确认 pending 为 0。

若已完整升级，`run` 报告 `executed=[]` 并以 0 退出，不视为异常。

`run` 只在主流程无错误、连接销毁与迁移锁释放均成功、结果有效后，最后打印一次
`升级完成：历史 <N> 条，业务表 <M> 张，再次执行 0 条`。该行必须是成功输出的最后一行；
任何失败（含收尾失败）都不得出现该文案。

## 6. verify：终态只读核验

`migration:verify` 不执行迁移，只核验历史完整、结构齐备、数据回填正确、pending 为 0。结构与 `status`/`run` 预检使用同一套比较规则：关键索引比较唯一性和完整有序列，关键外键比较本地列、引用表、引用列及列序，并核对引用 schema。交接前至少执行一次并保留脱敏输出。

## 7. 失败恢复手册

**必须先理解**：MySQL DDL 隐式提交。TypeORM 的 `transaction` 选项**不能保证**整批迁移失败后恢复旧结构；单条 DDL 原子性不等于多条迁移原子性。本入口失败后只做只读诊断，不自动 `down`、不 `DROP`、不删记录、不 Seed、不自动重跑。

失败后的处理顺序：

1. **立即停止**：停止业务写入，不要再次执行 `run`。
2. **保存现场**（只读，脱敏后留档）：
   - `SHOW TABLES`；
   - `SELECT id, timestamp, name FROM migrations ORDER BY id`；
   - `information_schema` 中相关表/列/索引/外键/CHECK；
   - 命令输出、退出码、失败迁移名与错误摘要。
3. **判定状态并选择流程**：按恢复后的实际状态对照下表执行，不能只凭记录条数判定。
4. **恢复或继续**：需要恢复时用升级前备份恢复目标库（必要时先重建库再导入），或由维护者评审后人工回退。恢复完成后按上表流程重新 `status`，不要直接跳到 `run`。

| 恢复后的状态 | 正确流程 |
| --- | --- |
| 已完整恢复到旧 14 条或其他受支持干净前缀 | 重新确认安全目标/停写/备份 → `status` 核对历史与前缀结构 → `run` → `verify` |
| 恢复为完整当前 24 条终态 | `status` → `verify`；需要验证 `run` 时，`run` 应报告执行 0 条 |
| 部分 DDL 已生效但无对应历史 | 停止；保留现场，走已确认的备份恢复或维护者审核的前向修复；不盲目重跑 |
| 已记录完整前缀且结构匹配，后续没有残留对象 | 人工核对现场与操作条件后继续执行 pending 迁移 |
| 连接中断、执行结果未知 | 先重连做只读核对（历史、真实对象、pending 残留），再按上表分类；不能推断“失败就一定没写入” |

**注意**：`verify` 是当前终态检查。旧库尚未升级时 `verify` 非 0 是预期结果，不能把它当作 `run` 前的必须门禁；
旧前缀的正确顺序是 `status` → `run` → `verify`，只有完整终态才可直接 `status` → `verify`。

严禁的“恢复”手段：

- 删除 `migrations` 记录制造 pending；
- 手工删除已建表/列来伪装干净；
- 直接调用迁移 `down`；
- 运行 Seed；
- 用演练脚本清库。

## 8. 常见失败与含义

| 输出关键字 | 含义 | 处理 |
| --- | --- | --- |
| 互斥锁 | 另一进程正持有同库迁移锁 | 等待其结束后重试；不要绕过锁 |
| 历史不是完整有序前缀 / 未知迁移 / 重复记录 | 迁移记录与仓库不一致 | 停止写入，核对历史来源；未知版本不得猜测放行 |
| 结构缺失 / 关键索引、字段、CHECK、外键缺失或索引、外键定义不符（含列序/唯一性/引用映射/表达式或前缀索引） | 已执行前缀的实际结构与契约不一致 | 停止写入，按结构漂移处理，优先恢复备份 |
| 疑似半迁移 | pending 迁移对象已存在但无记录 | 按脏中间态处理；不得盲目重跑 |
| 环境文件不存在 / 缺少 DB_* / 目标不一致 | 显式配置错误 | 修正配置后重新 status |
| DDL 执行失败 | 单条迁移失败 | 保存现场，按第 7 节恢复 |

## 9. 向 A 反馈时提供什么

可提供：目标 `host:port/database`、MySQL 版本、执行命令、退出码、issues/warnings 文本、失败迁移名称、历史迁移名称与时间戳、脱敏错误摘要。

不要提供：数据库密码、完整连接串、业务数据内容、密钥。

## 10. 测试入口（供复核）

- 单元：`npm run test:unit -- src/infrastructure/database/incremental-migration.spec.ts`（默认运行）。
- 实库：需显式破坏性授权，仅对隔离库 `lithography_e2e`：

```bash
MIGRATION_INTEGRATION=1 MIGRATION_INTEGRATION_ALLOW_DESTRUCTIVE=1 \
  npx jest src/infrastructure/database/incremental-migration.integration.spec.ts --runInBand
```

实库测试会清空并重建 `lithography_e2e`，结束后不会自动恢复；执行前必须先备份该库。
