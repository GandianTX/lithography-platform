## 3. 问题清单

### R01 [P1] 投稿加锁后仍读旧事务快照，会丢草稿修改并冻结旧内容/附件

- 位置：`backend/src/modules/lithography/queries/content-submission.query.service.ts:858`、`:872`、`:414`；调用入口 `backend/src/usecases/content-submission/update-content-submission-draft.usecase.ts:114`、`:138` 和 `submit-content-submission.usecase.ts:111`。
- 方向：数据、事务、状态时序。
- 最小触发条件：MySQL/InnoDB 使用 REPEATABLE READ；同一工程师两个请求在先前写事务提交前，均已完成事务内组织 SELECT。其中一个请求等待同一投稿主表行锁。TransactionRunner 未指定其他隔离级别。
- 当前行为：`content-submission-write-guard.ts:35` 先执行成员查询，`:40` 才锁主表。主表锁是当前读，但随后明细 `findOne` 和送审附件 `findOne` 没有锁定读；它们仍可能使用组织查询建立的旧一致性快照。更新用例将旧明细与补丁合并，再全量覆盖；送审用旧字段/旧 CURRENT 事实形成永久快照。
- 期望行为及依据：任务书 §3.3、S3、S4 要求在串行化后读取真实当前稿与当次有效附件；历史 G2/F01 修复要求已经明确“拿到主表锁不使普通 SELECT 自动成为当前读”。该不变量同样适用于本次新投稿流程，而非只适用于正式案例更正。
- 最小反例：初始 `title=old-title, description=old-description`。A 改标题为 `A-new-title`；B 已建立旧快照，等 A 提交后获得主表锁，再改说明。两个请求都成功，最终标题却回退成 `old-title`。另一反例中 B 改为送审：当前稿标题是 `A-new-title`，冻结标题却是 `old-title`。
- 影响：用户已保存的不同字段被静默覆盖；审核员看到的冻结内容可能不是送审时真实当前稿。附件替换/移除与送审也命中同一旧快照读取家族，可能冻结已退役附件或漏掉新附件。
- 现有测试为什么未发现：投稿单测将明细读取 mock 为即时固定值；集成并发主要验证“附件替换后一个 CURRENT”“送审只生成一次版本”“审批唯一”，没有强制“等待者先建立旧快照，再等待锁，再合并/冻结”的交错。
- 最小无债修复方向：保留主表互斥、固定锁顺序和现有事务入口；为写流程的明细和送审附件提供显式事务内当前读。读页面的普通查询保持不变；不要全局调低隔离级别，也不要新增版本列或用接口重试掩盖丢更新。
- 必补回归：两类草稿分别测试不同字段并发保存；保存→送审冻结最新字段；附件替换→送审冻结新附件；移除→送审不得复用旧附件。使用两个独立连接和可控屏障，显式记录隔离级别及建立快照的时点。增加查询锁选项契约测试，避免只测 mock 后的正确结果。
- 实际证据：运行真实 `UpdateContentSubmissionDraftUsecase`、`SubmitContentSubmissionUsecase`、写/查询 Service 和真实组织解析代码，仅用明确 RR/行锁模型替代 EntityManager。两组反例均断言成功；不是实库复现，实库回归仍未验证。
- 级别依据：有明确高风险调用链和确定性反例，可造成成功写入被覆盖及永久冻结内容不符，按 P1。
- 归属：当前 PR0，关联 T05/T08/T09；不得推给表单页面 PR。

### R02 [P1] “带 WHERE 的清理”未证明行级所有权，仍会删除碰撞记录并部分清理后才失败

- 位置：`backend/test/utils/test-organizations.ts:170`、`:180`；`backend/test/utils/test-accounts.ts:202`、`:168`；组合入口 `backend/test/utils/e2e-scoped-cleanup.ts:70`。固定 ID 同族：`backend/test/09-reference-document/reference-document.e2e-spec.ts:161` 和 `backend/test/12-reference-document-case/reference-document-case.e2e-spec.ts:267`。
- 方向：测试数据安全、清理生命周期。
- 最小触发条件：允许的隔离库中存在非本次创建的同登录名账号、同组织编码记录，或 id=43 的非本规格机型；执行者已提供合法清理许可。即便没有自然键碰撞，目标父记录存在范围外引用时也会触发部分清理风险。
- 当前行为：组织 helper 只用编码子查询连续执行十类 DELETE；账号 helper 只 SELECT id，然后删全部命中账号的成员/资料/账号。机型直接按固定 id 删除。没有本轮创建清单、关键字段核验和完整引用闭包预检。组合清理先删组织链再核验后续账号/机型；某条后续 RESTRICT 失败不能恢复前面已完成的删除。
- 期望行为及依据：终审工作流 §3 明确要求运行、语义、引用闭包四层证明；自然标识和固定 ID 不能作为删除授权。当前 G4 要求 beforeAll/afterAll 只清已确认目标，异主数据和中途失败均不被误伤。
- 最小反例一：隔离库先放入 `loginName=teststaffprimary`、但邮箱/角色/创建身份不是夹具的账号。当前 helper 只读取 `{id:true}`，无法辨别异主，继续发出成员、user_info、account 三类删除。
- 最小反例二：先放入未被任何业务引用、`id=43, modelCode=KEEP-NONFIXTURE` 的机型。09 组 beforeAll 的 `extraCleanup` 直接删除它；固定 ID 并不能证明它属于本规格。
- 影响：污染/破坏同一隔离库中其他测试或手工验证数据；组织清理还会将“其他组织拥有、但来源关联目标投稿”的正式资料纳入删除，而非视为越界引用先拒绝。
- 现有测试为什么未发现：清理验收 KEEP/MINE 使用不同自然标识；假 DataSource 规格把直接十类删除当作预期调用序。未覆盖同名异主、固定 ID 异主、外部引用闭包冲突，以及冲突发生前 DELETE=0。
- 最小无债修复方向：本轮造数使用数据库生成 ID 并立即登记；正常回收只处理清单内 ID，并在删除前重新校验归属和外部引用。确需恢复旧残留时，采用该规格可证明的完整字段/关系指纹，不按编码/登录名默认接管。组合清理先完成所有预检，再事务内按外键顺序删除；底层可直接调用的破坏性入口也应保证门禁不可绕过。仅修改本次接入的消费者，不重构未触及的历史测试。
- 必补回归：同名异主、同 id 异主、异组织成员、外部记录引用目标父级时全部 fail-closed，第一条 DELETE 调用为 0，所有行逐字段不变；beforeAll 各阶段失败只回收已登记记录；关闭全局 TRUNCATE，在非空库连续运行两次；用例单跑与 core 全组一致。
- 实际证据：对真实 `runGuardedSpecCleanup` 执行 recording DataSource 反例，环境守卫正常，组织预检为零却发出十类 DELETE；注入异主账号只选 id 后继续三类删除。未实际删除任何数据库行。固定 id=43 路径已按真实 beforeAll 调用链确认。
- 级别依据：不是仅缺测试；实际删除条件已明确命中不属于本规格的记录，属于可触发误删路径，按 P1。

### R03 [P1] 新组织/成员 Seed 缺少碰撞归属保护，可改写非 Mock 组织成员关系

- 位置：`backend/scripts/seed-mock.ts:627`、`:658`，特别是 `:672` 的更新列；公共 upsert 在 `:365` 附近；实际入口 `:2885`、`:2886`。
- 方向：数据、权限事实、测试造数。
- 最小触发条件：允许 Seed 的非生产库中，`organization_membership.id=915001` 已被另一账号/组织占用，且尚无 Seed 目标 `(organization_id,account_id)` 关系；其他 Seed 数据正常。该 id 位于预留区不构成行的所有权证明。

- 影响：原有组织成员关系被剥夺或重新归属，可信组织上下文随之改变；组织停用/启用等事实也有被 Seed 改写风险。事务只在抛错时回滚，而现有数量/分布校验无法识别一个已被改写成“正确 Seed”的碰撞行。

- 最小无债修复方向：组织按稳定编码解析实际 id，固定 id 和业务键冲突都先证明归属；成员关系核验 id 与组织/账号的精确对应，任何异主碰撞失败关闭。新建组织/成员可使用自增 id，避免依赖固定主键；不要新增表，也不要把整个库划成可被 Seed 重置的数据区。
