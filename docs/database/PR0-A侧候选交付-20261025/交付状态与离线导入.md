## 两种交付方式

### 网络/认证恢复后

A 在当前仓库正常推送功能分支，不 force、不推 main：

```bash
git push fork HEAD:refs/heads/feat/data-collection-core
git ls-remote fork refs/heads/feat/data-collection-core
git rev-parse HEAD
```

推送退出0且远端 SHA 与本地候选一致后，再让 B 拉取完整候选。不要把凭据发进聊天或文档；可由用户在本机恢复 GitHub SSH/凭据助手，或交由有权限的 B 管理 fork。

### 先离线交给 B

本轮提供 `PR0-A-candidate.bundle`。它包含目标 main 基线 `cc4c87e57e328eee3893a07f3776880f56e1b226` 之后的 PR0 提交和本轮候选，不包含 `.env`、未跟踪 Word、日志、数据库或构建物。

先将该文件发送 B。B 在具有上述基线历史的项目克隆中运行（路径替换为自己收到的文件）：

```bash
git bundle verify /path/to/PR0-A-candidate.bundle
git fetch /path/to/PR0-A-candidate.bundle refs/heads/feat/data-collection-core:refs/remotes/offline/pr0-a-candidate
```

确认自己的工作区没有未保存改动，再在**尚不存在的新分支**检出候选；遇到本地分支重名或改动冲突时停止，不 reset/覆盖：

```bash
git switch -c codex/pr0-a-candidate refs/remotes/offline/pr0-a-candidate
git rev-parse HEAD
```

最后一条的 SHA 应与 A 本次交付消息中的最终候选 SHA 一致。bundle 验证缺前置基线时，先补齐正确仓库历史，不能强行导入到无关仓库。

确认版本后，按 [B 独立验收入口](./B独立验收入口.md) 运行两条链并填写实际结果。离线导入不等于 B 已签收，也不等于 fork 已更新；后续仍由 B 按协作约定管理 fork，负责人处理上游合并。
