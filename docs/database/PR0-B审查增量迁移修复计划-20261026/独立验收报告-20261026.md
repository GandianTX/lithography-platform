## 4. 当前修复候选的问题

### R1 / P2：成功分支的 return 绕过收尾错误判定，CLI 错误退出为0

- **位置**：`backend/src/infrastructure/database/incremental-migration.ts:1188`、`:1223`、`:1236`、`:1258`；同族只读路径 `:1278`、`:1282`、`:1297`。
- **最小触发条件**：正常 run / status / verify 完成后，`DataSource.destroy()` 抛错；不需要迁移本身失败。
- **当前行为**：try 中的 return 会在 finally 完成后直接返回；finally 把错误收进数组，却没有抛出，后面的统一判定无法执行。run 只打印收尾错误仍 exit0；status/verify 连收尾错误也没有输出。
- **期望与依据**：计划4.1“退出/资源”和 M08 要求收尾失败可见、非0、无假成功；不能只靠 helper 本身正确。
- **真实反例**：临时预加载工具在调用真实 destroy 关闭连接后抛出 `review-injected-close-failure`。三个真实CLI均 exit0；run stderr包含该错误，status/verify stderr不包含。函数级反例也返回成功。
- **影响**：自动化或B依据退出码会误认升级/核验已成功；锁释放失败属于同一控制流家族，也可能被吞掉。
- **为何测试未发现**：单测 `incremental-migration.spec.ts:187` 之后只验证 `collectCleanupErrors` / `attachCleanupErrors`，没有实际跑通过成功分支再失败的执行器或CLI；回执`:103`将 M08 错写成“升级后结构/回填核验”。
- **最小修复**：暂存成功结果，finally 后统一判断主因和收尾错误，再决定抛出或返回；同步修复run及只读生命周期，不改Migration。修正回执M08对应关系。
- **必须补测**：run有pending/零pending，status、verify分别覆盖仅收尾失败；主因+收尾同时失败；锁释放失败后仍尝试断连；真实CLI非0断言。
- **归属**：当前修复候选。证据：`T/extra-cli-results.json`、`T/counterexamples-result.json`；临时注入工具只在审查侧，不进入交付实现。

### R2 / P2：预检只确认已执行迁移创建的表，缺索引旧库仍先执行升级

- **位置**：`backend/src/infrastructure/database/incremental-migration.ts:647`，尤其`:652`—`:656`；最终索引检查位于`:728`附近，已在执行迁移之后。
- **最小触发条件**：14条历史正确、旧表齐全，但 `base_user_account.uk_login_email` 缺失。仅在独立合成副本删除该索引制造反例。
- **当前行为**：status exit0；run继续执行全部新增10条，历史到24且创建organization后，才因“升级后校验失败”exit1。
- **期望与依据**：计划G2/M03要求已有记录对应结构漂移在第一条升级DDL/DML前拒绝；这不是额外数据库治理。该旧索引本就被当前共享终态契约列为关键索引。
- **影响**：将明确不符合旧基线的库推入已写入的新状态，失去预检“拒绝盲跑”的交付保证；本次没有观察到旧行误删，故不升级为P1。
- **为何测试未发现**：集成M03的结构异常只通过删除整张reference_document验证，未覆盖表仍存在但索引、列、约束缺失的情况。
- **最小修复**：增加与已执行历史对应的窄结构预检，核对该前缀应存在的关键列/索引/约束；覆盖已有ALTER对象，避免把未来pending才应存在的对象错误要求提前存在。不改旧Migration，不扩展为任意版本修复引擎。
- **必须补测**：旧前缀缺关键索引/列/约束时status与run均非0；业务结构和迁移历史前后不变，目标升级DDL/DML次数0；合法14条及完整24条仍通过。

### R3 / P2：恢复说明要求旧库先通过终态verify，无法按说明重新升级

- **位置**：`docs/database/增量升级操作说明-20261026.md:120`—`:121`；verify定义在同文件`:101`—`:103`，代码 `incremental-migration.ts:946` 附近检查历史必须完整。
- **最小触发条件**：失败后从升级前备份恢复到正常14条旧库，准备重新执行pending。
- **当前行为**：恢复手册要求“status无issues、verify通过后再run”；但verify要求当前24条及新增结构完整，因此在旧库必然exit1。实测恢复副本status exit0，verify exit1且报告“迁移未完成”。
- **期望与依据**：计划G3/6.2要求旧备份恢复后有可执行的安全继续路径；终态校验用于升级后，不应阻塞符合旧前缀的升级前状态。
- **影响**：B照文档无法完成恢复—重试闭环，可能被迫跳过检查或错误手工改库。
- **为何测试未发现**：M07只断言DDL失败后的保留和诊断，没有沿恢复说明走完恢复旧备份、预检、run、终态verify的顺序。
- **最小修复**：恢复后只读确认目标、历史/旧前缀结构与预期匹配，经安全确认后status→run→verify；若恢复的是完整终态则可以直接verify。明确完整前缀可继续、脏中间态需人工恢复/维护者前向修复，不能笼统放行。
- **必须补测/证据**：干净旧备份恢复后可按实际手册完成14→24→verify；半迁移未恢复时仍拒绝；备份导入需确认新目标或完整恢复，不能仅导入旧dump留下无记录新对象。
- **归属**：当前交接。证据：`T/extra-cli-results.json` 的 `review_recovery` 两项。
