## 4. F1：修复收尾失败假成功（R1/P2）

主要文件：`backend/src/infrastructure/database/incremental-migration.ts`、相邻单元/集成测试；必要时修改薄CLI的错误呈现。

### 实现要求

1. 扫描 `runIncrementalMigration`、`withReadOnlyDataSource` 及直接使用的收尾helper，收敛同族问题。
2. try内只计算并暂存结果；finally负责尝试释放锁、关闭资源，收集全部收尾错误；finally结束后统一判定。
3. 判定顺序：有主因则保留并附加收尾错误；没有主因但收尾失败则抛收尾错误；两者均无才返回成功结果。
4. 使用显式完成标志或带状态结果区分“没有结果”和合法返回值，不靠truthy判断，不用非空断言掩盖漏赋值。
5. 释放锁失败仍尝试关闭DataSource；初始化/取锁/预检失败也按实际已取得资源收尾。保留已有主因，不被诊断失败覆盖。
6. status/verify同样把收尾错误交给CLI呈现，不能静默。最终成功表述及exit0须以收尾完成为前提。
7. 不把收尾错误等同于DDL已回滚；提示核对实际结构和历史，不自动重试或补偿。

### 必补测试

| 场景 | 必须断言 |
| --- | --- |
| 有pending正常执行、零pending空操作 | 成功且结果完整；资源关闭一次，无异常 |
| 上述两类成功后destroy失败 | 执行器reject；CLI非0；收尾原因可见 |
| status/verify查询成功后destroy失败 | 两入口均reject；CLI非0，不能吞错 |
| 解锁失败 | 仍尝试关闭连接，CLI非0，解锁错误可见 |
| 迁移/查询主因 + 解锁/断连失败 | 主因保留，附加错误全部可见；不能只剩最后一个错误 |
| 诊断再次失败 | 原始主因仍保留；没有假成功或自动重试 |

必须通过实际执行器/CLI控制流，不能只测 `collectCleanupErrors` / `attachCleanupErrors`。
CLI故障可由测试专用预加载/受控DataSource注入；对应工具须随测试交付，不能依赖 `/tmp` 私有脚本。

## 5. F2：修复已执行前缀结构预检（R2/P2）

主要文件：执行器、`migration-schema-contract.ts` 及相邻测试。

### 最小设计

- 保留现有历史完整前缀检查和pending对象残留检查，新增“当前已执行前缀应具备的关键结构”检查。
- 优先在共享契约中为关键结构登记对应迁移名称/时间戳，按已执行集合选取应检查项；复用明确查询函数。
  不靠写死“只有14或24合法”，也不直接对旧库调用要求全部最终对象的终态校验。
- 覆盖当前契约已有关键列、索引、CHECK、外键，及已执行ALTER应存在的对象。应避免同名但错误类别/所属表
  的对象被误认；对关键约束核对契约需要的定义，如唯一性、目标列/引用关系和NOT NULL。
- 尚未执行迁移的对象不得提前要求存在；无记录却已存在的目标对象继续按半迁移拒绝。
- 只读元数据查询与状态分析；任何issue须在 `runMigrations` 和首条升级DDL/DML之前中止。
- 不尝试自动修复漂移。无法可靠匹配当前受支持前缀时，明确报差异并停止，不能以warning放行。
- 若继续使用源码提取，只能将其用于有明确覆盖和测试的辅助检查，不能让“文件能读、表名能找到”代替关键结构契约。

### 必补反例与防误报

| 场景 | 验收要求 |
| --- | --- |
| 原14条旧库缺关键索引、列、CHECK或外键 | status/run均拒绝；执行前后表/列/约束/历史/哨兵数据相同；无升级写入 |
| 已执行ALTER的合法前缀中相应对象缺失 | 预检拒绝，不只检查CREATE TABLE |
| 尚未执行ALTER，新增字段本来不存在 | 正常通过旧前缀预检，允许执行pending |
| 合法14条、合法中间前缀、完整24条 | 各按自身结构通过；旧库可升级，完整库run为0条 |
| pending对象已存在但无历史记录 | 保持失败关闭，无drop/fake/补历史 |
| 测试中的关键预检被跳过 | 缺对象反例必须失败；不能只以“最终未删除/函数返回”为证明 |

零写入断言应区分合法只读SELECT和升级DDL/DML；不能将所有数据库查询次数必须0作为测试目标。

## 6. F3：修复恢复手册并实际走通（R3/P2）

主要文件：`docs/database/增量升级操作说明-20261026.md`；对应集成测试/可复现验收步骤。

| 恢复后的状态 | 正确流程 |
| --- | --- |
| 已完整恢复到旧14条或其他受支持干净前缀 | 重新确认安全目标/停写/备份 → status核对历史与前缀结构 → run → verify |
| 恢复为完整当前24条终态 | status → verify；需要验证run时为0条 |
| 部分DDL已生效但无对应历史 | 停止；保留现场，走已确认的备份恢复或维护者审核的前向修复；不盲重跑 |
| 已记录完整前缀且结构匹配，后续没有残留 | 人工核对现场和操作条件后继续pending；不能只凭记录条数判定 |
| 连接中断、结果未知 | 先重连只读核对历史/真实对象，按上述状态分类，不能推断“失败就没写入” |

明确：verify是当前终态检查；旧库尚未升级时verify非0是预期，不能作为run前必须通过的门禁。
旧备份导入不能自动清除新对象。恢复到新隔离目标或执行已授权的完整恢复后，再证明历史与真实结构匹配；
不能把“导入命令exit0”当作“已回到干净旧结构”。正式runner不得为此新增自动删库/删表功能。

必做实测：在独立实例制造真实DDL部分失败 → 记录现场 → 将旧备份恢复至干净副本 → 按手册status/run/verify
完成升级 → 再run为0条；另保留未恢复脏目标，证明它仍拒绝。记录每步退出码、历史、关键对象与旧数据对照。
