## 4. G1：正式迁移入口设计

### 4.1 拟提供的命令契约

以下为**拟新增接口示例，当前尚不可执行**，实施时要同步文档与测试，不能只增加 npm 别名却仍调用清表脚本。

```text
npm run migration:status -- --env-file <明确配置文件> --database <目标库>
npm run migration:run -- --env-file <明确配置文件> --database <目标库> --confirm-database <再次确认的目标库>
npm run migration:verify -- --env-file <明确配置文件> --database <目标库>
```

| 行为 | 必须满足的契约 |
| --- | --- |
| 配置 | 指定文件缺失/无效立即失败，不能自动回落至另一份 .env；不得输出密码/密钥 |
| 目标 | 配置目标、参数声明与实际 `SELECT DATABASE()` 一致；输出脱敏host/port/database供核对，发现不一致拒绝写入 |
| status / verify | 只读；不创建缺失的 migrations 表、不回填历史、不运行迁移或Seed；不能盲用可能建历史表的 ORM helper |
| run | 单独显式确认写目标；完成只读预检后运行既有待执行迁移，成功后核验；不创建/删除目标库，不自动补Seed |
| 迁移源 | 固定仓库当前迁移目录，明确TS/编译JS模式，避免同一迁移被重复加载；不接受任意SQL或任意来源路径 |
| 运行环境 | `synchronize=false`、`dropSchema=false`、`migrationsRun=false`，不靠应用启动自动改库 |
| 空待执行集合 | 已完整升级且结构核验通过时，run成功退出并明确0条，不当异常 |
| 并发 | 同一目标只允许一个run进程；使用最小连接级互斥/清晰失败，锁持有连接保持至结束；不新建业务锁表或分布式平台 |
| 退出/资源 | 成功exit0，配置/预检/执行/后验失败非0；finally关闭连接/释放锁，清理失败不能覆盖原始主因或假成功 |

如旧库没有 migrations 记录、记录与实际表不匹配或历史来自未知版本，应失败关闭并说明缺什么。不能猜测“有十四张表就等于十四条迁移已执行”。

## 6. G3：MySQL DDL 部分失败与恢复

**必须写明：MySQL DDL隐式提交，TypeORM事务选项不能保证整批迁移失败后恢复旧结构。单条DDL原子性不等于多条迁移原子性。**

本候选最后一条迁移包含多次ALTER、默认组织建立和旧资料回填，不能只用一次事务异常就认定之前语句均已撤销。

### 6.1 失败时工具应做什么

1. 非0退出，记录原始失败迁移/阶段与脱敏错误；对失败事务不作“已整体回滚”承诺。
2. 尽可能只读列出已记录历史、仍pending清单和疑似已生效对象；诊断失败也保留原始主因。
3. 不自动down、不删新增表/列、不清迁移记录、不fake、不自动Seed、不自动重跑。
4. 释放进程资源；待人工确认前阻断继续升级和正式交接。

### 6.2 恢复决策

| 现场 | 推荐处理 |
| --- | --- |
| 无任何目标DDL/DML生效 | 修正配置/权限/环境后重新status，检查目标仍匹配再run |
| 已完成迁移形成完整前缀、结构完全匹配，后续未生效 | 只读确认及记录后，依正式入口继续待执行部分；不能仅凭记录条数判断 |
| 对象已存在但迁移未记录、字段/约束只完成部分 | 停止；优先恢复升级前备份至隔离副本验证；或由维护者确认专门前向修复，不让执行人临时猜测补SQL |
| 客户端掉线，提交/历史写入结果未知 | 重连只读核对历史与真实结构，不按“收到失败”推断“库没变”，不盲重试 |
| 数据本身不满足新约束 | 记录具体数据问题，先在脱敏副本制定受控处理，不删除原数据凑约束 |

不把恢复设计扩展成自动修复任意历史库；本轮只需要明确可观察、可停止、可复现与人工恢复边界。
