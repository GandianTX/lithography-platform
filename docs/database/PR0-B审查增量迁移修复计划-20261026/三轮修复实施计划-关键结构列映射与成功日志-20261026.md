## 4. T1：补足列定义契约

主要位置：`backend/src/infrastructure/database/migration-schema-contract.ts` 中现有关键索引/外键清单、
`PrefixStructureRequirement`、`collectPrefixStructureRequirements`。

1. 从现有Migration逐项核对当前关键索引和外键，不以当前可能漂移的数据库作为定义来源。
2. 索引至少登记：所属表、名称、唯一性、**有序列数组**。例如 `uk_login_email → ['login_email']`。
3. 外键至少登记：所属表、名称、**有序本地列数组**、引用表及**对应有序引用列数组**；实际引用schema须匹配
   预期目标库。比如客户外键应为 `['customer_account_id'] → base_user_account.['id']`。
4. 复合定义保留顺序，不转Set。当前正式资料来源版本外键应保持本地
   `['source_revision_id', 'source_submission_id'] → content_submission_revision.['id', 'submission_id']`。
5. 使用合适的类型区分索引与外键要求；避免可选字段缺失后用空数组、undefined或默认值当作已验证。
   数组为空、长度不匹配、缺所属迁移/定义时明确失败，不warning放行。
6. 继续按所属迁移过滤“已执行前缀应有对象”，不能把24条终态的未来对象要求提前施加到14/20条库。
7. 复用同一份关键结构定义，不另建一份只供verify使用的列清单。纯空库演练可保留其原检查流程，但共享契约
   的直接消费者必须回归，不能因改类型导致原入口无法运行。

## 5. T2：共用只读比较，覆盖三个入口

主要位置：`incremental-migration.ts` 的 `collectPrefixStructureIssues`、`inspectMigrationState`、
`collectStructuralIssues` / `verifyMigrationState`。优先提取窄比较函数，避免复制两套检查。

| 对象 | 查询与比较要求 | 禁止的替代判断 |
| --- | --- | --- |
| 索引 | 从statistics读取全部列，按SEQ_IN_INDEX排序；比较完整有序列、唯一性和必要元数据 | LIMIT1、只比名称/列数、把列序转Set、只查NON_UNIQUE |
| 外键 | 联合key_column_usage及必要约束元数据，按ORDINAL_POSITION比较本地列与对应引用列，同时核对引用表/schema | 只查referential_constraints中的约束名和引用表 |
| 异常结果 | 不能可靠解释的元数据明确报错/拒绝，指出脱敏后的对象与预期/实际差异 | 空结果默认成功、类型强转掩盖异常、跳过未支持定义 |

当前关键索引是普通列索引；若元数据出现与基线不符的前缀/表达式定义，不得仅凭同一列名放行。只需覆盖当前
契约允许的形式并明确拒绝不匹配，不要求建设通用索引语法解析器。

入口约束：

- `status`：只读报告当前前缀定义差异；CLI有issue即非0。
- `run`：同一只读预检在runMigrations与首条升级DDL/DML之前完成；发现差异不改变结构、历史或旧行。
- `verify`：当前终态也用同一列定义规则，不能只修status而让已升级错误结构继续verify=0。
- 合法旧前缀的verify仍可因“未到当前终态”非0；不把它误设为升级前门禁。
- 不把授权/元数据SELECT次数必须0作为零写入断言；要分别观察升级DDL/DML和合法只读查询。

## 6. T3：最终成功确认移到收尾后

位置：执行器当前约1349行的“升级完成”提示，以及finally后统一结果返回位置。

- 执行阶段可以记录“已执行N条”“结构检查通过”等事实，最终“升级完成”必须在无主因、无收尾错误、结果有效后打印。
- 有pending正常成功时最终确认一次；零pending完成确认同样不能早于收尾。
- 迁移失败、解锁失败、断连失败时最终成功确认零次，仍非0；原始主因和附加收尾错误继续可见。
- 不借移动日志改变失败诊断、资源释放顺序或已落地DDL的恢复语义。
