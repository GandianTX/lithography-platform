## 2. 复核方法与证伪假设

复核不是逐行认可实现回执，而是按“若实现有缺陷，哪条真实入口会先露馅”重跑：

1. **重读实现**：确认 `CREATE DATABASE` 不带 `IF NOT EXISTS`、只有明确成功才产生所有权；碰撞/未知/权限拒绝不 DROP；teardown 四步独立 `try/catch`，最早错误为主因。
2. **真实子进程**：H 规格以真实 `run-e2e-group.js --file` 启动 G04 子进程，不替换 Jest、不伪造生命周期；故意失败子进程与父规格通过分别统计。
3. **真实数据库**：独立 MySQL 8.0.46 + Redis 7.0.15；探针库由 G04 自己创建、克隆 schema、单会话 `USE` 切库、造数、清理。
4. **真实事务**：D1 第二笔失败发生在真实创建事务 `afterInsert`，不是只检查报错字符串。
5. **负对照**：临时恢复“先 DROP / 自行授权 / 首错中断 / DROP 失败不恢复不关闭 / 单笔事务”机制，要求目标断言实际变红。
6. **两轮与哨兵**：同一候选、同一库、不重置连续两轮完整 core；两轮之间逐行与文件 SHA 比对。

复核中主动检验的关键假设：

- **假设“skip 清理开关真实生效”**：日志显示 `全局清理已跳过`，且两轮后哨兵计数与运行前一致；若开关未生效，哨兵必被 TRUNCATE 清空，H01 的异主标记行也会消失。
- **假设“非夹具数据不会与既有断言冲突”**：Round 0 校准轮推翻了该假设（未软删的哨兵维修申请使 `total` 由 2 变 3），因此改为软删哨兵并重新建立基线；该轮不作为通过证据。

- **假设“探针库会被遗留”**：两轮及负对照还原后 `information_schema.SCHEMATA` 中均无 `lithography_e2e_probe`；H06 单独保留场景由父侧夹具清理收口。
