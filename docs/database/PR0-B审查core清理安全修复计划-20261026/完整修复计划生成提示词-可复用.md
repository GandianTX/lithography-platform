# 完整修复计划生成提示词（可直接复制）

将下面整段发给 AI；能提供时补上末尾的路径和报告。AI 应先读取材料再制定计划，不应仅复述问题或直接开始改代码。

```text
当前修复经历了多轮“修完又发现同类问题”。请基于当前项目实际状态，制定一份能够收敛当前交付范围的完整修复计划。本轮只读取、分析和生成新的计划文档，不修改代码、既有文档、PR、数据库或外部系统，不自动提交或推送。

协作背景：由你制定计划，我会在 Trae 或其他工具中让另一 AI 执行，再交回独立复核。执行者不一定能看到这段聊天、原机器路径、临时证据或你的工具权限。因此计划必须自足，并增加“跨工具执行说明”：明确阅读顺序、必须一并提供的材料、仓库相对路径、用户/执行 AI/独立复核者/B 的职责，及当前事实与强制验收、实施建议的区别。明确“本轮只生成计划”约束制定者；用户后续授权执行时，执行 AI 可以在范围内实施，但不因此获准推送、合并或操作共享/真实环境。要求执行前核对当前代码和已有改动，不因旧快照不同而回退、不重复覆盖已完成修复；缺关键材料或安全环境时如实报告。执行回执必须包含改动、新增源码及配置指纹、可重跑入口、真实结果、证据边界和待办，不能用同一执行 AI 的自审代签独立复核或 B 验收。

一、先理解和独立推导，再照历史问题核对
1. 读取项目规则、任务书、实际目标分支到当前候选的完整差异、当前 Review、修复计划和验收报告。包括未提交及未跟踪文件，不能只看最新 commit。
2. 开始时明确交付目标、纳入/不纳入范围、不可改变的基线和契约、本轮交付阶段、扩展触发及停止条件。
3. 在已知风险约束下，先从一次真实操作推演完整生命周期：输入/授权→准备/初始化→创建与登记→运行/状态变化→提交/回滚→清理/补偿→配置恢复/资源关闭→交接。自行提出可证伪的风险假设，再用历史问题和检查清单补遗漏。不要只围绕报告编号寻找修复位置。
4. 解释反复出现问题的共同机制：是根因未修、同族入口遗漏、新修复引入问题、环境/证据不足，还是验收范围发生了变化。不要把所有新发现都说成业务新增需求，也不要未经事实核验就判断已有实现错误。

二、一次性覆盖根因、同族和新增修复代码
5. 把每个已确认缺陷提升为当前范围内应成立的安全/行为不变量，列出违反位置、直接消费者及可到达的旁路。区分“已确认缺陷”“待验证假设”“已正确修复”“范围外”，不要混在待修列表里。
6. 公共 helper/API/状态/数据边界变化时，定位全部直接消费者；动态回归按实际行为差异选择。测试、脚本、runner、before/after、catch/finally、迁移/清理命令和文档中的执行入口也要检查，不能只审主函数或 it。
7. 对正常、拒绝、部分成功、后续步骤失败、初始化中断、重复执行、并发/响应晚到及收尾失败，选择当前实现确实相关的最小反例。不适用的分支写依据，不机械造用例。
8. 修复方案采用最小可行实现，保留已有效的修复；不为“完整”新增通用框架、扩大删除/授权范围、修改已接受基线或引入未获授权业务。已有实现部分满足时只补缺口，不推倒重写。
9. 特别审查计划将新增的测试与辅助函数：它们自己的准备、写删、归属、环境修改、故障注入、收尾和错误传播，必须满足与被测代码相同的约束。不能为了证明安全而引入新的破坏路径。

三、把计划写成可执行、可验收的闭环
10. 建立“需求/不变量→真实入口→外部行为→修复动作→测试→证据→完成状态”对应表。历史编号含义保持不变，相同验证引用同一证据，不重复堆清单。
11. 按依赖顺序列出任务表：负责人/角色、具体文件或入口、修改内容、最小反例、验收标准、依赖、交付物。不清楚人员分工时用职责角色，不凭空决定人名。
12. 对每个真实缺陷说明：原因、触发条件、影响、为何现有测试漏掉、最小修复方向、必须新增/复用的回归及证据。计划必须具体到行为，不只写“完善安全校验”“补充测试”。
13. 数据写删/清理相关时，覆盖显式授权、预期与实际目标、归属及稳定预期字段、首个副作用前预检、引用闭包、真实事务或补偿、结果未知、台账保留、其他资源释放及主/次错误。区分 DDL、事务 DML 和文件副作用，不能笼统声称都能回滚。
14. 高风险关键机制需要最小负对照：在安全临时副本撤掉目标保护，原反例应在相应断言失败；恢复后通过。不要用复制一份正确算法、只 mock 整个边界、只看报错文字或空库零残留来证明安全。
15. 明确哪些必须真实运行，哪些允许精确故障注入，以及每类证据不能外推到哪里。没有安全环境或运行结果时记未验证；不得用代码看起来正确代替验收。生成计划阶段不要求越权执行破坏性验证。
16. 给出环境准备、定向回归、必要完整回归、非目标数据保留、夹具/文件残留及证据交接方法。先修已知危险再运行全量，不把全量绿色当正确性的唯一证明，也不无故增加回归次数。
17. 最终结果绑定完整候选：HEAD、未提交与新增源码、相关配置/lock/runner 指纹、实际命令、环境、passed/failed/skipped 和退出码。内容变化只重验受影响命题；完整最终验收必须对应稳定候选。

四、明确什么叫完成，避免继续循环
18. 在实施前固定本轮完成定义，分别列出当前阻塞、必要补证、后续阶段待办和范围外建议。不要把等待 B 验收/远端 CI 等尚未到阶段的事项伪造完成，也不要无端前置成循环阻塞。
19. 已有证据按具体命题判断能否沿用，不要求重做所有历史验收；无法回读、候选不符或不覆盖新分支的证据不能当作当前通过。
20. 完成后须对完整生命周期独立复核，而非照开发者回执打勾。当前阻塞和必要证据缺口全部关闭即停止，不为了找新问题扩展到无关模块。新发现只有影响当前完成定义才纳入，其余记录建议归属。

请先核对当前文件，随后生成一个独立的 Markdown 修复计划；不要覆盖历史报告。计划开头注明当前事实、证据不足和实施边界，末尾附唯一完成条件与停止条件。简要说明它相较只修最后一轮问题，多覆盖了哪些实际风险。若确有不可自行决定的关键事项，先完成不依赖它的分析，只询问真正阻塞计划的最少问题。

材料（按实际情况替换；留空时先在项目中定位，找不到要说明）：
- 项目路径：
- 工作流路径：
- 任务书/交付目标：
- 当前问题或 Review：
- 既有修复计划与报告路径：
- 本轮交付阶段及已授权事项：
- 明确不允许改动的内容：
```
