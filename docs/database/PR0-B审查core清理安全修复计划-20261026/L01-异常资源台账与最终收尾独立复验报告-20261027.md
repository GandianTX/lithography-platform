## 3. [P2] L01 剩余：L-D 接收资源的账本仍仅存在于用例局部

1. **准确位置**：`backend/test/utils/e2e-probe-lifecycle-faults.e2e-spec.ts:336`—353，`cleanupLedger` 直接调用 `createProbeRunLedger()`，未进入模块级 `ownedLedgers`；真实 afterAll 第 195—214 行仅处理 `ownedLedgers.settle()`。
2. **最小触发**：L-D 的真实 J 子进程已 CREATE 成功且 FINAL 持续失败；L-D 已核验创建凭据并登记拥有者账本，随后它自己的回收在发送前暂时失败。
3. **当前行为**：`dropLedgerOwnedProbe` 正确保留局部账本而抛错，但用例退出后该账本不可达。真实 FINAL 的集合为空，输出 `FAULTS_FINAL=skipped-not-owned`，关闭应用，故障库遗留。
4. **期望行为**：有效接收的拥有者账本应立即登记入当前驱动器已有的规格级集合；正常回收成功后消费，失败仍能由真实最终收尾访问。已知未发送的暂时失败可有界精确回收；真实未知/持续失败可保留准确未决诊断，不能伪报无归属。
5. **任务依据**：L01 计划第 3 节要求所有真实 CREATE/有效交接都有规格生命周期可达的拥有者，第 4 节规定失败保留及真实收尾，第 5 节要求新增驱动自身同样安全。它与此前 H06 的遗漏是同一不变量，不是本轮新增业务标准。
6. **实际影响**：没有本轮外部数据误删实证；遗留本轮 `lithography_e2e_probe_fault`，下一次故障驱动会碰撞拒绝。回执“所有接收资源都已登记入集合”的结论尚不完整。
7. **现有测试为何漏掉**：L-D 将子 J 的持续失败作为被测场景，但假定 L-D 自己后续的拥有者回收总能成功。L-E/L-F 验证的是已登记集合中的资源，不能覆盖 L-D 这个漏登记的直接消费者。现有 6/6 正常通过不检验该父侧失败。
8. **最小修复方向**：使用现有 `ownedLedgers.add()` 把 L-D 的有效凭据账本登记到本规格集合，再 `record()` 和执行原回收；不重写 registry，不新建框架，不放宽凭据/归属，不按固定名清场。正常成功消费后，afterAll 仍为空跳过；失败后它必须看得到该账本。
9. **必须补回归**：有效凭据已登记后，拥有者第一次 DROP 明确发送前失败→真实 afterAll；断言原错误保留、对应账本被发现并安全处理、关闭执行，资源回收或准确未决状态。临时撤掉此 add 时，同一保护断言应失败。可复用现有驱动/精确子选择，避免递归跑整组。
10. **归属/级别**：当前 L01 的剩余 P2，不是另开一套新缺陷编号。原 H/J 修复继续有效，但 L01 暂不能整体关闭。

## 6. 执行事故：与代码缺陷分开记录

执行回执第 1、9、10 节披露：一次作废的第二轮首跑漏载自定义环境，落到本地默认 MySQL `127.0.0.1:3306 / lithography_e2e`、Redis `127.0.0.1:6379 / DB15`，执行全局 TRUNCATE 和 FLUSHDB；执行方称业务行已清空，无备份、未恢复。

本轮回读 `l01-core-round2.log`，确认该作废运行触及 2 个规格，出现两次 `skipDbCleanup=false, allowDbCleanup=true` 和“已清理 23 个表”，之后 auth 因缺物理清理许可失败退出；因此不能描述成“门禁拒绝前没有任何删除”。全局清理与 scoped 清理是不同许可入口。

证据边界：端口归属、Redis DB 与事故后数据状态按执行方披露记录；本轮没有连接这些服务重新查询。也没有足够证据独立确定清空前有多少需要保留的行，不把它擅自称作生产库损失或保证没有实际影响。

这不是复核者本轮执行的操作。当前源码修复范围不能自动授权恢复该库、重新造数、清空其他实例或将事故归零。**应由用户/该本地实例拥有者核对损失与是否重建测试数据。** 后续重跑必须先固定并核对实际目标、可丢弃归属及进程级清理配置；不能只凭一句 source 命令或库名包含 e2e 认定安全。

该事件单列为执行与交付风险，不虚构一个新的源码缺陷，也不因正确环境的两轮通过就声称事故已处理。作废运行不计入正式两轮，正确环境中 KEEP 不变仅证明正确目标未被影响。
