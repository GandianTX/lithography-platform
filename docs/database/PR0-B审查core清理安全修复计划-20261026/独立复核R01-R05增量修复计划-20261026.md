## 3. 各问题的实现要求

### 3.1 R02：本轮资源也要核验预期事实

推荐在现有测试台账旁增加按资源类别区分的**最小预期事实**，保留现有精确 ID 集合与清理计划结构，不把工具改造成任意表扫描器。

| 资源／关系 | 本次必须明确的事实 |
| --- | --- |
| 账号及 user_info | 创建返回 ID、loginName/email、身份/状态、昵称/角色等已用于归属判断的预期字段；userinfo 的 1:1 account_id 关系 |
| 型号 | 实际 ID、modelCode/modelName、enabled/sortOrder；明确哪些用例会合法修改 |
| 第三方绑定 | 实际绑定 ID、account_id、provider、provider_user_id、union_id；不能因账号归本轮而接管全部 provider |
| 维修申请 | 实际申请 ID、requestNo、客户/型号及现有内容指纹；合法接单/撤回变化有受控预期 |
| 工程师回复 | 实际回复 ID、父申请、工程师/客户及现有内容/状态指纹 |
| 验证记录 | 实际 ID、类型、目标/操作者/subject 关系及必要 payload 指纹 |
| 其他现有资源 | 逐类别复用现有父子核验与预期事实；本次若改变登记/删除契约，相应直接消费者不得遗漏 |

具体字段以实际 Entity、创建结果和现有指纹为准，只比较证明归属需要的字段。不要无差别比较所有列或易自动变化的时间戳；加密字段沿用现有安全契约，不输出或保存密码、Token、密钥。

必须满足：

1. 从受控创建输入、返回值、创建事务中的已知结果形成预期事实；清理阶段不得读取当前值反过来补成“预期”。
2. 已登记 ID 不再跳过必要字段/关系核验；删除前在同一事务内锁定、比对并完成引用闭包。
3. 合法角色、状态、正文等变化，只能在对应受控写入成功后显式更新允许变化的预期字段；写入失败保持旧预期，失败或结果未知时停止后续清理并保留诊断。
4. 不得提供 `skipFingerprint`、`trustOwnedId` 或“事实缺失就只按 ID 删除”的兼容兜底。
5. 创建成功而登记失败时须使测试失败，并保留可诊断的精确创建结果；不能继续运行或静默遗失该资源。
6. 覆盖账号、型号等同族分支；残留接管仍保持自然键定位＋严格指纹，不以本轮登记规则放松历史残留核验。

修改后逐一核对 28 个直接规格及其 fixture 辅助函数。每个消费者记录“已调整／既有机制等价安全／未验证”，不能只处理编译报错的调用方。

### 3.2 R01：关联关系不是删除授权

修改 `collectSpecialOwnedGraph` 中两处自动 `addIds` 的语义：

- `base_third_party_auth WHERE account_id IN (...)` 返回的行，必须已由本轮登记或严格残留指纹纳入；否则首删前冲突。不能将查到的全部绑定自动加入计划。
- `engineer_response WHERE request_id IN (...)` 返回的行，同样必须有行级归属证据；即使参与人完全相同，也不能自动接管。
- 显式登记的绑定/回复仍需字段和父子关系核验，登记本身不豁免 R02。
- 用户资料等现有明确 1:1 从属关系沿其既有核验机制处理；不要把这一例外推广成“账号下所有记录都可删除”。

调用方在真正创建绑定/回复成功后立即登记；若业务接口只返回有限字段，可在受控创建阶段定位并验证这次操作产生的精确记录，不得在 cleanup 中批量发现后登记，也不得把遇到的既有绑定直接标成本轮创建。

调整现有 `R02-C01`：正常成功测试先显式登记绑定，再断言删除；另设未登记绑定的拒绝测试，不得继续让“没登记但被删”成为预期成功。

### 3.3 R03：特殊状态造数原子提交，等待并行任务结束

目标：`backend/test/01-auth/auth.e2e-spec.ts` 的 `seedSpecialStatusAccount` 及其并行调用。

1. 在同一个 `dataSource.transaction` 的 manager 中取得仓储，完成占位账号 INSERT、密码 hash UPDATE、userinfo INSERT；不得混用事务外仓储。
2. 保留该 fixture 原本需要的特殊状态组合，不修改正式业务 Usecase 的状态一致性限制来让测试通过。
3. 事务成功返回后，立即登记真实 ID 和预期事实；登记前不执行其他异步操作。事务回滚不登记为“已提交资源”。提交结果未知时保留精确诊断，不能猜测后扩大删除。
4. 特殊账号可顺序创建，或等待 `Promise.allSettled` 后汇总错误；不能首错返回时让兄弟写入继续与 teardown 竞争。已经提交的成功批次必须有台账。
5. 任一造数失败仍需经原收尾链回收成功资源、关闭连接；原失败、清理失败、关闭失败分别保留。

优先复用适用的测试辅助函数；确需提取特殊 fixture 工具时，实际规格与回归必须调用同一实现，不复制一份“测试专用正确算法”。

### 3.4 R04：只有清理提交成功才能重置台账

目标：`backend/test/02-register/register.e2e-spec.ts` 的 beforeEach/afterEach/afterAll。

- 删除 beforeEach 的无条件 `ownership = createOwnedResourceLedger()`。
- 设置一个明确的成功清理后重置位置；cleanup 抛错、事务回滚、结果未知或诊断失败时保留原批次与失败状态。
- 推荐失败关闭：前次清理未完成时，在下一次造数前拒绝继续；afterAll 仍持有失败批次并尝试原安全清理或输出准确残留。若选择先恢复再继续，必须证明旧批次已清理提交，且原清理失败仍使 runner 非 0。
- 不能用下一轮新台账覆盖旧台账，也不能用 `finally` 清空、只 warn 后继续或把错误转成成功。
- 关闭应用/恢复环境仍执行；关闭失败不能覆盖此前错误。其他同族重置路径同步核对，只修与当前共享契约相关的生命周期。
