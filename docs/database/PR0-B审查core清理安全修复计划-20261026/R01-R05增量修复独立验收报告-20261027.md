## 3. 发现的问题

### N05 [P1] 故障子规格在没有启动许可时自行开启物理删除

- **准确位置**：`backend/test/fixtures/cleanup-faults-child.e2e-spec.ts:105`—113，尤其 `:110`；beforeAll `:92`—93 只校验库并保存原值，没有要求物理许可。
- **最小触发**：在合法、可丢弃 E2E 库中，以未设置 `E2E_ALLOW_PHYSICAL_CLEANUP` 的进程运行该子规格。
- **当前／期望**：afterAll 无条件写入 `'1'`，然后调用保留台账清理。期望缺原始显式许可时始终拒绝删除；故障测试只能恢复执行者已提供的许可，不能自行创造许可。
- **实际证据**：本轮新建实例中撤去启动许可运行正式子规格，退出 1、4 项失败，输出存在“缺少显式清理许可”和 `F09_RESIDUE=0`；该时间窗临时 MySQL SQL 审计记录 **2 条物理 DELETE**（用户资料、账号）。审计只取数量，不导出原始内容。此前第一次临时命令因 PATH 含空格引用问题未启动测试，纠正引用后才取得上述结果。
- **依据**：原计划 I1、增量计划的环境/许可约束、C04 及故障注入不得绕开实际安全门禁的要求。
- **影响／级别**：测试代码绕过独立物理删除许可。它仍受 E2E 库和行级范围约束，**不声称可绕过生产库白名单**；但安全许可边界已实际失守，P1。
- **为何已有测试未发现**：父规格只在有许可启动时验证“撤销后恢复”，没有验证执行者从未给许可的启动场景；runner 非 0 并未阻止 afterAll 自行授权删除。
- **最小修复**：beforeAll 在造数前独立校验原始许可；afterAll 仅恢复捕获到且已验证的原值，不硬编码授予 `'1'`。缺许可分支保留拒绝及诊断，不通过另一个入口删掉数据。
- **必须回归**：无许可/值为 0/原值为 1 三种启动；前两种无造数及 DELETE，后一种可在受控撤销后恢复，完成原 F09 验证。子进程错误和关闭仍可见。
- **归属**：当前 PR，本轮新增永久故障夹具直接引入。

### N01 [P2] R02 未覆盖计划要求的 user_info 预期字段

- **位置**：`backend/test/utils/e2e-scoped-cleanup.ts:72`—78、`:1200`—1222。
- **触发**：登记正常账号与资料后，未声明变更却修改 user_info 的 nickname/email/user_state；账号自身 loginName/email/status/identity 和角色不变。
- **当前／期望**：查询已读取昵称、资料邮箱、user_state，但 owned 事实没有对应字段、比对只检查账号与 access_group；资料和账号仍被删。计划 §3.1 第 46 行明确包含昵称等已用于归属判断的资料预期字段；不能只覆盖角色后称资料事实已核对。
- **证据**：真实临时 MySQL 修改上述资料字段后，当前入口 resolve；账号及用户资料均从 1 变 0。账号 loginName 漂移的对照则正确拒绝、账号保留，说明反例没有跳过整个预检。
- **影响**：当前明确约定的资料字段漂移保护未完成，P2；该反例不等同于已经证明跨组织/生产误删。
- **漏检原因**：F04 只测账号/型号已建模字段；类型本身省略资料字段，全部现有事实比较通过也不能发现省略的检查。
- **最小修复**：加入计划已明确的必要 user_info 事实与同事务比对，创建时登记，合法资料变更成功后显式更新；不扩成全列快照，不强制比较自动时间列或泄露加密明文。
- **回归**：昵称/资料邮箱等逐项单字段漂移拒绝、DELETE=0；合法资料变更更新预期后可回收，现有资料编辑规格继续通过。
- **归属**：当前 R02/T1 尚未完成部分。

### N02 [P2] 事实按引用保存，外部修改可静默改写“预期”

- **位置**：`backend/test/utils/e2e-scoped-cleanup.ts:340`；更新 `:362`；合并 `:1120`—1124 同族共享引用。
- **触发**：使用普通可变对象登记事实后，修改原对象的 loginName 或嵌套角色数组/payload，未调用 `updateOwnedExpectation`。
- **当前／期望**：Map 直接保存对象引用，浅展开更新仍共享嵌套值；台账预期随输入变化。期望登记/更新后形成与调用方输入隔离的事实快照，仅受控更新入口能改变下一次核验预期。
- **证据**：实际 helper＋真实 MySQL：原预期 `r27_alias`，直接修改原事实对象为 `r27_alias_unrecorded` 并改变数据库同字段；未调用预期更新，台账已经显示新名称，清理 resolve、账号变 0。不是用类型强转直接篡改台账 Map，而是合法传入对象的别名仍然可写。
- **依据／影响**：增量计划 §3.1 的受控变化规则、F05；事实不再是登记时的稳定依据，R02 可被意外输入复用绕过，P2。
- **漏检原因**：现有 F04/F05 使用新值或显式更新，未在登记后修改原输入，也未验证数组/payload 的深层隔离。
- **最小修复**：登记、显式更新及跨台账合并时隔离必要 JSON/数组/对象值，保持现有类型与空值语义；不增加业务框架。`readonly` 编译标注不能替代运行时隔离。
- **回归**：修改登记输入、patch 嵌套对象、被合并源输入均不隐式改变目标预期；真实漂移仍首删前拒绝；显式合法更新后正常清理。
- **归属**：当前新预期事实实现直接引入，属于 R02。

### N03 [P2] DataSource 未初始化时仍将未清理台账判作成功

- **位置**：`backend/test/utils/owned-ledger-lifecycle.ts:66`—70；afterAll `:99` 起同类不可用分支应同时检查。
- **触发**：已有本轮账号及台账，DataSource 关闭或不可用，随后执行 afterTestCleanup。
- **当前／期望**：`!isInitialized` 分支调用 succeed，清空台账/失败状态且 resolve；数据库中原行仍在。期望区分“确实空台账”和“有资源但无法确认清理”，后者保留状态、失败关闭并提供残留诊断。
- **证据**：创建真实账号，初始化并关闭用于清理的独立 DataSource；调用实际生命周期工具，`resetCount=1`、`ledgerIds=[]`、`cleanupFailure=null`，库中账号仍为 1。属于该公共入口的明确不可用分支，不声称正常 register 已会随机断连。
- **依据／影响**：R04、原 I4、增量计划 §3.4 明确失败/未知不能清台账；会丢失精确残留线索，P2。
- **漏检原因**：F09 注入的是已初始化连接下许可拒绝，始终进入 try/catch，不覆盖提前 succeed 的分支。
- **最小修复**：仅在空台账且无未决失败时允许无连接空操作；有资源/未决状态时保留并抛出可诊断错误。afterAll 不可用时也不得静默声称回收完成，仍执行应用关闭。
- **回归**：undefined/未初始化/已关闭连接＋空/非空台账组合，失败后下一用例不继续造数；明确成功清理才重置。
- **归属**：当前新增公共生命周期工具，R04 旁路未关闭。

### N04 [P2] C04 预期目标与实际连接一致性仍未校验，F11 两分支重复同一条件

- **位置**：`backend/test/utils/e2e-db-guard.ts:63`—69；当前 cleanup 入口调用该守卫；`e2e-scoped-cleanup-ownership.e2e-spec.ts:1947`—1969。
- **触发**：DataSource 配置目标 A，底层实际会话进入 B；A/B 都在明确允许的 E2E 名单中。
- **当前／期望**：守卫只验证 `SELECT DATABASE()` 在白名单，不比较配置预期与当前实际；F11(b)/(c) 都只是换一个不包含当前库的白名单。期望独立判断预期目标是否合法、实际库是否合法且与本次预期一致。
- **实际证据**：在临时实例新建空库 `lithography_expected_e2e`；以它初始化 connectionLimit=1 的真实 DataSource，再真实执行 `USE lithography_e2e`。两库列入白名单；打印预期 A、实际 B，清理仍 resolve、B 内本轮合成账号变 0。没有伪造 SELECT DATABASE 返回值。另一个 Proxy 反例只作补充，不能替代这条真实连接证据。
- **依据／影响**：原 I1/C04、增量计划 F11 明确要求明确预期来源并独立测试；当前允许库之间的目标偏差未受保护，P2，不声称未许可生产库可以通过。
- **漏检原因**：F11(b)/(c) 输入变化和失败消息实为同一个白名单拒绝命题；没有制造真实“配置目标与会话不同”。
- **最小修复**：从调用契约/已配置 DataSource 获取明确预期目标，在现有测试守卫内核对预期、白名单和实际一致性；按清理事务所用连接验证必要会话事实，不能仅放宽名单或向业务配置加入无关机制。

- **归属**：当前计划已要求补齐的 C04，本轮仍失败；不是新扩展的业务需求。
