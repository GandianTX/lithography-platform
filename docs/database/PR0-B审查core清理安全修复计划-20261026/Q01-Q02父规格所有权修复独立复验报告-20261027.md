## 4. L01 [P2] 辅助库与交接台账没有接入真实最终收尾，异常后资源成为不可达残留

### 4.1 准确位置与两种表现

**J 外层驱动**：`backend/test/utils/e2e-probe-lifecycle-outer.e2e-spec.ts:122`—139 的 `createRawForeignFixture`/`dropRawFixture`；第 263—280 行 afterAll 只回收 `outerLedger`（主探针库）。第 421、706 行创建辅助库，正常断言后第 435、719 行才删除。J03/J04/J05/J06 的辅助 ledger 也只保存在用例局部变量，未进入 afterAll 可访问的持久收尾集合。

**H06**：`backend/test/utils/e2e-probe-lifecycle.e2e-spec.ts:440`—458 的 `handoffLedger` 是用例局部变量；第 269—283 行 afterAll 只看 `parentLedger`。父侧回收失败后，helper 内部虽然没有 consume 这份交接台账，但用例抛错后真实 FINAL 无法再访问它。

### 4.2 触发、行为及影响

1. **最小触发 A**：J04/J08 中辅助库 CREATE 成功，后续建表/插行或断言失败，代码未走到正常末尾的 `dropRawFixture`。真实 afterAll 主台账为空，输出 `OUTER_FINAL=skipped-not-owned`，辅助库遗留。
2. **最小触发 B**：H06 凭据已核验、交接台账已登记，父侧 DROP 失败。用例抛错，FINAL 输出 `PARENT_CLEANUP_FINAL=skipped-not-owned`，未决子运行台账没有交给最终收尾。
3. **期望**：成功 CREATE 后立即在驱动器自己的、跨用例异常仍可访问的收尾状态中登记；子交接台账登记后也要进入真实 afterAll 可访问的状态。成功清理才消费。已确认可安全回收的资源精确收尾；结果未知或连接不可用时保留归属、目标、运行及失败诊断，非零退出，不为凑零残留盲删。
4. **影响**：这两条路径没有复现原 Q01 的非本轮数据误删；它们遗留本轮已知资源，后续安全门禁会碰撞拒绝，需人工处理才能重跑。原创建事实没有统一留给最终收尾，违反本轮异常路径交付要求。

### 4.4 任务依据、漏检原因及最小修复

- **依据**：本计划第 4.2 节要求 CREATE 成功立即保存归属、失败不清账、最终收尾保留未决状态；第 5 节要求 H06 交接记录在回收失败后保留；J03/J06/J08 和 K4/K5/K7 要求新驱动自身也覆盖部分创建/收尾失败。这些是本轮已有标准，不是新增业务要求。
- **为什么现有测试没发现**：J03/J06 把注入错误 catch 在用例体内，随后仍正常走到显式清理，所以 helper 的“记录仍在”断言可通过，却没有验证用例提前终止时真实 afterAll 是否拿得到它。J08 的 finally 只覆盖专门构造的局部示范分支，没有覆盖 `createRawForeignFixture` 的实际失败生命周期。正常两轮的零残留也覆盖不到此分支。
- **最小修复方向**：让 H 的有效子交接台账、J 的各辅助台账及“相对 SUT 异主”的夹具拥有者记录进入规格生命周期可访问的窄收尾集合，或等价的有归属作用域封装。原始夹具也要在 CREATE 明确成功后立即登记给**驱动器自己的账本**，不能登记进用来验证无归属的 SUT 空台账。afterEach/afterAll 按依赖独立尝试回收已知本轮资源，失败保留记录并汇总错误，继续恢复环境/关闭应用。
- 不要求自动无限重试或删除未知资源；不允许退回固定名清场。正常路径成功清理后消费记录，最终收尾不重复授权。无需生产表或通用资源管理框架。
- **必须补回归**：真实 helper CREATE 后失败→真实 afterAll；实际断言提前失败→收尾；H06 有效交接后父回收失败→最终收尾可访问未决账本；多资源中一个回收失败时其他资源仍处理。断言已知资源回收或精确未决状态、主错误与关闭结果，负对照移除最终可达登记后应失败。
- **归属**：当前修复包一个 P2 阻塞，两个表现属于同一“所有权状态未跨异常生命周期保存”的根因。不是两条独立新业务缺陷。
