## 3. 发现的问题

### R01 [P1] 自动扩图把未登记的绑定和回复变成可删除资源

- **位置**：`backend/test/utils/e2e-scoped-cleanup.ts:939`—948；同文件 `:1030`—1063，尤其 `addIds(plan.engineerResponseIds, ...)`。
- **最小触发**：只登记本轮账号；在该账号下另建一条不属于该台账、未给残留指纹的第三方绑定。第二条路径是已登记工单/客户/工程师下存在一条未登记、未给内容指纹的回复。
- **当前／期望**：清理按账号查询全部绑定、按申请查询全部回复，并把命中 ID 加进删除计划；参与人相同就能删除。期望关联关系仅用于发现引用；未经本轮创建登记或严格残留核验的记录应在首删前造成冲突，不应反过来成为本轮资源。
- **实际证据**：真实 MySQL 8.0.46 上分别调用当前入口；绑定台账 `[]`、回复台账 `[]`，两次均未抛错，对应非台账行均从 1 变 0，根账号/工单也被删除。使用 `GITHUB` 绑定，正式 Migration 明确支持该 provider。
- **依据**：修复计划 I2/I3、C03；B 要求不能扩大删除范围或只按关联账号判断归属。第三方表实际唯一约束为 `(account_id, provider)`，注释“账号的 1:1 从属行”也不能证明所有 provider 绑定属于本轮。
- **影响／级别**：在允许的测试库内仍可稳定误删非本轮关联记录；事务只能原子提交错误删除范围，不能保护这些记录。属于 P1 数据安全边界失守。
- **测试为何漏掉**：新增 `e2e-scoped-cleanup.e2e-spec.ts:737` 的 R02-C01 没登记绑定 401，却预期它被删除，把自动接管作为成功行为；外部回复反例只覆盖外部参与人，没有覆盖“参与人相同但记录本身不归本轮”。
- **最小修复**：创建绑定/回复后登记实际 ID 和必要预期事实；移除“查到关联行就 addIds”的权限提升。对未被明确纳入的关联行预检拒绝；需要处理历史残留时只能通过相应指纹入口。
- **必须回归**：两类未登记关联记录各一条真实库反例；正常已登记及严格指纹接管；前序目标零删除；更新 R02-C01；所有直接消费者及完整 core。
- **归属**：当前 PR，由本轮新增四类资源和扩图行为直接引入，不能列为以后优化。

### R02 [P2] 已登记 ID 被用作跳过关键字段核验的豁免

- **位置**：`backend/test/utils/e2e-scoped-cleanup.ts:509`—511；型号同族路径 `:584`—587；台账类型 `:64` 起仅保存各类 ID。
- **最小触发**：账号创建登记后，未通过受控测试更新预期，却改变其 `login_name`；同时向清理器传入原始预期指纹。
- **当前／期望**：只因 ID 已在 owned 中就从核验候选中过滤，后续锁定关系没有补上账号关键事实比对；账号照常删除。计划要求登记证据加预期字段，合法角色/状态变化应显式更新预期，而不是豁免全部已登记行。
- **实际证据**：真实库创建账号及 user_info，登记真实 ID；改名为 `reassigned-unexpected-name`；传原 login/email/status/identity/nickname/role 指纹，清理不抛错，账号由 1 变 0。该反例验证的是计划中的防漂移要求，**不声称出现真实账号 ID 重用**。
- **依据**：计划 I2 两条明文规定及 C02；工作流 3.2 的四层证明和受控预期变化规则。
- **影响／级别**：当前明确要求的字段保护未实现；不能把“残留严格”表述成“所有目标字段漂移拒绝”。本轮完成定义缺失，P2。
- **测试为何漏掉**：字段漂移用例主要只传 residue；正常规格会合法修改角色，修复时选择整体跳过 owned 指纹，未增加“允许已记录变化、拒绝未记录变化”的对照。
- **最小修复**：以最小类型记录本轮资源的必要预期事实；对合法测试写操作明确更新预期。不要在清理时读取当前字段回填预期，也不要把所有可变状态都锁成创建初值。
- **必须回归**：owned 字段漂移首删前拒绝；合法角色/状态变更更新预期后可清理；型号同族路径；残留核验继续严格。
- **归属**：当前 PR；属于本轮为角色变更新增的豁免及计划执行偏差。

### R03 [P2] 特殊状态账号造数不是原子操作，登记晚于多步写入

- **位置**：`backend/test/01-auth/auth.e2e-spec.ts:219`—247；并行创建 `:195`。
- **最小触发**：占位账号 INSERT 和密码 UPDATE 已成功，user_info.save 抛错；或者更早的密码更新失败。
- **当前／期望**：登记在全部写完后的第 247 行；前序写入不在同一事务中，失败留下已提交账号、台账为空。残留路径要求完整用户资料指纹，不能安全补认该半账号。期望要么整段造数事务失败全部回滚，要么首次创建返回后即时登记并保证部分状态可安全回收。
- **实际证据**：从当前源码 AST 提取真实 `seedSpecialStatusAccount` 函数体；仓储适配器执行真实 MySQL INSERT/UPDATE，user_info 写入点注入错误，返回 `registeredIds=[]`，库中账号仍存在。密码 hash 在此适配器中用合成值替代；该证据不冒称完整 Nest/Jest 故障链已执行。
- **依据**：计划 I2 的即时登记、C07 部分造数；公共 `createTestAccount` 已有原子 fallback，但这个新迁移的特殊账号分支绕开了它。
