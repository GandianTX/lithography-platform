## 3. 发现的问题

### M01 [P1] G04 以固定库名删除非本轮探针库，缺少创建所有权保护

- **位置**：`backend/test/utils/e2e-db-target-consistency.e2e-spec.ts:29`、`:46`—50、`:140`—145。
- **最小触发**：允许的隔离实例上，`lithography_e2e_probe` 已存在，包含其他测试/上一轮/其他使用者的数据；执行当前标准 G04 规格。
- **当前行为**：beforeAll 的 `DROP DATABASE IF EXISTS` 直接销毁既有库，随后重建；afterAll 再无条件 DROP，同样没有“本轮创建成功”记录。固定名字不是归属证据；初始化失败时也没有可靠的创建所有权条件控制收尾删除。
- **期望**：只销毁本轮明确创建且拥有的临时库。可采用本轮唯一名称；若用固定名称，发现已存在应在破坏前拒绝，不能先删以保证测试可跑。只有本轮 CREATE 确认成功后才允许对应销毁，未知结果保留诊断。
- **实测**：本轮独占实例预置 `lithography_e2e_probe.keep_nonfixture`，1 行 `not-owned-by-G04-this-run`。调用正式 `test:e2e:file` 后测试 **2 passed、exit 0**，但探针库从存在变为不存在，实例 `Com_drop_db` 从 **0 增至 2**。全为合成数据，没有伤害保留库。
- **依据/影响**：原 I2/I3、增量计划的归属及非夹具保留原则；本轮新测试直接引入稳定可复现的非本轮数据破坏，P1。独占可丢弃实例是安全复现条件，不等于普通 core 夹具可不检查归属。
- **为何现有测试没发现**：只在新克隆后的探针行上断言保留，未在规格开始前预放异主同名库；只比较 Com_delete 不会发现 DROP DATABASE。守卫测试绿色不能证明准备/收尾安全。
- **最小修复**：去掉“先 DROP 再 CREATE”的覆盖行为；明确本轮库名和创建所有权；发生碰撞拒绝且原库不变；afterAll 只处理确属本轮的库，不能因前面初始化失败误删既有库。
- **必须回归**：已存在同名非夹具库完整保留；本轮新建库正常回收；CREATE 前/后失败与结果未知；重复运行/名称碰撞；监测 DDL 副作用而非只数 DELETE。
- **归属**：当前新增 G04 永久反例，当前 PR 合入前必须修，不是范围外数据库运维任务。

### M02 [P1] G04 启动自行设置物理许可，未授权时仍执行破坏性 DDL

- **位置**：同文件 `:119`—137，尤其 `:131`—132；it 内 `:159`—160、`:202`—203 亦硬编码许可；afterAll 原始配置恢复缺失。
- **最小触发**：以未设置 `E2E_ALLOW_PHYSICAL_CLEANUP`（或静态同族值 0）的进程运行 G04，当前主库在名单内。
- **当前/期望**：beforeAll 只验证主库目标，随后自行把许可写为 `'1'` 并把探针库加入名单，DDL 没有启动许可拒绝。期望先校验执行者提供的原始许可；DDL 不因未使用 DELETE 语句而豁免。测试可以受控撤销/恢复已验证许可，不能自行授予。
- **实测**：M01 同一次正式执行明确从启动环境撤去该许可，自定义 dotenv 也没有该键。仍然 **2 passed、exit 0、两条 DROP**。值 0 的结果本轮未单独执行，不冒称两种都已实测。
- **依据/影响**：原 I1、N05、计划 U1/§3.1 的同族授权恢复要求；原故障子规格已修复，但新增 G04 再次绕过启动许可，P1。当前证据限于 E2E 实例，不声称标准 runner 可访问未允许生产库。
- **为何测试漏掉**：G04 的拒绝断言发生在 beforeAll DDL 之后；它们验证正式 helper 的库一致性，不验证测试准备本身的授权。前面的自动授权也让 it 中捕获的“原值”已经变成 1。
- **最小修复**：在任何探针库创建/删除和造数前，独立捕获并校验原始许可；缺失/0 时拒绝且 afterAll 不补授权。临时名单调整只针对已授权、已证明本轮创建的探针范围，捕获原配置并可靠恢复，不以扩大名单代替归属和一致性核验。
- **必须回归**：未设置、0、1 三种启动；前两种 CREATE/DROP/INSERT/DELETE 均为 0，资源仍关闭；原值 1 时原 G04/G04b 拒绝行为成立。库名单与许可最终恢复正确。
- **归属**：当前 N05 同族约束未收口，直接涉及新增测试，不应仅以原 child 的 G01/G02 通过宣布整体无风险。

### M03 [P2] G04 收尾异常会跳过后续关闭

- **位置**：同文件 `:140`—149。
- **最小触发**：shiftedDataSource.destroy 或探针库 DROP 抛错，例如缺少 DROP 权限、连接中断。
- **当前/期望**：顺序 await 没有 finally/统一收尾，前一步拒绝就不执行后面的 app.close。期望每个释放动作都被尝试，保留最初错误，后续关闭/恢复错误分别可见；数据库操作失败不能阻止应用关闭。
- **证据**：从候选 AST 提取实际 afterAll 回调，在精确 DROP 点注入 `injected-drop-failure`。调用序为 `[shifted.destroy, DROP rejected]`，`appClosed=false`。这是实际函数体的故障替身，不冒称真实 MySQL 拒权或已观测整个 Jest 永久挂起。
- **依据/影响**：原 I5、N03 收尾约束及计划要求“关闭不因清理失败跳过”；新增直接消费者未使用已有安全收尾器，可能留下连接/应用资源，P2。
- **为何测试漏掉**：G04/G04b 均走正常销毁；共享 runE2eTeardown 的测试不覆盖没有调用它的这个 afterAll。
- **最小修复**：将本轮拥有的探针清理、环境恢复、shifted 连接和 app 关闭接入可靠的逐步收尾；用已有 runE2eTeardown 或等价窄实现，任一步失败仍执行其余关闭，保留主因，不吞错。
- **必须回归**：destroy、DROP、环境恢复、app.close 的单点/组合失败；每个关闭被尝试且无重复；旧错误保留，规格非 0；未创建/无所有权时不执行 DROP。
- **归属**：当前新探针测试生命周期，不要求重构业务服务或无关消费者。
