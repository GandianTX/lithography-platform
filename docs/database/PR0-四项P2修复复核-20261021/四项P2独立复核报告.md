### V01：原反例已被切断

- 回落账号插入、密码回写、userinfo写入在同一个真实事务内，不再留下不可按完整指纹回收的半账号。
- 新增可选 ownership 参数覆盖真实 createTestAccount；事务或 Usecase 成功后登记，不再只由外层 seedTestAccounts 完整返回后登记。
- 一项失败而另一项延迟成功时，allSettled 确保后者已经完成并登记后才抛错，不留下 afterAll/close 之后的在途造数。
- `test/utils/test-accounts-atomicity.e2e-spec.ts` 虽以 e2e-spec 命名，其5项实际为纯内存事务模型；本报告不将它们冒充 MySQL 回滚证明。
- 真正的 MySQL 失败回滚由 `e2e-scoped-cleanup-ownership.e2e-spec.ts` C10 验证：定向注入 user_info 保存失败后，账号/userinfo均不存在；同邮箱可立即创建完整账号并精确回收。本轮已执行两次。

### V02：原来漏查的引用方向已覆盖

独立调用真实 runGuardedSpecCleanup，提供 O1/A 本轮关系及 O2/A 外部关系。当前 SQL 同时包含两个候选方向，外部关系在第一条删除前暴露：

```json
{"bothDirections":true,"precheckRejected":true,"deleteCount":0}
```

这不是靠数据库 FK 到 DELETE account 才拒绝。实库 C05B 使用真实计数代理断言零删除，并验证本轮组织/账号、内外两条成员关系逐字段不变，两次通过。

retainedAccounts 仅用于核验、不删除其账号，因此不加入 owned 账号方向；本次修改保留这一直接消费者边界，未顺带回收其其他组织关系。

### V03：角色和退出事实不再被 Seed 还原

当前成员 SELECT 已携带 member_role/status/left_at；任意与预期指纹不同均抛冲突，SAME 分支不写库。独立调用真实 upsertSeedMembership 的结果：

17项 Seed 单测还覆盖双键碰撞、基础组织实际ID、DISABLED组织拒绝、正常新建、指纹一致 no-op 等。

本轮没有运行完整开发 Seed、改动现有成员再恢复，也没有再次验证整份 Seed 的真实库双跑；实施回执中的该部分仍是实施者记录。对于本次 V03 的最小修复，真实函数路径、零 DML 断言及脚本接线已核对，原覆写路径不存在，无需为了关闭它在现有库改写账号权限。

### V04：原丢通知窗口已消除

- waiter 在竞争请求启动前登记，arrived Promise 保存此轮通知，即使先 signal 后 wait 也能完成。
- 历史轮没有活动 waiter 的信号不保留到下一轮；超时移除 waiter。
- W01 刻意延迟持锁方120ms放大“通知先到”时序，仍通过。
- W01～W07 在 finally 释放持锁连接后等待竞争请求收敛；没有继续采用“启动请求→等待其他SQL→才注册通知”的旧顺序。
