## 二、发现与修复清单

### P1-1 案例类型保留守卫大小写敏感，存在绕过缝隙（已修复）

- **位置**：`reference-document-fields.normalize.ts`（normalizeDocumentType 仅 trim）；`create-reference-document.usecase.ts`（伪造守卫）；`update-reference-document.usecase.ts`（普通→案例改造守卫、案例正文/类型保护）；根因同时影响 S6 更正门禁的判定口径统一。
- **根因**：数据库列排序规则为 `utf8mb4_0900_ai_ci`（大小写不敏感，且 `reference_document` 无 CHECK 兜底），应用层却用 `=== 'FAULT_CASE'` 大小写敏感比较；投稿域已按 `toUpperCase` 归一比对，两域口径不一致。`documentType: 'fault_case'` 变体可绕过「管理员直建不可伪造 FAULT_CASE / 普通资料不可改造为案例」守卫，且变体资料不受通用编辑保护。
- **修复**：
  - 新增唯一判定函数 `isFaultCaseDocumentType`（trim + toUpperCase 比较，注释标明与列排序规则及投稿域口径对齐）；
  - create 守卫、update 改造守卫、update 案例保护、S6 更正门禁四处统一改用该函数（判定单源）。
- **补测（穷举变体）**：
  - 单测：create 伪造拒绝循环 `['FAULT_CASE','fault_case','Fault_Case']`；update 改造拒绝同循环；新增「大小写变体目标同样受保护」用例；S6 门禁新增（'fault_case' 变体按不敏感判定等价案例，明细缺失同样失败关闭）；
  - 端点级（12 spec V-S6-3）：新增 `documentType: 'fault_case'` 直建拒绝断言（`REFERENCE_DOCUMENT_INVALID_PARAMS`，库内 0 条），实测通过。

### P2-1 读取链路「本组织管理员」判定未用精确 activeRole（已修复）

- **位置**：`get-content-submission-revision.usecase.ts`、`download-content-submission-attachment.usecase.ts`（`roles.includes(SUPER_ADMIN)`）。
- **根因**：模块既定纪律为「roles 含角色 + activeRole 精确匹配」双重判定（投稿人/审核链路均如此，失败关闭）；两处读取链路仅用 roles，管理员兼工程师账号以 ENGINEER 身份操作时可读取同组织他人投稿/附件，与审核链路口径不一致。
- **修复**：新增 `isActiveSuperAdmin`（roles 含 SUPER_ADMIN 且 activeRole 精确 SUPER_ADMIN，与审核链路同口径，注释说明失败关闭理由）；两处替换；两文件 docblock 同步注明精确口径。
- **补测**：submit-return spec 与 attachments spec 各新增「roles 含 SUPER_ADMIN 但 activeRole 为 ENGINEER → 他人投稿/附件 NOT_FOUND 且不触读（不触盘）」用例。

### P2-2 `DomainErrorCode` 联合类型遗漏 `ContentSubmissionErrorCode`（已修复）

- 已定义 `ContentSubmissionErrorCode` 但未纳入 `DomainErrorCode` 联合（无运行时影响，类型完备性）；已补入。同批核对：其余各域错误码类型均在联合中。
