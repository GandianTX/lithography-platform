## 2. 缺陷是怎样产生的

位置：backend/test/utils/test-accounts.ts:145—148。

函数依次对以下三表创建DELETE QueryBuilder并执行：

1. OrganizationMembershipEntity；
2. UserInfoEntity；
3. AccountEntity。

没有WHERE，没有接收本轮真实创建ID或指纹，没有核验实际数据库/显式清理许可，没有DataSource.transaction，也没有删除前引用闭包检查。仅按“先子后父”的顺序删除，不能代替归属和原子性。

本地TypeORM DeleteQueryBuilder实现仅在显式启用useTransaction等条件时才主动包事务；当前调用未启用。相关spec也直接传DataSource，没有把这三步置于同一事务内。因此在普通自动提交连接中，前两条可以已提交，第三条再失败，不能自动回滚前两条。

最小触发条件：库里存在本轮夹具之外的账号/资料/成员；既有参考资料引用某个旧账号，账号外键为ON DELETE RESTRICT。

结果链：

- 整表删成员：旧成员关系也可能被删；
- 整表删用户资料：旧资料已删；
- 整表删账号：遇旧参考资料的创建人引用，外键1451拒绝；
- 前两步没有同一事务可回滚，账号和本轮夹具残留，身份资料链被破坏。

外键保护了仍被引用的账号，**没有**保护此前已经删除的用户资料或成员。若没有任何外部引用阻止账号删除，整表清理甚至可能返回成功，同时把非夹具账号一起删掉；因此“没有报错”也不是安全证据。

## 6. 修复及工作流应如何收口

本轮只提出方向，不执行修复：

1. 以共享helper及直接调用方为范围，取消无条件整表账号/成员/资料删除；记录本轮真实创建ID，核对关键字段/归属及相关引用。
2. 清理入口在第一条DELETE前独立核对显式许可、预期/实际测试库和全部目标；目标或外部引用冲突时零删除。
3. 同一事务内按依赖顺序精确删除；主动注入后续删除失败，证明前面删除回滚。仅新增WHERE而没有归属证明，或仅包事务但仍整表删，都不充分。
4. 统一beforeAll/beforeEach/afterAll的清理与错误传播；保留业务主因、清理错误和精确残留，资源仍应关闭。auth-identity有两个afterAll，不应重复执行不安全清理或因先抛错跳过关闭。
5. 旧库保留/恢复验证与完整core使用不同的明确环境。完整core只对可丢弃E2E环境运行；非夹具合成哨兵仍需用于安全反例。环境拆分不替代修复。
6. 修复后在新的隔离实例中执行B要求的非夹具保留、所有权/引用拒绝、部分失败回滚、正常零残留及完整core/样例验证；新候选必要CI另回读。不能对B保留故障现场反复重跑。

工作流宜补强的是可核对的执行产物，而非重复原则：

- 每个被改清理helper都列“导出函数—全部直接调用方—所在runner组—调用生命周期—安全入口—证据”的表，任何调用方不得仅因文件未改而消失；
- 将“历史/已拆分”与“当前交付会实际调用”分别核验；必经破坏路径不得只凭历史标签放行；
- 存在非夹具合成账号、userinfo、membership及保护性资料引用的哨兵，应贯穿目标执行链或明确的每个危险入口，前后逐字段比较；
- 明确Seed安全、迁移保留、helper安全、完整runner安全是不同证明对象；
- “零残留”必须同时有“非本轮数据未变”，不能用整表为空作为安全证据；
- 测试环境分清空库/夹具库/含保留数据副本，以及普通清理与故障中断；缺少相应证据必须标未验证。
