# 部署与增量升级 SOP（当前 29 条迁移）

本 SOP 对应仓库当前迁移清单：**29 条迁移、33 张业务/基础表**（`migrations`、`typeorm_metadata` 单独计数）。
适用于两类场景：

1. **新环境初始化**：空库按正式入口一次执行到当前终态。
2. **既有库增量升级**：PR0 24 条迁移（或更早的 14 条干净前缀）升级到当前终态，只执行 pending 迁移。

前置阅读：`docs/database/增量升级操作说明-20261026.md`（14 → 24 的入口契约、退出码、失败恢复原则）。本文件不重复其条款，只补充当前数量、组织回填与未接入能力边界。

> 所有命令均在 `backend` 目录执行。入口全部是受版本控制的 `package.json` 脚本，不依赖任何未提交的临时脚本。

## 1. 不可违反的边界

- **既有库绝不清库**：`npm run migration:drill:empty-db` / `migration:drill:upgrade` 会先**删除目标库全部表**再重建，仅用于迁移链自证的隔离演练。对既有库使用它们等同于数据丢失。
- **不清除开发库迁移历史**：本机 `lithography_drill` 为 PR0 之前形态（15 表、0 条迁移记录），不得手工补写 `migrations`、不得用 drill 重建。它应走“纳管或重建”的独立方案，不在本 SOP 的升级范围内。
- **不伪造 pending**：不得删除 `migrations` 记录、不得手工 `DROP` 对象、不得调用 `down` 来制造干净状态。
- **不对部分失败自动回滚**：MySQL DDL 隐式提交，入口失败后只做只读诊断，恢复依赖升级前备份或维护者评审的前向修复。
- **秘密不进仓库/命令行/日志**：配置文件放仓库外并 `chmod 600`；命令输出只含脱敏的 `host:port/database`，不含密码。

## 2. 显式配置与目标核对

配置文件（示例放仓库外，权限 0600）：

```bash
# /path/to/.env.production  (chmod 600)
DB_HOST=...
DB_PORT=3306
DB_USER=...
DB_PASS=...
DB_NAME=<目标库>
DB_TIMEZONE=+08:00
```

规则：

- 必填 `DB_HOST`、`DB_PORT`、`DB_USER`、`DB_NAME`；`DB_PASS` 可选。
- 必须**不包含** `DB_SYNCHRONIZE=true`；入口自身强制 `synchronize=false`。
- `--config-file` 必须显式给出，缺失/为空/缺字段/端口非法/`DB_NAME` 与 `--database` 不一致都立即失败，**不会自动回落** `env/.env.development` 或其他文件。
- `migration:run` 额外要求 `--confirm-database` 与 `--database` 完全一致；入口还会用 `SELECT DATABASE()` 核对实际连接目标。

## 3. 新环境初始化

适用：空库（无表）。

```bash
# 1) 只读预检（此时历史为空，属于合法空前缀）
npm run migration:status -- --config-file /path/to/.env.production --database <目标库>

# 2) 执行全部迁移
npm run migration:run -- --config-file /path/to/.env.production --database <目标库> --confirm-database <目标库>

# 3) 终态只读核验
npm run migration:verify -- --config-file /path/to/.env.production --database <目标库>
```

预期结果：

- 首次 `run` 执行 **29 条**迁移，输出末行 `升级完成：历史 29 条，业务表 33 张，再次执行 0 条`。
- `verify` 输出 `业务表 33 张；历史校验与数据回填校验通过`。
- 再次 `run` 报告 `executed=[]` 并以 0 退出（幂等空操作）。

初始化后仍需按第 6 节建立组织与成员关系，否则业务侧无法按组织隔离派单。

**迁移链自证（仅隔离环境）**：如需在空库上额外验证“清空后全量重建”，在明确可丢弃的目标库执行：

```bash
MIGRATION_DRILL_DATABASE=<可丢弃库> MIGRATION_DRILL_ALLOW_NON_TEST_DB=true \
  npm run migration:drill:empty-db
```

该命令会清空目标库，执行 29 条迁移并断言表/列/索引/CHECK/外键/生成列契约，**不得对既有业务库执行**。

## 4. 既有库增量升级（PR0 24 → 29）

适用：已具备 PR0 24 条迁移历史的库（也兼容 14 条等受支持的干净前缀）。

### 4.1 升级前

1. **备份并验证可恢复**：对目标库做物理/逻辑备份，并在同版本 MySQL 副本上实际导入一次；只证明 dump 可解压不算通过。
2. **停写**：停止业务写入、后台任务与其他迁移进程；窗口内只允许本入口写目标库。
3. **核对目标**：确认配置文件 `DB_NAME`、`--database`、`--confirm-database` 三者一致，且实际连接 `SELECT DATABASE()` 相同。
4. **只读预检**：

```bash
npm run migration:status -- --config-file /path/to/.env.production --database <目标库>
```

预期：`历史 24 条，仓库 29 条，pending 5 条`，无 issues。

### 4.2 执行

```bash
npm run migration:run -- --config-file /path/to/.env.production --database <目标库> --confirm-database <目标库>
```

执行顺序（入口保证）：

1. 双确认与显式配置校验、实际连接目标核对；
2. 获取库级互斥锁 `GET_LOCK('lithography:migration:<库名>')` 并持有到结束，另一进程明确失败；
3. 与 status 相同的只读预检，任何 issue 在首条 DDL/DML 前拒绝；
4. 仅执行 pending 迁移（本轮为 5 条：`AlterOrganizationMembershipCustomerSingleActive`、`AlterRepairRequestOrganizationAndHandling`、`CreateMaintenanceReportAndContent`、`CreateMaintenanceReportAttachmentVersionReview`、`CreateLocalInstallationUploadBackup`）；
5. 升级后核验历史、表数量、列/索引/CHECK/外键/生成列、旧资料回填、组织归属完整性；
6. 再次确认 pending 为 0。

预期输出末行：`升级完成：历史 29 条，业务表 33 张，再次执行 0 条`。

### 4.3 后验与重复执行

```bash
npm run migration:verify -- --config-file /path/to/.env.production --database <目标库>
npm run migration:run    -- --config-file /path/to/.env.production --database <目标库> --confirm-database <目标库>
```

- `verify`：历史完整、结构齐备、回填正确、pending 为 0。
- 第二次 `run`：执行 0 条并以 0 退出，不视为异常。

### 4.4 旧数据与组织回填核对

- 旧参考资料：`owner_organization_id` 必须非 NULL 且指向存在的组织；`ingest_method` 非 NULL；存在旧资料时 `CLIENT_DEFAULT` 组织必须唯一。
- 旧维修申请：`owner_organization_id` **只按“客户账号存在唯一 ACTIVE、`member_role=CUSTOMER` 的成员关系”回填**；无有效成员关系保持 NULL，进入异常清单，**不按厂家、`company_name` 或登录名猜测**。
- 未变更的旧表数据必须逐字段保持不变；旧列的接单/撤回/创建事实不得改写。升级前后应以逐字段摘要（如按表 `MD5(GROUP_CONCAT(...))`）与文件清单比对，留存脱敏记录。

无归属旧工单的运行时规则（与列表/详情/接单一致）：

- 列表：仅 `MINE` 范围可见本人已接单的无归属记录；`AVAILABLE` / `ALL` 不因 NULL 而放开给全体工程师。
- 详情：无归属记录仅**客户本人**或**接单工程师本人**可读。
- 接单：无归属记录一律按 `NOT_FOUND` 拒绝，直到建立可信组织归属。
- 因此部署后应先完成组织与成员关系初始化（第 6 节），再开放派单。

### 4.5 组织归属缺失/冲突的只读排查

```sql
-- 无归属旧维修申请（异常清单）
SELECT id, customer_account_id, accepted_by_engineer_account_id, created_at
FROM repair_request
WHERE owner_organization_id IS NULL
ORDER BY id;

-- 客户存在多条 ACTIVE 成员关系（歧义，禁止猜测）
SELECT account_id, COUNT(*) AS active_count
FROM organization_membership
WHERE status = 'ACTIVE'
GROUP BY account_id
HAVING COUNT(*) > 1;

-- 客户无任何 ACTIVE CUSTOMER 成员关系
SELECT rr.id
FROM repair_request rr
LEFT JOIN organization_membership m
  ON m.account_id = rr.customer_account_id
 AND m.status = 'ACTIVE'
 AND m.member_role = 'CUSTOMER'
WHERE m.id IS NULL
ORDER BY rr.id;
```

以上结果只用于人工确认归属，不得用放宽权限的方式“消除”异常。

## 5. DDL 部分失败的诊断与恢复

入口失败后：立即停写、不重跑、不 `down`、不删记录、不 Seed。只读保存现场：

```sql
SHOW TABLES;
SELECT id, timestamp, name FROM migrations ORDER BY id;
-- 相关表的 information_schema：列 / 索引（含唯一性与列序）/ 外键 / CHECK
```

按实际状态决策：

| 恢复后状态                             | 正确流程                                                     |
| -------------------------------------- | ------------------------------------------------------------ |
| 完整恢复到旧 24 条（或受支持干净前缀） | 重新确认目标/停写/备份 → `status` → `run` → `verify`         |
| 已完整为当前 29 条终态                 | `status` → `verify`；需要时 `run` 应执行 0 条                |
| 部分 DDL 生效但无对应历史              | 停止；保留现场，走备份恢复或维护者评审的前向修复             |
| 历史完整且结构匹配、无残留对象         | 人工核对后继续执行 pending                                   |
| 连接中断、结果未知                     | 先重连只读核对历史与真实对象，再分类；不得推断“失败即未写入” |

`verify` 是终态检查：未升级的旧库 `verify` 非 0 属预期，不能当作 `run` 前的门禁。

## 6. 组织初始化与人员映射

1. 确保 `CLIENT_DEFAULT` 组织存在且唯一（旧资料回填依赖它）。
2. 为每个真实客户账号建立**唯一** ACTIVE、`member_role=CUSTOMER` 的成员关系；为工程师建立其所属组织的 ACTIVE 成员关系。
3. 管理员建号路径要求操作管理员自身具备有效组织归属（`resolveForAccount` 先于写入）；自助注册不自动建立成员关系。**当前版本尚未提供“管理员分配组织”的公开入口**，需按下述任一方式补齐：①在管理端补充组织分配能力后再开放自助注册客户的派单；②由运维按第 2 条直接在库内建立成员关系。未建立成员关系的客户，其工单无法派单，这是预期行为，不能通过放宽权限消除。
4. 无可靠映射来源的存量账号：保持无成员关系，列入异常清单人工确认；**禁止**按厂家、公司名或登录名自动关联。
5. 重复 ACTIVE 成员关系会触发数据库唯一约束（生成列 `active_account_id` / `active_org_account_id`），必须在写入前清理冲突，而不是依赖放宽权限。

## 7. 未接入能力的实际可用范围

以下能力本轮**数据契约完成、真实链路未验证**，部署后不得宣称已上线：

| 能力                         | 当前状态                                        | 部署后行为                                                                 |
| ---------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------- |
| AI 分析结果关联              | 生产装配 `UnavailableAnalysisOutputReader`      | 明确不可用，不自动降级为模拟成功；提交总结仍可走未使用 AI 的路径           |
| 真实附件上传                 | 仅客户端元数据格式/限额归一化，无服务端存储回读 | 不得以客户端自报大小/校验值/存储引用作为完整性依据；真实上传验收未完成     |
| 云端上传/备份接收端          | 仅本地任务与备份记录（状态机、幂等、回执字段）  | 数据库任务记为 PENDING/FAILED 等中间态，不等于真实云上传或真实备份成功     |
| 本地上传/备份内部用例        | 未暴露 GraphQL 公开接口                         | 仅内部装配；不为测试新增无鉴权入口                                         |
| 恢复场景（旧任务、安装身份） | 未实现恢复编排                                  | 恢复后须人工核对 `local_installation` 单行身份与遗留任务，不得假设自动接管 |
