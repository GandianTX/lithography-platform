### V01 [P2] 账号造数半途失败时，已落库账号尚未登记，后续无法正常回收

- 位置：`backend/test/utils/test-accounts.ts:170`、`:227`、`:238`、`:241`。实际直接消费者：`backend/test/11-content-submission/content-submission-integration.e2e-spec.ts:387` 未传 CreateAccountUsecase，因此使用此回落路径。
- 方向：测试造数、部分失败、生命周期。
- 最小触发：直接 repo 回落路径插入 account 成功后，密码回写或 user_info.save 抛错。
- 当前行为：回落实现没有事务；只有 createTestAccount 完整返回后，seedTestAccounts 才登记 accountId。部分账号已落库，但 ownership 为空，afterAll 无法回收。下一轮 residue 要求 user_info 指纹完整，会把这种半账号判为冲突，无法自动恢复。
- 期望与依据：计划 F1 §4.2/§4.3 要求成功取得 ID 后立即登记或对原子失败整体回滚，并验证 beforeAll 各关键阶段失败。task T1.3 声称 createTestAccount 支持 ownership，但当前该函数签名实际上没有该参数。
- 影响：隔离库留下半账号；重跑被唯一键或残留指纹拒绝阻断，需手工排查。当前没有证明会误删其他记录，因此按 P2，不定为 P1。
- 测试漏检原因：C08 调用本地 `failingBeforeAll`，手动创建完整组织、手动登记并手动调用 teardown；没有在真实账号 helper 的 account→密码→user_info 链路中注入失败。它不能证明该 helper 的失败回收正确。
- 最小修复：优先让回落账号+userinfo 创建处于同一事务；或在拿到账号 ID 时立即登记并保证部分行可被精确安全回收。不仅在调用方完整返回后登记。并检查 Promise.all 一项失败后其他造数仍在途的情况，在退出初始化前等待所有任务收敛，避免 afterAll/close 后才继续写库。
- 必补：分别在 account 插入后、密码回写、userinfo 写入阶段失败；断言无半账号残留或已登记并可精确回收；一项失败而另一项延迟成功时，初始化/teardown 顺序正确；真实 spec 初始化失败后再运行能够恢复。
- 归属：本轮 F1/R02，属于已要求的 C08，不是新增业务需求。

### V02 [P2] 清理漏查本轮账号在范围外组织中的成员关系，冲突直到 DELETE 阶段才发生

- 位置：`backend/test/utils/e2e-scoped-cleanup.ts:502`、`:506`；引用闭包 `:707` 之后没有补查该方向。
- 方向：数据库引用闭包、失败关闭、验收契约。
- 最小触发：owned 同时有本轮组织 O1 和账号 A；A 除 O1 的成员关系外，在范围外组织 O2 也有成员关系。
- 当前行为：orgIds 非空时，成员 SELECT 只按 organization_id 查询；按 account_id 查询被 `orgIds.length === 0` 限制。O2→A 没有进入预检，之后已开始删除资料/成员/组织/user_info，直到 DELETE account 被 O2 的 RESTRICT 外键拒绝。
- 期望与依据：F1 §4.3 第 4/5 项和 C05/C06 要求两个引用方向均核验；任何外部引用应在本次组合清理的第一条 DELETE 前拒绝，DELETE=0。
- 影响：当前事务回滚机制能够保护已执行删除，未发现此反例永久误删，因此不是旧 P1。问题是必要预检缺失、错误被数据库兜底、零删除承诺不成立，属于 P2。
- 测试漏检原因：现 C05 只测“外部账号加入本轮组织”，没有测反方向“本轮账号加入外部组织”。C06 也没有覆盖这一引用方向。
- 最小修复：组织候选和账号候选都查询，取并集并核验每条关系的两端；不要在组织非空时跳过账号方向，也不要把外部组织/成员自动纳入清理。保留根行锁及同事务预检/删除。
- 必补：O1/A/M1 都 owned，但 O2/M2 外部，断言归属预检拒绝、总 DELETE=0、所有行不变。覆盖 owned+residue、账号在多个组织的实际组合。
- 归属：本轮 F1/R02，计划明确要求的外部引用闭包。

### V03 [P2] Seed 仍会重新启用已退出成员并重置角色，与原计划 S06 不符

- 位置：`backend/scripts/seed-mock.organization-write.ts:145`、`:244` 附近的 SAME 判定、`:318`；测试 `backend/scripts/seed-mock.organization-write.spec.ts:420`。
- 方向：Seed 权限事实、计划契约。
- 最小触发：成员 id、orgId、accountId 与 Seed 一致，但该成员已变为 LEFT、left_at 非空或角色被人工修改。
- 当前行为：读取成员只取得 id/org/account；三者一致就 SAME，随后无条件更新 member_role/status/left_at。默认 ACTIVE 的 Seed 会把 LEFT 改回 ACTIVE、清空退出时间，并把 ENGINEER 改回 SUPER_ADMIN。
- 期望与依据：原计划 F2 S06 明确要求不能因为 Seed 自动启用或改角色；§5.3 要求核验可重置 Mock 的归属依据，不以固定 id/角色单独证明。新 spec.md §4 将匹配后的 role/status 修改列为白名单，但没有来自用户的变更授权，不能以实施侧规格改写已确认计划。
- 影响：非生产 Seed 运行会撤销外部对成员权限的修改，不符合本次“安全拒绝优先”边界。原异主 FK 覆盖已修，当前不夸大为生产直接授权绕过，按 P2 记录。
- 测试漏检原因：现 S05 覆盖了 DISABLED 组织，但没有覆盖 LEFT/被改角色成员；现末尾测试反而把角色重置视为成功，因此“S01～S06 通过”不能等同原计划 S06 完成。
- 最小修复：读取并核验 member_role/status/left_at 等必要事实；对于不符合已确认可重复 Seed 指纹的成员，失败关闭且零写入。正常第二次 Seed 可 no-op。若团队确实要允许强制重置已退出成员，需要用户明确接受这一不同契约，不能仅在本地 spec 中自行放宽。
- 必补：LEFT 成员保持 LEFT 和原 left_at，修改角色成员不被还原，均明确拒绝且 DML=0；正常指纹的重复执行仍幂等。补真实脚本事务冲突回滚验证。
- 归属：本轮 F2/R03，原计划 S06；不要求新增角色或业务表。

### V04 [P2] 并发测试屏障存在丢通知窗口，无法保证 W 系列确定性

- 位置：`backend/test/11-content-submission/content-submission-integration.e2e-spec.ts:201`、`:255`；W01 调用顺序 `:1361`、`:1370`、`:1374`，W02～W06 同类。
- 方向：测试异步时序、回归可靠性。
- 最小触发：竞争请求的组织解析及发起行锁较快，signalLockAttempt 在 waitForLockAttempt 注册 waiter 之前执行。
- 当前行为：signal 只唤醒当前 waiter，不保留到达事实；W01 启动竞争请求后先 await holder.query，再注册 waiter。通知可能已在这次 await 中发生并丢失，随后等待 15 秒超时，尽管生产锁逻辑正确。
- 期望与依据：计划 F3 要求 W01～W06 确定性交错，不依赖调度碰运气。成功跑一次或多次不能证明先 signal 的交错不存在。
- 影响：合法执行时序下出现假红/偶发 CI 失败，关键 RR 回归无法作为稳定验收依据；不是生产丢更新重现，按 P2。
- 测试漏检原因：当前调度大多在 waiter 注册后才到 signal；没有 signal-before-wait 测试，也没有独立验证屏障两种先后顺序。
- 最小修复：在启动竞争请求之前创建该轮专用等待 Promise，或用带代次/计数的到达屏障保存信号；不能仅调大 timeout。避免同一 submission 其他历史锁尝试误满足本轮屏障。finally 放行/关闭后还需等待竞争请求收敛，不能遗留测试在途操作。
- 必补：先 signal 后 wait、先 wait 后 signal、同 ID 多轮隔离、超时回收 waiter/请求；在刻意延迟 holder.query 的情况下 W 系列仍稳定通过。
- 归属：本轮 F3/R01 的新增测试，不涉及生产接口重构。
