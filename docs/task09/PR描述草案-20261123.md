## 2. 关键设计取舍（供评审重点看）

1. **来源身份不信任包内自报值**：包内 `source_account_id` 只是"待核验的账号 id"，授权真源是**本机数据库当前事实**。裁决集中在 `core/local-runtime/policy/record-package-source-identity.policy.ts`（纯函数）＋来源域核验器，**编排侧不另立第二套口径**。伪造账号/停用/归属变化/同公司他人四类反例**逐条拒绝且不落任何业务行**。
2. **跨资源失败精确补偿**：暂存成功但绑定/业务写失败 → 按 fileId **精确释放**（标记失效、行保留可追踪、不删字节）；**结果未知先核对再重试**只做保守裁决——无同键回执时同身份同版本也判冲突，不补记回执，不伪造同一内容证明。**零数据库迁移**。
3. **过期清理三道闸门**：公司范围（**本机正在备份的公司**——此前只按安装标识扫描会误删外公司包，已修）、业务引用守卫（四张引用表入边检查）、绑定守卫。DB 行不物理删，只回收存储字节。
4. **恢复执行的安全边界**：**业务数据写入走中立受控端口**（`LOCAL_RESTORE_RECORD_WRITER`），未注册即**失败关闭**——恢复编排**不直接写业务表**（与记录包导入同一条纪律）；三道闸门（写入闸门／回滚补偿／解密材料）真实参与裁决。
5. **用途维度不新增数据库列**：用途取自**云端签名声明**（`signed_claims.purpose`），本机只核对不自己发 ⇒ 撤销一个用途不影响另一个，**无迁移、无结构变更**。
6. **真实链是唯一能发现"替身掩盖缺陷"的地方**：本 PR 修复了 4 个只会在真实库/真实文件下暴露的缺陷（迁移外键表名写错、原件暂存扩展名带点、导入回执违反两个 CHECK 约束、恢复受理违反状态机 CHECK）。
7. **写传冻结的覆盖面此前被严重高估**：盘点 105 个写入口后发现，只有 4 个接入了冻结闸门（覆盖率 6.5%），
   业务域（工单/报告/资料/原件）与"数据出域/出盘/外传"链**全部裸奔**——恢复期间的并发写入会被整体替换掉。
   本轮按「被写行所属公司数据区（与备份/恢复范围同列）」扩到 **45 个**；仍未冻结的 17 条**逐条登记**（不声称全面停写）。
   新增 `assertBusinessWritable`：本机未启用本地运行部署时放行，避免把既有业务写入整体打挂。
8. **云服务缺失时"不注册端口"比"注册一个假实现"更安全**：本轮落地的云适配在未配置地址／凭据时
   **不提供任何实现**，调用方按受控原因码失败关闭——避免"看起来能上云、实际没上"的伪成功。
9. **真实链是唯一能发现"这三类缺陷"的地方**（第四轮实证）：受保护包生成在真实库上直接失败
   （`ORDER BY t.id` 撞上**复合主键**表）、凭据用途**永远不可核验**（写入要对象、读取只认 JSON 文本）
   ⇒ 上云永远被跳过、资产行缺 `installation_id` ⇒ **"有完整回执 ⇒ 手动清理"永远不可用**。
   三者都只在真实库／真实 HTTP 上暴露，单测与替身都看不见——**修复后各自留了回归证据**。
