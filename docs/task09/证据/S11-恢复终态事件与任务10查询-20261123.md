## 1. 问题定位

| 侧 | 事实 |
| --- | --- |
| 任务 10 读侧 | `core/management-audit/policy/management-audit-detail.policy.ts` 把 `detail` 投影为**固定白名单**：`reason`／`stage`／`changedFields`／`attemptNo`／`beforeOrganizationName`／`afterOrganizationName`；非白名单键**静默丢弃** |
| 任务 09 写侧（改前） | `ManagementAuditService.appendRestoreEvent` 把 `detail` 写成 `{ restore_id, backup_id, protection_backup_id, result, reason_code, counts }` —— **一个键都不在白名单内** |
| 后果 | 任务 10 的"关键操作记录"页读恢复事件 ⇒ 白名单投影后**没有任何可展示字段**（`detail = null`）⇒ 恢复原因与阶段**读不到** |

## 2. 改动清单

### 2.1 新增 core 策略（对齐口径的单一来源）

`backend/src/core/local-runtime/policy/local-restore-audit.policy.ts`（新建）

- `LOCAL_RESTORE_AUDIT_STAGES`：三个阶段标识
  - `RESTORE_SUCCEEDED`（成功终态）
  - `RESTORE_ROLLED_BACK`（失败但已按保护副本回滚）
  - `RESTORE_ROLLBACK_FAILED`（失败**且**回滚也失败 ⇒ 保留保护副本、设备继续停写停传）
- `buildLocalRestoreAuditDetail` / `serializeLocalRestoreAuditDetail`：
  **直接复用任务 10 的 `serializeManagementAuditDetail`** ⇒ 写侧与读侧共用同一套白名单、
  长度与字符集规则，"写得进去的必然读得出来"。

> **长度陷阱（本轮实测踩到）**：读侧 `stage` 上限 **32 个字符**，
> 初版阶段名 `RESTORE_EXECUTION_ROLLBACK_FAILED`（33 字符）被读侧**截断**成
> `RESTORE_EXECUTION_ROLLBACK_FAILE` ⇒ 读出来的阶段名不完整。已缩短为 `RESTORE_ROLLBACK_FAILED`。

### 2.2 事件写入（幂等 ＋ 字段归位）

`backend/src/modules/lithography/management-audit.service.ts#appendRestoreEvent`

| 事实 | 落在哪 |
| --- | --- |
| 恢复 ID | 事件列 `target_id`（`target_type = 'LOCAL_RESTORE'`） |
| 作用公司 | 事件列 `organization_id` |
| 操作者与当时等级 | 事件列 `actor_account_id`／`actor_admin_level` |
| 真实终态 | 事件列 `result`（`SUCCEEDED`／`FAILED`） |
| 原因 | `detail.reason`（受控原因码，如 `RESTORE_EXECUTION_FAILED`） |
| 阶段 | `detail.stage` |
| 计数明细 | **不进 detail**（只进服务端日志；`detail` 是可展示摘要，不该放业务计数） |

- **幂等**：插入前按 (operation, target_type, target_id, result) 查一次；已存在则跳过
  ⇒ **重试执行不产生重复记录**（同一恢复 ID 的不同终态仍各留一条——那是不同事实）。
- 写侧仍只写 `reason`／`stage` 两个白名单键 ⇒ **不泄漏**包正文、原件字节、文件路径、密钥、堆栈。

### 2.3 终态事件写入点（只有终态）

| 位置 | 阶段 | 说明 |
| --- | --- | --- |
| `local-restore-execution.service.ts`（成功路径） | `RESTORE_SUCCEEDED` | 终态事件**先写**：写不进去就不算恢复成功（冻结不解��） |
| 同上（失败且回滚成功） | `RESTORE_ROLLED_BACK` | 失败终态事件（尽力而为，不反过来打断失败处置） |
| 同上（失败且**回滚也失败**）→ `failAndKeepHold` | `RESTORE_ROLLBACK_FAILED` | **本轮新增**：这条路径原先**完全没有事件**，而它恰恰是最需要留痕的（设备继续停写停传） |

- **预检与受理不写事件** ⇒ "受理 ≠ 恢复成功"在事件层面也成立。
- **普通备份／同步不生成恢复记录**：`target_type = 'LOCAL_RESTORE'` 只在
  `appendRestoreEvent` 一处产生（恢复执行链的唯一出口）；其余三类 operation 各有各的写入方。

## 6. 剩余限制（如实登记）

1. **幂等是"先查后写"**，不是数据库唯一索引保证：两个**并发**重试理论上仍可能各写一条。
   恢复执行本身由"运行行 `RUNNING` 独占 ＋ 冻结事实唯一"串行化，
   真正并发的双写窗口极小；未为此新增唯一索引（该表同时承载凭据类事件，
   全局唯一索引会误伤"重复补发凭据"这类合法重复）。
2. **`counts`（恢复行数）不进入可展示摘要**：任务 10 白名单没有对应键，
   本轮按"复用任务 10 契约、不擅自扩白名单"处理；计数只进服务端日志。
3. 读侧只覆盖**任务 10 已有的 `managementAuditEvents`**；
   恢复页自身的结果展示（前端）在第 14 项处理。
