## 2. 跨端身份（旧 G2／G5）——已实现，本轮核对

| 事实 | 作用 |
| --- | --- |
| `account_uuid`（账号不可变稳定标识，唯一索引） | **最强证据**：命中 ⇒ 两个账号行是同一条账号事实（克隆／同步场景） |

## 3. 本轮新增：混合导出（旧 G15）

### 3.1 需求依据

- R070 的输入参数只有 `record_ids` ＋ `version_nos`（**没有资源类型判别式**）；
- V44 原型的入口是「导出**我的**维修记录包」（"我的记录"跨类型）；
- 导入侧**本就支持混合类型包**（按条目各自的 `resource_type` 逐条处理）⇒ 导出侧不混合会造成两侧不对称。

### 3.2 实现（**旧接口保持兼容**）

| 层 | 改动 |
| --- | --- |
| core/模块类型 | `RecordPackageExportCommand` 新增**可选** `entries?: { resourceType, recordId }[]` |
| 导出服务 | `resolveExportEntries`：有 `entries` 时按其逐条处理（**每条自带资源类型**），否则回落旧的"单一类型 ＋ id 列表" |
| 用例层 | 归一化：混合形态优先，旧形态自动转成 `entries` ⇒ 服务层只有**一份**条目清单口径 |
| GraphQL | 新增**可选**入参 `entries: [RecordPackageExportEntryInput!]`（`@InputType`）；旧的 `resourceType` ＋ `recordIds` **原样保留**，旧客户端不受影响 |
| 结果 | 汇总字段 `resourceType` 取**首个条目**的类型；**逐条结论各自带自己的 `resourceType`** |

### 3.3 实现过程中抓到并修复的一个真实缺陷

第一版把"逐条授权判定"仍传命令级的单一 `command.resourceType` ⇒ **混合导出时工单条目被按"资料"口径授权**（假阳性风险）。
已改为逐条传各自的 `resourceType`（`assertRecordAuthorized(command, resourceType, recordId)` ＋ 策略调用同改）。

### 3.4 取证

`CI=1 npx jest src/modules/lithography/record-package-export.service.spec.ts` → **12 例全绿**，含新增 2 例：

- `混合导出：一次导出可跨资源类型（逐条各自授权、逐条各自入清单）` ⇒ `itemExported=2`、
  逐条结论类型为 `['REFERENCE_DOCUMENT','REPAIR_REQUEST']`、清单两条 `resource_type` 各自独立、`record_uuid` 互不相同；
- `混合导出：旧接口形态不受影响（单一类型 ＋ 记录 id 列表）` ⇒ 旧调用路径行为不变。

记录包相关整体：`CI=1 npx jest`（导入用例 ＋ 导出服务 ＋ 导出授权策略 ＋ 可移植身份策略 ＋ 来源身份策略）
→ **5 套件／63 条断言全绿**。
