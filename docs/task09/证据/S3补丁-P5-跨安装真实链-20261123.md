# S3 补丁 · P5 跨安装真实链验证（2026-11-23）

> 对应总计划《S3 补丁》P5-1「在已核实可丢弃的双设备／双公司隔离环境……导出含实际原件的包 →
> 异安装同公司有权导入 → 逐项结果 → 来源详情读回」。
> 本轮**首次真实跑通**该链路，并在真实库／真实文件下抓到 **3 个此前单测掩盖的缺陷**（已全部修复）。

## 0. 一句话结论

- **P5-1 已完成**：两台"设备"（两套隔离库 ＋ 两个独立文件根 ＋ 两个独立安装身份）之间，
  `导出（含真实原件字节）→ 复制到 U 盘介质路径 → 安全预检（不写库）→ 确认导入 → 逐项结果 → 读回核对`
  **10 项断言全绿**；**原件字节逐字节一致**（SHA-256 与字节数全等）。
- **顺带修复 3 个真实缺陷**（§2）：迁移外键表名写错、暂存扩展名带点、导入回执违反两个 DB CHECK 约束。
  这三个都**只会在真实库／真实文件下暴露**，单测替身无法覆盖。

## 2. 本轮抓到并修复的 3 个真实缺陷

| # | 缺陷 | 为什么单测没抓到 | 修复 |
| --- | --- | --- | --- |
| D1 | 迁移 `1775503000000`（上传任务账号绑定）外键指向 **`account`** 表，真实表名是 **`base_user_account`** ⇒ 该迁移在**任何既有库**上都无法执行。连带影响：上一窗口宣称的"归属列已落地"在真实库上**并不成立**（dev 库既无该两列，迁移历史也无此条） | 单测用替身仓储，不触真实 DDL | 订正为 `base_user_account`（该迁移**从未在任何库生效过** ⇒ 按"未生效的迁移可就地订正"处理，**不改已接受基线**）；随后两个库补跑迁移（dev 补 2 条、e2e 补 4 条） |
| D2 | 原件暂存把扩展名**带点**（`.pdf`）传给存储层，而存储层只接受不带点的小写扩展名 ⇒ **任何带原件的记录包**在暂存阶段失败关闭 | 暂存用例的替身 `save` 接受任意扩展名 | 扩展名去点后再传给存储层（MIME 查表仍用带点形式）；补回归断言 `save(content, 'pdf')` |
| D3 | 导入回执违反两个 DB CHECK：① `chk_sync_receipt_confirm_time`（非 PENDING/CONFLICT 须有 `received_at` 或 `confirmed_at`）——原实现 `receivedAt: null`；② `chk_sync_receipt_source`（`source_system` 只能 `'LOCAL'`/`'CLOUD'`）——原实现写 `'LOCAL_IMPORT'` ⇒ **真实库上导入必然失败** | 回执服务用例用替身仓储，不校验约束 | ① `receivedAt` 写导入时刻（"对端实际接收时间"＝本机收到该版本；`confirmed_at` 是旧版字段，实体注释明确不双写）；② `source_system` 改 `'LOCAL'`（U 盘是本地来源；哪台本地安装交付由 `source_installation_id` 区分，读侧据此不会把导入误判成"已同步到云端"）；补 2 条回归断言 |

> **共同教训**：这三个缺陷都位于"替身无法覆盖"的位置（真实 DDL、真实存储契约、真实 CHECK 约束）。
> 单元测试全绿**不等于**真实库可用——真实链验证是唯一能发现它们的手段。

## 4. 脚本与复现

`backend/scripts/task09-cross-installation.ts`（两段式，交接文件 `/tmp/task09-cross-installation.json`）：

```
# 设备 A：先灌同构夹具，再导出
SEED_DOTENV=env/.env.development npx ts-node -r tsconfig-paths/register scripts/seed-mock.ts
TASK09_CROSS_ENV_FILE=env/.env.development TASK09_CROSS_DATABASE=lithography_task09_dev \
  npx ts-node -r tsconfig-paths/register scripts/task09-cross-installation.ts source
# 把包目录复制到"U 盘"路径后，在设备 B 执行：
TASK09_CROSS_ENV_FILE=env/.env.e2e TASK09_CROSS_DATABASE=lithography_task09_test_e2e \
  TASK09_CROSS_FIELD_KEY=<公司共享密钥> TASK09_CROSS_FIELD_IV=<公司共享IV> \
  npx ts-node -r tsconfig-paths/register scripts/task09-cross-installation.ts target
```

脚本用**既有集成用例的装配范式**（`ConfigModule.forRoot` ＋ `LoggerModule` ＋ `TypeOrmModule.forRoot` ＋
`TypeOrmTransactionModule` ＋ 业务模块），库名与 env 文件一致性复用迁移入口的同一套校验（不猜库名）。

## 5. 本轮顺带修复的装配缺陷（影响面比记录包更广）

`src/infrastructure/logger/logger.module.ts` 原先 `exports: [PinoLogger]`——**Nest 11 不允许从导入模块转导出
provider**（`validateExportedProvider` 只接受本模块自有 provider 或已导入的**模块类**），
⇒ 该模块**无法被任何独立装配**引用（应用启动、仓库既有实库/集成用例都受影响）。
已改为转导出 **nestjs-pino 的模块类**（合法；nestjs-pino 的模块本身是 `@Global`，效果等价）。
**未改任何业务语义**。
