## 1. G28 优先级核对（先核对，再动手）

### 1.1 三方依据的实测摘录

| 依据 | 原文／实测 | 对 padding 的约束 |
| --- | --- | --- |
| 任务书 V2.3《前端布局与视觉验收》第 4 条 | 「Chromium 原型实测基线（中文、默认壳）。三种视口的主标题字号 24px、标题框高 32px，**卡片间距 20px、圆角 14px、内边距 24px**，表头 14px 且背景为 #fafafa。」 | **明确要求 24px** |
| 任务书 V2.3《前端布局与视觉验收》第 1 条 | 「按原型 `.page-header` → `.page-title`／`.page-description` → `.page-stack` 下的卡片组织内容。参照 `.ant-card-head-title`、**`.ant-card-body`**、`.collection-stats`…」 | 指向原型的**卡片体** |
| 任务书《逐项验收矩阵》 | 「视觉以V44相应页面及页面V6.5为依据，先定位实际路由与selector，记录原型尺寸与实现computed style／rect／overflow。」 | 原型＝基准 |
| `frontend/docs/gkj-visual-baseline.md` §2.6 `DataCard / TableContainer` 行 | 「gkj `.panel-card`：半透明白底 rgba(255,255,255,.92)、1px #e2e8f0、14px 圆角、0 10px 30px rgba(15,23,42,.06) 投影」 | **未规定 padding** |
| 同上 §2.5「公共面板（panel-card）」行 | 同样只列背景／描边／圆角／投影 | **未规定 padding** |
| 同上 §2.6 `StatCard` 行 | 「padding 16px…**统计卡片不是普通 panel-card**」 | 仅约束 StatCard，与本项无关 |

### 1.2 结论：不存在"要求冲突"，无需产品裁定

- 任务书对**任务 09 的目标页**明确要求按原型的 24px；
- 仓内全局设计规范对 panel-card 的 padding **无任何规定** ⇒ 16px 只是
  `src/index.css` 里的**实现取值**（`e8adc9a` 引入 gkj 视觉壳时的初值），不是规范固化值；
- 因此**不存在"仓内规范要求 16px vs 任务书要求 24px"的冲突**，
  按计划第 11 项第 2 条即可直接走"该页面局部对齐并检验其他直接消费者"。

### 1.3 对 S20 证据前提的纠正（重要）

S20 §3 写道：

> 另有已通过的视觉规格固化（`e2e/admin-document-database-visual.spec.ts` 的 `padding: '16px'`）。

**该前提不成立**。实测 `e2e/admin-document-database-visual.spec.ts`：

```49:55:frontend/e2e/admin-document-database-visual.spec.ts
  card: {
    backgroundColor: 'rgb(255, 255, 255)',
    borderColor: 'rgb(229, 231, 235)', // #e5e7eb
    borderRadius: '10px',
    boxShadow: 'rgba(15, 23, 42, 0.05) 0px 1px 3px 0px',
    padding: '0px',
  },
```

- 断言的选择器是 `.kb-card`（**知识库页专用**卡壳，见同文件 `:331` `requireElement<HTMLElement>('.kb-card')`），不是 `.data-card`；
- 断言值是 `'0px'`，不是 `'16px'`；
- 圆角断言是 `'10px'`，与 `.data-card` 的 `'14px'` 也**不同** ⇒ 进一步说明二者是两套卡片语言；
- `.kb-card` 在 `src/index.css` 里**根本没有 padding 声明**（内边距由其子元素承载）。

⇒ 全仓**没有任何**断言固化 `.data-card` 的 16px；唯一的 16px 断言在
`frontend/e2e/task09-visual-metrics.spec.ts`，而那正是本项自己的度量规格
（其注释把 24px vs 16px 登记为"已知偏离"）。故"旧测试固定 16px ⇒ 自动豁免"不成立。

## 2. 实现：局部对齐（不动全局卡片语言）

### 2.1 改动清单

| 文件 | 改动 | 理由 |
| --- | --- | --- |
| `frontend/src/index.css` `:root` | 新增 `--panel-padding: 16px`（默认）与 `--panel-table-padding: 16px` | 把"卡片体内边距"变成**语义 token**，使局部覆盖有唯一真源 |
| 同上 `.data-card` / `.table-container` | 原共用一条 `padding: 16px` ⇒ 拆为 `.data-card{padding:var(--panel-padding)}` 与 `.table-container{padding:var(--panel-table-padding)}` | 原型 `.table-container` 实测 **16px**，与卡片体 24px **不同**；不拆开会被作用域误伤 |
| 同上 新增 `.v44-panel-page` | `--panel-padding: 24px` | 页面级作用域，承载 V44 局部对齐 |
| `frontend/src/pages/local-settings/index.tsx` | 根容器加 `v44-panel-page` | 目标页 |
| `frontend/src/pages/local-backup/index.tsx` | 根容器加 `v44-panel-page` | 目标页 |
| `frontend/src/pages/record-packages/index.tsx` | **未改** | 该页无公共卡片面（`card: 'NONE'`），加类无效果且会误导 |
| `frontend/src/pages/sync-conflicts/index.tsx` | **未改几何**（仅移除 `destroyOnClose`，见 §5.2） | 同上 |

### 2.2 为什么不做全局改动

`.data-card` 是**跨任务共享**的卡片语言，直接消费者逾 20 处
（登录、注册、管理端、工程师端、客户端、我的资料记录、工单列表等）。
全局改 24px 会改写这些页面的既有几何，超出任务 09 的授权范围；
而 `.v44-panel-page` 只覆盖**任务 09 的目标页**，其余消费者的几何**不变**
（§3.4 的回归断言给出证据）。

### 2.3 改动后的 token 真源

```76:84:frontend/src/index.css
  --panel-padding: 16px;
  /* 表格容器内边距：V44 原型 `.table-container` 实测 16px（与卡片体 24px 不同），
     独立成 token，避免卡片体的页面作用域覆盖误伤表格容器。 */
  --panel-table-padding: 16px;
```

## 5. 顺带修掉的两处真实缺陷

### 5.1 `sync-conflict` adapter 零形状校验（渲染期崩溃）

**现象**：冲突详情响应里 `localSnapshot` 若是对象而非字符串，
`src/features/sync-conflict/ui/sync-conflict-detail-panel.tsx` 直接渲染它 ⇒
渲染期 `TypeError` ⇒ 整页被路由错误边界替换，**用户看不到任何冲突事实**。

**对比**：第 06 项已为 `repair-request-adapter.ts` 建立三处 adapter 形状校验的先例；
`sync-conflict-adapter.ts` 的**三处映射函数**（清单／详情／裁决）此前**零校验**。

**修法**（失败关闭）：形状不符即抛受控错误，让页面落"可重试失败态"，
而不是把错形状的值交给渲染层。清单／详情／裁决三处均接入校验，
并**区分"字段缺失"与"显式 null"**（GraphQL 契约里 `diff` 可空，
显式 `null` 是合法响应，字段缺失才是非法响应）。

单测：补全原夹具（原先只给 `{ conflictId: 'c-1' }` 这类**残缺**响应，
真实服务端必定返回选择集里的全部字段），并新增形状校验用例
（快照非字符串、缺 diff、diff 显式 null 合法、清单项缺字段、裁决缺 outcome）。

### 5.2 同步冲突抽屉的 `destroyOnClose` 吃掉焦点恢复

**现象**：任务书要求"取消后焦点返回触发控件"，但同步冲突抽屉关闭后
焦点落到 `body` 而非「查看差异」按钮。

**定位过程**（真实浏览器实测，非推断）：

| 关闭时机 | 关闭后焦点落点 |
| --- | --- |
| 抽屉打开后**立即**关闭（不等详情加载） | `body` |
| 详情渲染完成后 +0ms 关闭 | `body` |
| 详情渲染完成后 +300ms 关闭 | `body` |
| 详情渲染完成后 **+700ms** 关闭 | **「查看差异」按钮** ✅ |

触发按钮在全过程**始终存在**（`triggerCount=1`，排除"元素被重建导致引用失效"），
焦点也**先正确回到按钮**、随后才丢失 ⇒ 根因是
`destroyOnClose` 在**关闭动画期间**销毁抽屉子树，使 antd 在打开时捕获的触发元素引用失效。

**修法**：移除 `destroyOnClose`。抽屉内容本来由 `activeConflictId === null` 条件控制，
关闭即卸载详情面板（无残留、无重复请求），不影响原语义；
但关闭动画期间子树不被销毁 ⇒ 焦点稳定返回。
新增「动画期内立即关闭」用例守住该边界（§3.5）。
