## 1. 发现并已修复的缺陷

### R1 · 审计幂等键漏掉"终态阶段"⇒ 更严重的终态被静默吞掉

| 项 | 内容 |
| --- | --- |
| 位置 | `backend/src/modules/lithography/management-audit.service.ts#appendRestoreEvent` |
| 现象 | 幂等判定键是 `(operation, targetType, 恢复 ID, result)`；`result` 只有 `SUCCEEDED`／`FAILED`。于是**同一恢复 ID 的两次失败终态**（例如首次执行"已回滚"、重试后"回滚也失败"）会被判为同一事实 ⇒ **后一条（更严重的那条）事件不再写入** ⇒ 任务 10 页面读不到"回滚也失败"这一最需人工处置的终态 |
| 根因 | 终态的**粒度是"结果 ＋ 阶段"**（`RESTORE_SUCCEEDED`／`RESTORE_ROLLED_BACK`／`RESTORE_ROLLBACK_FAILED`／`RESTORE_HOLD_RETAINED`），幂等键只覆盖了"结果"这一半 |
| 修复 | 幂等键改为 `(恢复 ID, 结果, **阶段**)`；既有事件的阶段按**读侧同一套投影**（`projectManagementAuditDetail`）取：阶段相同 ⇒ 跳过（同一事实的重复执行不重复留痕）；阶段不同 ⇒ **照写**（是另一个终态事实）；既有事件阶段**读不出来**（历史自由文本）⇒ 判定为"无法确认同一事实" ⇒ 写新的（宁可多留，不可漏掉终态） |
| 用例 | `management-audit.service.spec.ts`：① 幂等用例改为**按真实行形态**给既有事件（detail 带可读阶段）；② 新增"失败终态**升级为更严重阶段**时必须留痕"；③ 新增"既有事件阶段读不出来 ⇒ 不吞掉新事件" |

### R2 · "数据已回滚但冻结解除失败"这条终态**完全没有审计事件**

| 项 | 内容 |
| --- | --- |
| 位置 | `backend/src/modules/lithography/local-restore-execution.service.ts#failAfterWrite`（`localWriteHoldService.release` 失败的 catch 分支） |
| 现象 | 该分支调用 `failAndKeepHold(...)` 时**没传审计信息** ⇒ `audit === undefined` ⇒ **一条审计事件都不写**。而这条路径的结论是"数据已回滚，但**设备继续停写停传**、需人工处置"——恰恰是最需要留痕的终态；任务 10 页面因此**完全看不到这次恢复尝试** |
| 根因 | `failAndKeepHold` 的 `audit` 参数是**可选**的，两条调用路径只给其中一条传了 |
| 修复 | ① `local-restore-audit.policy.ts` 新增终态阶段 `EXECUTION_HOLD_RETAINED: 'RESTORE_HOLD_RETAINED'`（数据侧与"已回滚"相同，差别在**停写停传没有解除**）；② 该分支补传审计信息 ⇒ 终态照写，阶段标成"冻结未解除" |
| 用例 | `local-restore-execution.service.spec.ts` 新增"数据已回滚但**冻结解除失败**：终态必须留痕（阶段＝冻结未解除）"（构造：保护副本可读 ⇒ 回滚成功；`release` 两次均失败） |

### R3 · 抑制事实采集**晚于**打断循环外键 ⇒ 删除事实与"原稿→工单"关联都会丢

| 项 | 内容 |
| --- | --- |
| 位置 | `backend/src/modules/lithography/local-restore-record.writer.ts#restoreScope`（`captureSuppressionFacts` 与 `breakCircularForeignKeys` 的先后） |
| 现象 | `repair_request_intake` 的范围口径是 `SERVICE_OR_PARENT_ORGANIZATION`（**自身服务公司 ∪ 引用了本公司工单的行**）。原顺序是"先打断循环外键（把 `converted_request_id` 置空）→ 再采集抑制事实"，带来两个后果：① 那些**服务公司为空、只靠父行归属**的报修原稿，在打断后**掉出范围** ⇒ 采集不到其删除事实 ⇒ **备份之后被删除的报修原稿会被旧包复活**（违反 R086「不复活删除下架」）；② 采集到的行带着 `converted_request_id = null` ⇒ 后面回填抑制事实（按**整行**写回）会把**已经还原的"原稿 → 工单"关联覆盖回空** ⇒ 关联事实丢失 |
| 修复 | 把**抑制事实采集移到打断循环外键之前**（顺序敏感）：采集时父行归属分支仍可用、采集到的行保留原关联；打断只影响"清空"这一步，不影响"当前事实"的采集 |
| 用例 | `local-restore-record.writer.spec.ts` 新增"抑制事实采集**先于**打断循环外键"（记录 `getMany`（采集）与 `update`（打断）的调用顺序并断言先后） |

## 2. 复核后确认**无问题**的结论（同样留痕，避免重复怀疑）

| # | 复核对象 | 结论与依据 |
| --- | --- | --- |
| 1 | 公司范围谓词（6 种口径：`OWNER`／`SERVICE`／`SERVICE_OR_PARENT`／`PARENT_OR_OWNER`／`PARENT_OWNER`／`INSTALLATION_COMPANY`） | 无跨租户缺口：`SERVICE_OR_PARENT` 的"∪ 引用本公司工单"分支**不是**跨公司泄漏——`repair_request_intake` 的数据归属就是本机服务公司（`service_organization_id`），本机导出自己的服务记录属预期；`INSTALLATION_COMPANY` 为"安装 × 公司"双条件，无整表口径 |
| 2 | 混合导出与导入的对称性 | 清单按**逐条** `resource_type` 记录，导入侧也按 `item.resource_type` 逐条处理 ⇒ 两侧对称；清单**没有**包级 `resource_type` ⇒ 混合包不会被误判成单一类型 |
| 3 | GraphQL 层 `resourceType` 仍为必填 | 混合形态下该参数冗余但**无害**（逐条判定用各自的类型，汇总取首条类型并已在证据登记）；旧客户端不受影响 ⇒ **不改契约**（改可选属契约面变更，另需裁定） |
| 4 | 冻结守卫口径 | 导出／导入／清理／派发同族用例统一用 `assertCompanyWritable`（要求本机安装身份），新增的 `RestoreScopeWriteGuardService` 走 `assertBusinessWritable`（业务写入口口径：未初始化本地身份时放行）⇒ 与各自场景一致，无口径漂移 |
| 5 | 审计事件表无 `backup_id` 列 | 恢复 ID 落在事件列 `target_id`，经 `backup_restore_run.backup_id` 仍可关联 ⇒ 备份包 ID 不丢事实（只是不再冗余进 `detail`；读侧本就投影不到该键） |
