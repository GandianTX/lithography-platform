### 2.2 修掉的耦合缺陷：备份链抛错会吞掉当日的过期清理

**现象**（改前 `local-backup-schedule.runtime.ts:51-77`）：备份调度、上云重试、过期清理
三段**共用一个 `try`** ⇒ **备份调度或上云重试一旦抛错，`runRetentionCheck()` 根本不会执行**，
当日的过期清理被静默跳过。

**为什么是缺陷**：任务书第 52 行要求过期清理「**每日**及恢复运行检查」——
清理是**独立职责**，不能被其它链的异常吞掉。

**修复**：三段职责**互不阻断**，各自失败关闭（各自 try/catch + 各自记日志）；
`runCycle` 另加**兜底 catch**，防止任何意外逃逸成未处理的 Promise rejection
（启动处是 `void this.runCycle()`，无人 await）。

**回归**：`local-backup-schedule.runtime.spec.ts` **6/6** 通过，其中新增 2 例：

- 「备份调度失败**不阻断**过期清理（清理是独立职责）」；
- 「过期清理自身失败只记日志，不中断进程、不逃逸成未处理 rejection」。

### 3.2 实现：预检与删除进入同一数据库事务

**改前的口径缺口**（`local-backup-cleanup.service.ts` 改前 `:344-416`、`:494-582`）：
`decide*` 裁决（读资产）→ 逐项 `cleanupOne`（各自独立 `update` ＋ 文件删除）**分属不同事务**。
并发下目标集合可能漂移：另一轮清理刚把某包置为 `CLEANED`，本轮仍按旧快照去删同一个目录。

**修复**：

| 改动 | 说明 |
| --- | --- |
| 注入 `TRANSACTION_RUNNER`（`@Optional()`，`TypeOrmTransactionModule` 是 `@Global()`） | 生产必有事务运行器；替身装配时可降级 |
| 新增 `protected resolveTransactionRepositories(tx)` | 生产：两个仓储都取自**同一事务**的 `EntityManager`；单测可整体覆盖 |
| 新增 `private runInCleanupTransaction(work)` | 一轮清理的「全量预检 ＋ 逐项删除」在**单个事务**内完成 |
| `cleanupManualPackages`／`cleanupExpiredPackages`／`cleanupAllExpiredPackages` | 三条入口全部改走事务路径（读范围 → 裁决 → 逐项删 → 运行汇总） |
| 事务内读取加**悲观写锁** `lock: { mode: 'pessimistic_write' }` | 并发清理的执行者在此串行；拿到锁后读到**最新状态**再裁决 |
| 文件删除**不因单项失败抛出事务** | 失败项记 `RETAINED` ＋ 原因，逐项结果仍落库（符合「文件与SQL非原子，失败明确记录」） |

**由此得到的并发幂等**（计划第 2 条「必要时实现符合需求的并发幂等」）：

- 第二个执行者**等待**行锁 ⇒ 第一个提交后它读到 `local_status='CLEANED'`、
  `local_reference=null` ⇒ 裁决为 `PACKAGE_ALREADY_CLEANED` ⇒ **跳过，不重复删除**；
- 「每日一次」的节流标记仍是**进程内存字段**（`retentionCheckDay`），
  多副本部署下各跑一次，但因清理本身幂等且受行锁保护 ⇒ **重复执行无害**；
  当前实际部署为**单实例 Worker** ⇒ 无实际影响，**该失效点如实登记**（§6）。

### 3.3 实现：「恢复运行时检查」（任务书第 52 行）

**需求原文**（任务书第 52 行）：

> 过期仅成功本地包约30天，**每日及恢复运行检查**，不强制留最近一份。

**改前的事实**：全仓检索 `cleanupAllExpiredPackages|cleanupExpiredPackages` 的调用方只有
`local-backup-schedule.runtime.ts:91`（每日）与
`cleanup-local-backup-packages.usecase.ts:86`（管理员手动／`RETENTION` 模式）
⇒ **恢复运行时**从不触发过期清理。

**修复**：在 `LocalRestoreExecutionService.execute` 的**成功路径**、**冻结解除之后**触发一次
`cleanupAllExpiredPackages()`。

| 设计要点 | 理由 |
| --- | --- |
| 挂在**冻结解除之后** | 恢复期写入冻结未解除时，清理链的冻结闸门（`assertCompanyWritable`）会拦下该公司的清理 ⇒ 挂在冻结前等于白跑 |
| 只挂**成功路径** | 失败路径仍**持有冻结**（`failAndKeepHold`）⇒ 清理必被闸门拦住 |
| **失败关闭** | 清理出错**不改判恢复结果**（恢复事实已落库：状态、审计事件、冻结解除都已完成）⇒ 只记服务端日志 |
| 依赖注入为 `@Optional()` | 避免与清理链形成硬耦合；测试替身可直接注入 |

## 6. 本项遗留与边界（如实登记）

1. **跨公司暂存原件残留（G6）**：本机安装映射之外的公司的 `stored_file` 暂存行
   **不会被本机清理任务回收**，可能长期占用 `var/reference-documents` 空间。
   本轮按「非需求必需」**未实现**回收，也**未**把它写成「已清理」。
   若产品要求，方案为沿用 `local_company_setting` 的多公司口径（**不需要新增字段**）。
2. **`stored_file` 无释放原因／时间列（G7）**：按行追溯「为何被释放」目前**不可行**
   （只有 `status` 与返回结果／日志）。如需追溯须**新增迁移**加列，
   本轮无需求依据 ⇒ 未加列，**登记为待产品裁定项**。
3. **无暂存原件批次键（G8）**：功能上由**逐条精确补偿**等价覆盖；
   「按一次导入批量回收」这一**操作形态**目前不可直接执行（需先收集 fileId 清单）。
4. **「每日一次」标记仍是进程内存字段**：多副本部署下各实例会各跑一次每日检查。
   清理本身幂等且受行锁保护 ⇒ 重复执行无害，但会产生重复扫描开销。
   当前实际部署为**单实例 Worker**（仓内无编排/副本配置）⇒ 无实际影响。
5. **需要物理清理授权的实库规格未运行**：`local-backup-cleanup.interrupt.realdb.spec.ts`
   要求 `E2E_ALLOW_PHYSICAL_CLEANUP=1`，而 `env/.env.e2e` 中该值为 **`false`**
   ⇒ 本轮**未擅自开启**（该规格默认 skip）。中断可辨认的**单测**已覆盖，
   实库版留待授权后补跑。
6. **恢复失败路径不触发过期清理**：失败路径仍持有写入冻结，
   清理必被闸门拦住 ⇒ 触发无实际效果（有意为之，已在 §3.3 说明）。
7. **第 10 项遗留**（D5／D7／D2／D3-D4／D8-D11）与第 08 项遗留不受本项影响，
   仍按既有登记保持。
