# S2 · 写入／同步冻结入口清单化核对（任务 09 · 2026-11-23 第三轮）

> 目的：落实修复计划 S2-1「梳理全部业务写入、文件、导入、同步 Worker 与公开 API 的冻结入口，
> 核对受影响设备公司范围、并发和重启；**不能仅以少数守卫已接入认定全面停写**」。

## 1. 核对结论（本轮最重要的发现）

接手时的**真实覆盖面**是：写入／同步冻结闸门只接在 **4 个** local-runtime 用例上，
业务域（工单／报告／资料／投稿／原件／后台 Worker）**零覆盖**。

| 指标 | 接手时 | 本轮结束 |
| --- | --- | --- |
| 写入口总数（usecase 级 ＋ Worker runtime 级） | 105 | 105 |
| 必须冻结（写公司业务数据区／公司数据出域出盘） | 62 | 62 |
| 已挂冻结守卫 | **4** | **45** |
| 未守卫且必须冻结 | **58** | **17**（见 §5 保留清单） |

**判定依据**：恢复链的整体替换范围＝`BACKUP_TABLE_DESCRIPTORS` 的 **14 张表**
（`repair_request`／`repair_request_revision`／`maintenance_report` 及其版本、附件、报警、步骤、故障子表／
`reference_document`／`reference_document_revision`／`stored_file`／`local_upload_task`／`local_backup_run`）。
凡写入这些表的入口 ⇒ 恢复期间写入会被整体替换掉 ⇒ **必须冻结**；
写入不在该范围的表（投稿、AI 会话、过程行等）⇒ 恢复不会覆盖，列为**本轮不冻结**（并已登记）。

## 2. 冻结口径（本轮新增的统一口径）

- 判定单位＝**被写行所属的公司数据区**，与备份／恢复范围口径**完全一致**：
  - `repair_request` 的归属列是 `owner_organization_id`（客户公司），不是服务公司；
  - `reference_document`／`maintenance_report` 用各自的 `owner_organization_id`；
  - `stored_file` 用 `owner_organization_id`。
- 归属公司为空（历史行）⇒ 该行不属于任何公司数据区 ⇒ 不受冻结影响（与 `scope = owner_organization_id` 的
  备份范围一致，不扩大也不缩小）。
- 冻结范围＝**本机安装标识 × 受影响公司数据区**（`local_write_hold` 表落库 ⇒ 进程重启后仍可识别）。
- **两种准入语义**（新增 `LocalWriteHoldService.assertBusinessWritable`）：
  - `assertCompanyWritable`（本地运行域既有口径）：**失败关闭**，本机未初始化安装身份也拒绝；
  - `assertBusinessWritable`（本轮新增，供业务域调用）：本机**未启用本地运行部署**时按"无冻结"放行
    —— 该部署根本不具备本地备份／恢复能力，不存在恢复期冻结；若此时失败关闭会把既有业务写入整体打挂。
    本机已初始化时与 `assertCompanyWritable` 同口径（冻结期失败关闭）。

## 4. 并发与重启核对

| 维度 | 结论 | 依据 |
| --- | --- | --- |
| 冻结事实的持久性 | `local_write_hold` 落库 ⇒ **重启后仍可识别** | `LocalWriteHoldService.hold()` 写表；`listActive()` 读表 |
| 判定位置 | 判定只有一处（core 纯策略 `decideLocalWriteHoldVerdict`），事实层只取事实 | `core/local-runtime/policy/local-write-hold.policy.ts` |
| 守卫与恢复的互斥 | 恢复执行自身**先 hold 再写**（`local-restore-execution.service.ts`），业务守卫因此拒绝并发写入 | 编排层自持冻结 |
| 守卫是否误伤恢复自身 | 否：恢复写入走 `LOCAL_RESTORE_RECORD_WRITER` 端口（直接仓储），不经业务 usecase 守卫 | `modules/lithography/local-restore-record.writer.ts` |
| 守卫失败语义 | 失败关闭（抛 `DomainError(SYNC_ERROR.WRITE_HELD)` ＋ 受控原因码 `WRITE_HELD_FOR_RESTORE`） | `local-write-hold.service.ts` |
| 跨进程可见性 | 冻结事实在 DB，API 与 Worker 两个进程都读同一张表 ⇒ 跨进程可见 | `local_write_hold` 表 |

## 5. 本轮**未**冻结的写入口（保留清单，17 项）

下列入口写入的表**不在恢复整体替换范围**内（恢复不会覆盖这些行），本轮不冻结：

- 投稿域 5 项（`content_submission*`）：投稿表不在 14 张恢复表内；
- AI 会话域 4 项（`ai_conversation`／`ai_message`）：AI 表不在恢复范围；
- 后台 Worker 7 项（`ai-worker` 3、`ai-workflow` 2、`intake-analysis` 2）：
  `intake_analysis_attempt` 不在恢复范围，但其中**回写 `repair_request` 的那一条**
  （`consume-intake-analysis-job`）需在后续轮次补齐守卫；
- 账号与权限域 26 项、`local_upload_task`／`local_backup_run` 的**事实写入**若干：
  账号域属平台级（恢复期仍需可管理账号，否则恢复后无人能登录）；
  运行事实写入属本机元数据（由恢复编排自身持有）。

> 处置：**明确登记为遗留缺口**，不声称"全面停写"。下一轮按 `intake-analysis` 回写 `repair_request`
> 这一条优先补齐（这是剩余项中唯一会覆盖恢复范围表的入口）。
