## 2. 两个真实缺陷（本轮新发现并修复）

### 2.1 循环外键：任何删除顺序都会被挡住（G21 修复后才暴露）

`repair_request.intake_id → repair_request_intake.id` 与
`repair_request_intake.converted_request_id → repair_request.id` **互指**：

```
QueryFailedError: Cannot delete or update a parent row: a foreign key constraint fails
(`lithography_task09_dev`.`repair_request_intake`,
 CONSTRAINT `fk_repair_request_intake_converted_request`
 FOREIGN KEY (`converted_request_id`) REFERENCES `repair_request` (`id`) ON DELETE REST)
sql: DELETE FROM `repair_request` WHERE `owner_organization_id` = 4
```

**处置**（两处，缺一不可）：

1. **口径层**：`repair_request_intake` 的范围改为 `服务公司 ∪ 引用了本公司工单的行`
   ⇒ 清空工单行时，所有可能挡路的 intake 行都**同在恢复范围内**（会被一起删除并按备份载荷还原）。
2. **执行层**：清空前先**打断循环外键**——把"指向本次将被清空的工单"的
   `converted_request_id` 置空（`UPDATE repair_request_intake SET converted_request_id = NULL
   WHERE converted_request_id IN (SELECT … 本次范围内的工单)`）。
   被置空的行都在恢复范围内，随写回按**原值还原**（延后外键回填），业务事实不丢。
3. **写回层**：插入 `repair_request_intake` 时不带 `convertedRequestId`，
   待 `repair_request` 写入完成后按 intake 主键回填（`applyDeferredForeignKeys`）。

> 实现注意：备份载荷里的行是**实体实例**（`getMany()` 产出），属性名是**驼峰**
> （`convertedRequestId`），不是数据库列名——按列名去置空会**静默失效**（本轮已实测踩中并修正）。

### 2.2 载荷行是实体实例：外键列名口径必须用驼峰

第一版实现按数据库列名 `converted_request_id` 处理延后外键，
单测立刻失败（插入时仍带着 `convertedRequestId`）⇒ 证明"载荷行 ≠ 数据库行"。
已改为驼峰属性名，并在注释中固化该事实。

## 5. 旧包行为（明确取舍：拒绝，不静默丢数据）

范围扩大后，**2026-11-23 之前生成的旧包缺少 12 张子表**。
恢复侧 `checkScopeConsistency` 对"载荷缺少某父表的子表"**失败关闭**：

```
备份载荷缺少子表数据（maintenance_report_attachment），无法安全替换父表（maintenance_report）：
该备份包未包含报告版本等业务历史数据，恢复会丢失这些事实，请重新生成备份后再恢复
```

- **不兼容旧包**是刻意的：若兼容（只恢复有载荷的表），清空父表时旧子行会被删掉且**无法还原** ⇒ 静默丢数据。
- 拒绝路径已在单测中断言（`旧包（缺新增子表）⇒ 失败关闭，不静默丢数据`）。
- 清单**解析**层仍兼容旧包（`范围快照表较少仍可解析`）——只是**恢复执行**层拒绝。
- 影响面：**已落盘的旧包需要重新生成**才能恢复（PR 描述中须写明）。
