## 1. 缺陷现状（修复前）

### 1.1 调用链

| 阶段 | 入口 | 落库位置 |
| --- | --- | --- |
| 受理 | `local-backup.resolver.ts:169` → `AcceptLocalRestoreUsecase` → `BackupRestoreAcceptanceService.review` | `backup-restore-acceptance.service.ts:124` |
| 预检 | `local-backup.resolver.ts:229` → `PrecheckLocalRestoreUsecase` → `BackupRestorePrecheckService.execute` | `backup-restore-precheck.service.ts:126` |
| 执行 | `local-backup.resolver.ts:200` → `ExecuteLocalRestoreUsecase` → `LocalRestoreExecutionService.execute` | `local-restore-execution.service.ts` → `local-restore-record.writer.ts` |

### 1.2 事务边界的三处缺口

1. **写入器开了事务却不用**：`local-restore-record.writer.ts:347`
   `this.transactionRunner.run(async () => {...})` —— callback **没有形参**，
   未接收 `transactionContext`；`repositoryForTable()` 返回的是 `@InjectRepository` 注入的
   普通仓储 ⇒ 事务被打开，但 DELETE/UPDATE/INSERT 全在**事务外的默认连接**上自动提交。
   受影响的写库阶段共 6 处：清库（`:468`）、打断循环外键（`:541`）、写回（`:582`）、
   延后外键回填（`:598`）、抑制事实回填（`:522`）、原件绑定（`:308/:316/:322`）。
2. **恢复执行链没有事务边界**：`local-restore-execution.service.ts`、
   `execute-local-restore.usecase.ts`、`accept-local-restore.usecase.ts`、
   `backup-restore-acceptance.service.ts`、`backup-restore-precheck.service.ts`
   均**未注入** `TRANSACTION_RUNNER`。
3. **端口契约缺口**：`LocalRestoreRecordWriteRequest` 不带事务上下文字段
   （`local-restore-record-writer.contract.ts:38-57`）⇒ 编排层无法把上下文传到写入层。

### 1.3 失败与补偿现状

- `local-restore-execution.service.ts:251` `failAfterWrite` → `:367` `rollbackToProtection`
  用**保护副本再跑一遍完整恢复**（又一次清空＋写回），同样不在统一事务内；
- 回滚失败 ⇒ `LOCAL_RESTORE_ROLLBACK_FAILED` 并**保留冻结**（`:531` `failAndKeepHold`）✓；
- 写入器自身 catch 只对外给 `LOCAL_RESTORE_WRITE_FAILED`，**但事务内已发生的写不会回滚**
  （因不在事务 manager 上）。

## 2. 修复内容

### 2.1 写入器全程使用同一事务 `EntityManager`

- `repositoryForTable(table, transactionContext?)`：
  **有上下文时**用 `getTypeOrmEntityManager(ctx).getRepository(entity)` 取**事务内仓储**；
  无上下文时回落注入仓储（只读路径与离线装配用）。
  实体类型从注入仓储的 `target` 取，避免维护两套"表 → 实体"映射。
- 下列阶段全部改为在事务内执行：抑制事实读取 → 循环外键打断 → 逆序清除 → 正序插入
  → 延后外键回填 → 抑制事实回填。
- `transactionRunner` 缺席时**失败关闭**（不写任何业务行），保持原语义。

### 2.2 原件还原：先暂存字节，再在同一事务内绑定行引用

文件写入不可回滚，因此把"字节落盘"与"行引用变更"分开：

1. 第一步逐份核对包内字节（字节数 + SHA-256）并**暂存字节**，**不落行引用**；
2. 第二步把全部行绑定放在**同一事务**内：任一绑定失败 ⇒ 整体回滚 ⇒ 行引用不会停在
   "部分新、部分旧"的错配状态；字节已落盘但未被引用 ⇒ 只是孤儿文件，不构成数据不一致。

### 2.3 与既有机制对齐

事务上下文本就是仓内既有机制（`PersistenceTransactionContext` + `WeakMap` → `EntityManager`），
本轮沿用同模块同纪律的先例：`record-package-import.service.ts:79-101`
（`transactionContext ? getTypeOrmEntityManager(ctx).getRepository(X) : 注入仓储`）。

## 5. 已知边界与后续

1. **终态与审计事件仍在写入事务之外**：执行链顺序是"写回（事务）→ 逐表核验 → 终态事件 →
   解除冻结 → 终态 SUCCEEDED"。若在"写回提交"与"终态提交"之间被中断，终态会**诚实在 `RUNNING`**
   且**保留冻结**，可由运维重新执行收口（自检已验证"进程中断后重新执行可收口"），
   不会伪装成功。把终态并入同一事务需要扩展写入端口契约，属可选收敛项。
2. **文件与数据库非同事务**：字节写入不可回滚，采用"先暂存字节、再事务内绑定行引用"；
   绑定失败时以"该原件失败"上报并由上层走补偿（按保护副本回滚），不会留下"行指向不存在字节"。
3. **补偿路径本身也是整批替换**：`rollbackToProtection` 用保护副本再跑一次完整写回，
   现在该写回同样在事务内 ⇒ 补偿失败时不会留下半截数据。
4. `restoreOriginals` 的行绑定现在失败即整体回滚，**已写入但未被引用的字节成为孤儿文件**；
   本轮未实现孤儿字节回收（属后续清理项，不影响数据一致性）。
