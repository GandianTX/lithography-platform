### 2.1 中断取证为什么是"确定性的"

第一次实现时，父进程在子进程打印 `READY` 后立刻 `SIGKILL`，结果子进程**先跑完整个恢复**
（写入太快）⇒ 断言退化成"恢复成功后被杀"，证明不了"写入途中被杀"。

改进：子进程先在**独立连接**上执行
`SELECT … FROM repair_request WHERE owner_organization_id = ? ORDER BY id LIMIT 1 FOR UPDATE`
并**持有该事务**；恢复的 `DELETE FROM repair_request …` 会**阻塞在这条行锁上**。
父进程在 `READY` 后等待 1.5s 再 `SIGKILL` ⇒ 杀掉的瞬间**业务写入正在途中**。

为了让"未提交"与"半截提交"可区分，子进程在备份之后把**本公司全部工单**的
`fault_description` 改成 `MUTATED-AFTER-BACKUP`：
事务回滚 ⇒ 全部仍是标记值（`mutated=4 restored=0`）；整批提交 ⇒ 全部不是标记值；
半截 ⇒ 两者并存 ⇒ **断言失败**。

## 3. 新增实现："不复活删除下架"（R086）

### 3.1 问题

恢复采用"**整体替换**"策略 ⇒ 备份载荷里的旧行会覆盖当前行。
若某条工单在**备份之后**被删除，恢复会把备份时刻的"未删除"版本写回去 ⇒ **复活已删内容**，
违反 R086「不恢复旧Token停用权限旧等级，不复活删除下架」。

### 3.2 实现（当前事实优先）

- core 口径（`protected-backup.policy.ts`）新增逐表 `suppression` 声明：
  - `repair_request`：抑制指标 `deletedAt`（非空）／`deprecated`（非 0）；
  - `reference_document`：`deletedAt`／`deprecated`／`publicationStatus = 'OFFLINE'`（下架）；
  - `repair_request_intake`：`deletedAt`。
- 恢复写入层（`local-restore-record.writer.ts`）：
  1. 清库**之前**采集范围内**命中抑制**的行（整行实体快照）；
  2. 清库 ＋ 写回（按备份载荷）；
  3. 写回**之后**把命中的行按**恢复当下的整行事实**还原。

**为什么还原"整行"而不是几个列**：删除事实是**复合事实**。工单的库级 CHECK 要求
`chk_repair_request_deletion_consistency`（`deprecated = 1 ⇒ deleted_at 非空 且 is_accepted = 0`）
与 `chk_repair_request_acceptance_consistency`（`is_accepted = 0 ⇒ 接单人与接单时间为空`），
只还原部分列会**撞库级 CHECK**（本轮实测确实撞到，见 §5）。
整行还原既满足 CHECK，又保证"当前事实优先"。

### 3.3 语义边界（如实记录）

- 命中抑制的行：**当前事实优先**（删掉的仍删掉、下架的仍下架）。
- **未**命中抑制的行：完全按备份载荷写回（业务状态仍是备份时刻的事实）。
- 备份之后**新建又删除**的行不在载荷内 ⇒ 随恢复一起消失（恢复＝回到备份时刻），
  但**不会以"未删除"形态复活** ✓。

## 4. 新增取证："现有权限凭据不被旧包复活"

`local_account_authorization`（本机授权：账号 × 公司 × 用途 × 授权状态 × 权限版本）
**不在受保护备份范围**内 ⇒ 恢复不触碰任何授权行。
实库断言：恢复前后授权表指纹完全一致（`before=3:5758261711 after=3:5758261711`）。

同理，旧 Token／旧等级／旧撤权状态也不在载荷内；授权续期只带白名单材料
（既有实现 `local-authorization-renewal.policy`）。
