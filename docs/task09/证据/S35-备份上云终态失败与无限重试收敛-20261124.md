# S35 · 备份上云终态失败与无限重试收敛（任务 09 第 10 项 · L2 闭合）

- 日期：2026-11-24
- 分支：`feat/task09-local-backup-restore`
- 实测环境：MySQL 8.0.46 / `env/.env.e2e` → 隔离库 `lithography_task09_test_e2e`
- 入口：`backend/scripts/task09-cloud-real-chain.ts`（受控云替身＝本机真实 HTTP）

## 0. 结论速览

| 项 | 结论 |
| --- | --- |
| 缺口来源 | `S33` §6 **L2**：「超限的备份包会持续按退避重试且始终失败（未新增终态／未改重试策略）」 |
| 缺陷性质 | **确定性失败被当成瞬时故障**：同一份备份包一旦生成即不可变，超限／清单不一致／清单不可读是**本机事实**决定的必然结果，重试多少次都撞同一道闸门 |
| 生产后果 | 资产行永远停在 `FAILED` 且**每轮都被重新捞出重试**（退避 5→10→…→60 分钟封顶）：既烧资源又**永不收敛**；运维看到的也只是"又失败了" |
| 修复 | 引入**终态失败**分类：本机包结构性失败 ⇒ 受控原因码标记为终态 ⇒ 重试链**不再捞取**，尝试次数冻结 |
| 结果 | 云真实链 **35 → 40 断言全绿**；**敏感性反证**确认修复前如实失败（`attemptCount` 从 1 涨到 2） |
| 未动 | 已接受基线迁移**零修改**（不新增状态枚举、不改 CHECK）；远端类失败的终态语义**不臆造**（见 §3.2） |

## 1. 缺陷复现（修复前）

合成一个**超出上传大小上限**的备份包（生成真实本机包 → 把清单里某一件的**声明字节数**改成远超任何上限的值
→ 同步更新资产行的清单摘要，使"上限闸门"先于"清单摘要闸门"命中）：

| 观察点 | 修复前 | 期望 |
| --- | --- | --- |
| 第一轮上传后资产状态 | `FAILED`，`failureReason=CLOUD_PACKAGE_TOO_LARGE` | ✔ 受控原因码本就保留 |
| 第二轮（+24 小时，远超任何退避到期） | **再次被尝试**，`attemptCount` 1 → 2 | 终态资产不应被再次尝试 |
| 长期行为 | 每轮都被捞出重试，**永不收敛** | 应停止重试 |

> 敏感性反证（本次实测）：把终态判定临时短路后重跑，断言
> 「超限包：第二轮不再尝试」**如实失败**（`attemptCount=2 (第一轮 1)`），
> 证明该缺陷真实存在、且新断言能区分修复前后。

## 2. 修复

### 2.1 终态分类（纯裁决）

`backend/src/core/local-runtime/policy/local-backup-cloud-upload.policy.ts` 新增：

- `CLOUD_UPLOAD_TERMINAL_FAILURE_CODES`：`CLOUD_PACKAGE_UNREADABLE`／`CLOUD_PACKAGE_INCOMPLETE`／`CLOUD_PACKAGE_TOO_LARGE`；
- `decideCloudUploadFailureDisposition(code)` → `'TERMINAL' | 'RETRYABLE'`；
- `isTerminalCloudUploadFailure(code)`。

三者的判定依据**全部来自本机自己的事实**（清单缺失／不可解析／摘要不符／清单与字节对不上／超出上限），
与云端如何响应**无关** ⇒ 属于本仓可自行判定的终态。

### 2.2 重试链尊重终态

`backend/src/core/local-runtime/policy/local-backup-upload.policy.ts`：

- `BackupUploadDecisionInput` 新增 `failureReason?: string | null`；
- `decideBackupUploadAttempt()` 的裁决顺序改为
  **开关关闭 → 授权失效 → 不可重试 → 已成功 → 终态失败 → 退避到期**，
  命中终态返回 `{ action: 'SKIP', reason: 'TERMINAL_PACKAGE_INVALID' }`。

`backend/src/modules/lithography/local-backup-upload.service.ts`：
把资产行上已有的 `failureReason` 传入该裁决（资产行是**跨轮次**的事实载体，
因此终态标记天然跨轮次生效，不需要新增状态枚举或改 CHECK）。

### 2.3 为什么不改数据库 CHECK

`chk_backup_asset_cloud_status` 定义在 **`1775501500000-create-backup-and-audit-for-v13.migration.ts`**，
该迁移属于**已接受基线**（本 PR 新增的只有 5 条其它迁移）。按仓库规则
「不修改已接受基线迁移」，若要新增 `REJECTED` 状态就得再写一条改 CHECK 的迁移。
本轮**选择不改 schema**：终态由**受控原因码**承载，资产状态仍是 `FAILED`，
但尝试次数冻结、重试链不再捞取——**运维可见的终态语义与新增状态枚举等价**，
且不触碰已接受基线、不引入迁移风险。

## 3. 边界（明确不做 / 不臆造）

### 3.1 本机包结构性失败 ⇒ 终态（本轮已做）

| 受控码 | 含义 | 处置 |
| --- | --- | --- |
| `CLOUD_PACKAGE_TOO_LARGE` | 超出单件／整包大小上限 | **终态** |
| `CLOUD_PACKAGE_INCOMPLETE` | 清单登记与包内字节不一致 | **终态** |
| `CLOUD_PACKAGE_UNREADABLE` | 清单缺失／不可解析／摘要不符／原件目录读不到 | **终态** |

### 3.2 远端类失败 ⇒ 暂定可重试（**不臆造生产协议**）

`CLOUD_REJECTED`（4xx）与 `CLOUD_INVALID_RESPONSE`（回包形态非法）到底是终态还是可重试，
取决于**生产接收端**的真实语义：4xx 可能是"包被判定不合规"（终态），
也可能是"配额已满，稍后重试"（可重试）。在生产协议（G4／G5）落地前无法判定，
因此本轮**保守按可重试**处理，并在生产联调时按云端事实调整。

> 与业务同步链的差异：业务同步链按 4xx 终态处理（该链已冻结的口径，D8）。
> 两链差异**待联调统一**，此处如实登记，不静默抹平。

### 3.3 仍然保留的取舍

- **L1**（备份包整读进内存再组 multipart）：**未做**。上限已把"失控"降级为"受控失败"；
  彻底消除需改为流式 multipart（改动面覆盖 uploader/client 的 multipart 契约，属另一议题）。
- **L3**（业务同步链总量上限在读取过程中累计）：**已满足**"读取过程中判定"，
  内存峰值受总量上限约束，非缺陷，无需改动。

`runOversizePackageTerminalScenario()`，**35 → 40 断言全绿**：

| 断言 | 结果 |
| --- | --- |
| 超限包：按失败处理并保留受控原因码（不得抹平成"上传失败"） | ✅ `cloudStatus=FAILED reason=CLOUD_PACKAGE_TOO_LARGE` |
| 超限包：云端没有收到该包（不得上传半截或跳过闸门） | ✅ `packages=3`（未增长） |

| 超限包：第二轮不再尝试（终态，不按退避无限重试） | ✅ `attemptCount=1 (第一轮 1)` |
| 超限包：同一轮里其它可重试资产仍在重试（证明本轮不是空转、断言有效） | ✅ `round attempted=4 skipped=10` |

> 因此不能用整轮 `attempted` 计数判断本资产是否被重试（首版断言过严，已修正为资产级断言并加反证）。
