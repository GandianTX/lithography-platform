## 3. 修复的三个生产缺陷（均只在真实库上暴露）

### 3.1 预检写库违反 CHECK ⇒ 恢复链完全不可用（P0）

- **现象**：`Check constraint 'chk_backup_restore_run_execution_guard' is violated`（预检事实写入时）。
- **根因**：库级 CHECK 规定
  `status='PENDING'` ⇒ `protection_backup_id IS NULL AND confirmation IS NULL`；
  但预检在写入 PENDING 事实时**带上了保护副本 id**（保护副本已在预检阶段真实生成）。
- **影响**：**预检在真实库上必然失败** ⇒ 受理与执行都无从谈起 ⇒ 整条恢复链不可用。
- **修复**：预检写入 PENDING 行时 `protection_backup_id` 置空，保护副本标识随**快照**
  （`snapshot.protection.backupId`）落库；受理阶段从快照解析标识，并在
  **PENDING → RUNNING** 的状态迁移里把它写进本列（RUNNING 行本就要求带该列，符合 CHECK）。
- **回归**：真实库预检由"必然失败"变为 `outcome=PASSED`，受理 `accepted=true`。

### 3.2 失败落库违反 CHECK ⇒ "失败保持冻结"落不了库（P0）

- **现象**：`Check constraint 'chk_backup_restore_run_check_outcome' is violated`（失败路径）。
- **根因**：该 CHECK 规定终态 `FAILED`／`INTERRUPTED` 的行**不得**带核对结论
  （`check_status` 必须为空）；失败路径只写了 `status/finished_at`，把预检结论 `PASSED` 留在行上。
- **影响**：恢复一旦失败，**连"失败"这个终态都写不进库** ⇒ 冻结状态与事实都悬空。
- **修复**：失败落库时同时清空 `check_status`（核对结论仍完整保留在 `check_snapshot` 里）。
- **回归**：失败场景断言由"抛异常中断"变为 `status=FAILED holdRetained=true`。

### 3.3 清库路径误用 SELECT 别名 ⇒ 恢复写入必然失败（P0）

- **现象**：`Unknown column 't.document_id' in 'IN/ALL/ANY subquery'`。
- **根因**：恢复写入的"清空"阶段用 `DELETE` 执行，却复用了 `SELECT` 的表别名 `t`
  （`DELETE FROM x WHERE t.document_id IN (...)` 里没有 `t` 这个别名）。
- **影响**：清库阶段在真实库上必然报错 ⇒ 恢复写入整体不可用。
- **修复**：范围过滤按"有无别名"参数化——`SELECT` 用别名，`DELETE` 用**裸列名**。
- **回归**：错误消失，写入推进到下一步（暴露 §4 的结构性缺口）。

## 4. 未闭合的结构性缺口（G21）：备份范围未覆盖带外键的子表

- **现象**（写入阶段的真实报错）：
  `Cannot delete or update a parent row: a foreign key constraint fails
  (maintenance_report_review, CONSTRAINT fk_maintenance_report_review_version
  FOREIGN KEY (version_id, report_id) REFERENCES maintenance_report_version (id, …))`
- **根因**：恢复采用"**先按公司数据区清空、再按清单写回**"的整体替换策略，
  但**备份范围只有 14 张表**；指向这些表的**子表**里，有 9 张不在范围内，
  于是清空父行时被这些残留子行挡住：

  | 范围外子表 | 指向（父表） | 外键列 |
  | --- | --- | --- |
  | `maintenance_report_review` | `maintenance_report_version` | `version_id` ＋ `report_id` |
  | `reference_document_case_detail` | `reference_document` | `document_id` |
  | `repair_process_entry` | `repair_request`（另指向 `stored_file`） | `request_id`／`file_id` |
  | `repair_request_diagnostic_step` | `repair_request` | `request_id` |
  | `repair_request_fault_panel` | `repair_request` | `request_id` |
  | `repair_request_intake` | `repair_request`（`converted_request_id`，可空） | `converted_request_id`／`file_id` |
  | `ai_conversation` | `repair_request`（可空；自身有 `owner_organization_id`） | `request_id` |
  | `ai_report` | `repair_request` | `request_id` |
  | `engineer_response` | `repair_request` | `request_id` |

- **为什么不能"顺手清掉"**：这些表承载真实业务事实（工程师回复、AI 会话、报修原始输入、排查步骤…）。
  恢复时清空却不备份 ⇒ **数据丢失**，比"恢复失败"更糟。
- **为什么本轮没有直接修**：修复口径＝**把这 9 张表纳入备份／恢复范围**，
  需要同时改：core 的范围描述符与外键顺序、备份侧的表→仓储映射、
  恢复写入侧的表→仓储映射与清空顺序、以及断言范围表清单的既有单测。
  这是一次**结构性变更**，牵动面大，本轮工期不足，**不做半成品**。
- **修复方案（下一轮可直接执行）**：
  1. 在 `BACKUP_TABLE_DESCRIPTORS` 补 9 条范围口径：
     `maintenance_report_review`／`reference_document_case_detail`／
     `repair_process_entry`／`repair_request_diagnostic_step`／`repair_request_fault_panel`／
     `ai_conversation`（自身有 `owner_organization_id` ⇒ `OWNER_ORGANIZATION`）／
     `ai_report`／`engineer_response` 走 `PARENT_OWNER_ORGANIZATION`（父表 `repair_request`），
     `repair_request_intake` 走 `converted_request_id` 口径（可空 ⇒ 需单独确认范围列）；
  2. 在 `BACKUP_RESTORE_TABLE_ORDER` 按**外键顺序**插入（子在前、父在后；
     `maintenance_report_review` 必须在 `maintenance_report_version` 之后）；
  3. 备份侧与恢复写入侧各补 9 条「表 → 仓储」映射与实体注入；
  4. 复跑本自检脚本：**11 项断言应全绿**（脚本已就位，可直接当验收闸门）。
