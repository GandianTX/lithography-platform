## 2. 恢复执行编排

`modules/lithography/local-restore-execution.service.ts` ＋ `usecases/local-runtime/execute-local-restore.usecase.ts`
＋ GraphQL `executeLocalRestore`（管理员专属）：

```
受理事实 → 写传冻结 → 按清单恢复（业务数据走中立受控端口 / 本机运行数据直写）
        → 核验（逐表行数由来源域给出）→ 解除冻结
```

- 三道闸门真实参与裁决（`restore-execution-capability.policy`）：**写入闸门**、**回滚补偿**（保护副本仍在）、**解密材料**。
- **失败保持冻结**：不解除冻结、不删保护副本与任务、终态写回受控原因码；
  冻结落库 ⇒ **重启后仍可识别**（S5-3）。
- 业务数据写入经**中立端口** `LOCAL_RESTORE_RECORD_WRITER`；**未注册即失败关闭**（恢复编排不直接写业务表）。

## 3. 本轮抓到并修复的 3 个真实缺陷

| # | 缺陷 | 影响 | 修复 |
| --- | --- | --- | --- |
| D1 | 恢复**受理**只写 `confirmation` 不改状态 | 违反 `chk_backup_restore_run_execution_guard`（PENDING 行 `confirmation` 必须为空）⇒ **真实库上受理必然失败** | 受理即进入 `RUNNING`（带 `started_at` ＋ `protection_backup_id`），状态机自洽 |
| D2 | 迁移里表名用模板变量 `` `${TABLE}` `` | 迁移诊断器按字面量解析"应创建的表"⇒ 误报"结构缺失" | 建表语句内联**字面量**表名 |
| D3 | schema 契约未登记新表对象 | 迁移**前置校验**失败（外键/索引要求缺失、CHECK 漂移） | 登记表、索引、外键（含 `REQUIRED_FOREIGN_KEYS`／`REQUIRED_INDEXES`）；CHECK 因 MySQL 归一化差异不纳入关键清单 |
