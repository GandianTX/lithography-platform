# S26 · 「保留本地」资料等可写资源支持（第 05 项 · P1-5／G10）

> 日期：2026-11-24
> 范围：任务 09 第 05 项「资料等可写资源『保留本地』（P1-5、G10）」
> 结论：**需求内可写资源（资料）不再因缺实现直接拒绝**；无权与只读仍安全；报告按只读显式拒绝并给出依据。

| G10-4 | **跨域边界不存在**：usecase 跨域依赖被架构守卫禁止（`no-cross-domain-usecases-imports`） | `backend/eslint.config.mjs` | 真实缺口 |

于是工单分支在真实链上会被自己的受控入口拒掉——即「保留本地」这条路径此前**实际不可用**。

## 2. 口径冻结（按 R067 明确三类资源的可写状态与真实角色）

| 资源 | 可写状态（只读口径） | 真实可写角色（来源资源事实） | 「保留本地」裁决 |
| --- | --- | --- | --- |
| 工单 `REPAIR_REQUEST` | 未删除／未下架／未冻结／未结单 | **管理员**（`SUPER_ADMIN`；一级全公司／二级本公司 ＋ 记录级可见性 ＋ 版本条件 ＋ 状态机校验）；**接单工程师与客户不改正文** | 已支持（本轮补留痕型修订，修掉 G10-5） |
| 资料 `REFERENCE_DOCUMENT` | `ONLINE` ＋ `CONFIRMED` ＋ 未软删 | **一级管理员**（资料正文修订；`admin_level=1`）；工程师／记录人对正式资料**只有删除权、没有正文修订权** | **本轮新增**（经中立契约调用来源域受控写入） |
| 报告 `MAINTENANCE_REPORT` | 正式态冻结（`SUBMITTED`／`PENDING_REVIEW` 不可反写、`APPROVED` 只读） | **仅作者本人在 `DRAFT`／`RETURNED` 自写**；管理员只有审核动作 | **显式拒绝**（逐条依据见 §3.3） |

**不按管理员身份替代**：LOCAL 的写权一律由**来源资源的受控入口**裁决——
资料正文修订只对一级管理员开放 ⇒ 二级管理员与工程师在资料分支被**受控拒绝**（`INSUFFICIENT_PERMISSIONS`），
而不是"LOCAL 是管理员动作所以一律放行"。

## 3. 修复内容与设计取舍

### 3.1 core 纯策略：载荷映射与资源准入（单一口径）

- `LOCAL_RESOLUTION_SUPPORTED_RESOURCE_TYPES` 扩展为 `['REPAIR_REQUEST','REFERENCE_DOCUMENT']`；
- 载荷改为**按资源类型区分的联合类型**（不共用一张大表）：
  - 工单：`content_md`／`handling_result`／`closure_reason`／`maintenance`（口径不变）；
  - 资料：`title`／`description`（**正文 `content_text` 不进载荷**）。
- 资料字段名取业务同步 body 的 **snake_case**（`business-sync-source.service.ts` 的资料分支正是这个形态），
  与 CLOUD 对齐分支的白名单一致；类型非法拒绝、空串按"没有该字段"。

**取舍：资料正文不反写。** 「保留本地」要保留的就是本地正文本身；
资料的生效正文可能来自**冻结的维修报告版本**（`source_kind` 指向报告），
用快照里的资料自身正文覆盖会让读侧回退到自身正文、丢掉冻结报告正文。
因此写入只落标题／说明，修订历史的前后快照沿用**当前生效正文**。

### 3.2 中立契约：跨域边界（G10-4）

- 新增 `backend/src/usecases/common/ports/sync-conflict-local-resolution-writer.contract.ts`
  （`SYNC_CONFLICT_LOCAL_RESOLUTION_WRITER`），与既有 `SYNC_CONFLICT_LOCAL_VIEW_WRITER`（CLOUD 对齐）同构；
- 实现在来源域：`backend/src/modules/lithography/sync-conflict-local-resolution.writer.ts`
  （行锁 → 不可用／只读守卫 → 版本条件 → 条件推进 `current_revision_no` ＋ 追加修订历史行）；
- 编排层只做裁决与事务边界，**不直接改业务行**；契约未注册即失败关闭。

### 3.3 报告为什么保持只读（逐条依据）

1. **没有受控修订入口**：报告域全部写入口都是作者本人在 `DRAFT`／`RETURNED` 的草稿工作流
   （`create/update/submit/approve/return…`），没有"按外部载荷写入报告正文"的入口；
2. **没有通用修订历史表**：只有 `maintenance_report_version`（提交时冻结的版本快照，不可变），
   不是任意修订历史，无法承载"裁决留痕"；
3. **状态即冻结**：`SUBMITTED`／`PENDING_REVIEW` 不可反写、`APPROVED` 只读（`sync-source-record.query.service.ts` 的 `toReportFact`）；
4. **写权归属不同**：管理员只有审核动作，不能改正文（`assertMaintenanceReportReviewRole`）。
   ⇒ LOCAL 对报告**显式拒绝**（`LOCAL_RESOLUTION_RESOURCE_UNSUPPORTED`），并已实测（V9）。

### 3.4 工单分支：留痕型修订开关（G10-5）

- 受控修订入口新增**可选** `allowUnchangedContent`（默认 `false` ⇒ 管理员手工修订的既有语义完全不变）；
- 仅「保留本地」显式开启：要保留的对象本来就是本地当前内容，内容不变是必然结果，
  但业务上必须留下可追溯的修订历史行（谁、何时、为何保留本地）。
- "无变化"判定抽成模块级纯函数 `isRevisionNoop`，不改变既有判定口径。

### 3.5 编排层的裁决边界

| 边界 | 实现 |
| --- | --- |
| 管理员动作门 | 沿用管理员文档库域口径（`SUPER_ADMIN` ＋ activeRole） |
| 公司范围 | 一级全公司／二级本公司（沿用 admin 域范围口径，裁决在 core 纯函数） |
| **同公司记录** | 资料归属公司必须等于冲突登记公司（一级管理员也不例外），否则按不存在同码失败 |
| 写权 | 资料分支＝一级管理员（core 单一口径 `assertFirstLevelAdminWriteAccess`，与资料域共用） |
| 并发版本 | 冲突登记的本地版本必须等于来源当前版本；来源版本已被推进 ⇒ 拒绝 |
| 只读 | 已删除／下架／冻结／结单一律受控拒绝（`CONFLICT_SOURCE_READ_ONLY`） |
| 幂等 | 冲突行 `local_resolution_state`（`WRITING`／`WRITTEN`）＋ 条件更新；资料分支**修订与 decision 同事务** |

## 6. 已知边界与遗留

1. **V8 未在隔离库实测**：库中没有二级管理员账号（已如实标注跳过）；该分支由单测覆盖
   （`apply-local-sync-conflict-resolution.usecase.spec.ts` 的"二级管理员受控拒绝"用例）。
2. **资料的「保留本地」不改正文**：这是语义取舍（本地正文即保留对象，且不得覆盖冻结报告正文）；
   若后续产品要求"裁决后生成一条新的正式资料版本正文"，需另行设计并走资料域结构化修订入口。
3. **工单分支仍沿用 review M7 的三段事务**（受控修订入口自持事务），
   资料分支已做到"修订 ＋ decision 同事务"；两条路径的差异已在本文件与代码注释中写明。
4. **资料 revision 0 的记录不产生冲突**（同步候选要求 `current_revision_no > 0`），
   因此 LOCAL 的"版本必须 ≥1"口径在真实链上不会挡住资料；该口径与 CLOUD 对齐分支保持一致，未擅自放宽。
5. **前端未改**：「保留本地」按钮的可用性由服务端 `sourceReadOnly` 决定，
   资料类型已有来源页路径（`/reference-documents/:id`），本项未新增前端入口。
6. **G10 状态**：原「未完成内容清单」中的 G10（"保留本地未覆盖资料／报告"）**已闭合**：
   资料＝可写且已实测；报告＝按正式需求只读并逐条给出依据、已实测拒绝。
