## 2. 修复内容

### 2.1 收尾门禁（`task09-restore-selfcheck.safety.ts` 新增）

门禁是**只前进、不回退**的显式状态，每一阶段必须**真实通过**才推进：

| 阶段 | 含义 | 允许的动作 |
| --- | --- | --- |
| `authorized` | 入口授权 + 受控文件根已确认 | 只允许清理本轮临时文件 |
| `identityVerified` | 实例身份／一次性库标识／安装与公司／账号成员关系核对通过 | 追加：允许释放冻结 |
| `scopeVerified` | 范围预检通过（无他人活动冻结、既有授权未被覆盖） | 追加：允许释放冻结 |
| `baselineComplete` | **全部**受控表的主键基线快照成功 | 追加：允许删除本轮数据库对象 |

对应纯逻辑：`assertFileCleanupAllowed` / `assertHoldReleaseAllowed` /
`assertDatabaseCleanupAllowed`。**旧实现的 `finally` 无条件清理已被彻底移除**：
门禁未通过的分支只会"关闭连接 + 清理本轮明确创建的临时文件"，并把
"库中可能仍有本轮对象残留，需人工核对"写进回执（退出码非零，不可见的失败被消除）。

### 2.2 所有权登记取代全表差集

删除集合不再由"全表 after \ before"推断，而是来自两类**可核对的事实**：

1. **本轮登记的真实主键**：备份／恢复／冻结／公司设置／授权／审计事件
   （生产操作返回什么就登记什么，含"本轮造数"时改写过的关键字段）；
2. **由本轮恢复 ID 反查到的父子行**：
   - 恢复运行行的 `backup_id` / `protection_backup_id`；
   - 预检快照 `snapshot.protection.backupId`（**PENDING 行该列恒为空**，只看列会漏）；
   - 备份资产行的 `run_id` / `local_cleanup_run_id`（**父行**，漏登记即残留）；
   - 带本轮 `restore_id` 的冻结行；
   - `operation=RESTORE_LOCAL_BUSINESS` 且 `target_id` 指向本轮恢复的审计事件。

关键字段（安装标识／公司／父行）作为 `expectedFields` **登记在案**，删除前在
**同一事务内逐条读回真实行比对**，不一致即整体回滚（`OWNED_OBJECT_MISMATCH`）。

### 2.3 失败关闭与同事务预检

- 基线缺任何一张表 ⇒ `BASELINE_INCOMPLETE`，**禁止**删除（不再有空集合回落）；
- 登记为"本轮创建"却**运行前已存在**的主键 ⇒ `OWNED_OBJECT_PREEXISTED`，拒绝删除；
- 删除前在**同一事务**内：逐条核对关键字段 → 外部引用预检（`EXTERNAL_REFERENCE`）
  → 先子后父删除；任一不符 ⇒ 整体回滚；
- 删除后核对：本轮对象已清空、**运行前已存在对象仍在**；
- 非本轮新增行（并发写入）**保留不删**，并作为"未归属新增行"写进回执、退出码非零。

### 2.4 哨兵

- 基线快照**前移**到哨兵建立之前：哨兵不再"进基线后永不清理却称零残留"；
- 只回收**本轮确实创建**的哨兵（复用到的既有哨兵不回收、不冒充本轮对象）；
- 哨兵核对（前后指纹一致）先于回收执行，回收发生在核对之后。

## 5. 过程中发现的真实口径差异（已登记，供后续计划参考）

1. **保护副本资产的 `installation_id` 恒为 `00000000-0000-4000-8000-000000000000`**：
   `protected-backup.service.ts` 写的是真实安装标识，但"异机拒绝"场景刻意把资产改成
   外来值以验证预检拒绝。删除前核对因此必须认**本轮登记过的改写值**，
   否则会把合法行当成串号而拒绝删除（脚本用 `ownedBackupInstallationOverrides` 登记）。
2. **恢复终态审计事件的真实分类是 `operation=RESTORE_LOCAL_BUSINESS` /
   `target_type=LOCAL_RESTORE`**（不是 `BACKUP_RESTORE_RUN`；后者只出现在单元测试夹具里）。
   所有权推导按真实口径取，否则终态事件会变成未归属残留。
3. **预检被拒时保护副本标识只落在快照里**：库级 CHECK 约束要求 PENDING 行
   `protection_backup_id` 为空 ⇒ 必须同时读 `check_snapshot` 才能取到保护副本。

> 另有一处**本轮自引入又已修掉**的缺陷：为满足 lint 的 `no-base-to-string` 曾把
> 主键读取收窄为"只认 string"，而 MySQL 驱动对 BIGINT 主键返回 number
> ⇒ 12 条备份运行父行漏登记（变成未归属残留）。已改为统一的 `toIdText`
> （string / number 都接受），并复跑确认 43 个对象全部回收。

## 6. 已知限制

1. **失败运行会留下本轮对象**：门禁未过时按计划**禁止**数据库删除，因此失败运行会在
   隔离库里留下本轮对象与"超管授权行"，后续运行会因"目标范围已存在授权行"而拒绝。
   这是**计划要求的方向**（宁留勿删），代价是失败后需要人工核对清理（回执已明确提示）。
2. 隔离库账号无 SUPER，无法用触发器制造删除失败，C4 改用**外键守卫表**实现同等语义。
3. 目录级递归删除目前只有 `task09-identity-counterexample-matrix.ts` 一处，
   本轮已补路径守卫；其余脚本的文件删除均为"受控根内按清单删除"。
