### 2.3 本项在此发现的缺陷：演练夹具未适配 49 基线（已修）

**首次跑 ② 失败**：`❌ 空库 migration 演练失败: Field 'publication_status' doesn't have a default value`。

- 根因：`verify-empty-db-migrations.ts` 的 `insertLegacyUpgradeFixtures()` **只判定了 `owner_organization_id` 是否存在**，
  随后按固定列清单写入 `reference_document`。而迁移 `1775501100000`（基线内）把
  `publication_status`／`ownership_status`／`source_kind` 收紧为 **NOT NULL 且无默认值**，
  于是夹具在基线 ≥ 该点时**必然写入失败**。
- 影响：**本 PR 的真实基线（49）根本无法被演练覆盖**；既有 npm 脚本 `migration:drill:upgrade` 固定
  `MIGRATION_DRILL_BASELINE_COUNT=14`，因为 14 早于该收紧点，所以一直"绿"——**绿灯掩盖了真实基线不可测**。
- 修复（`backend/src/infrastructure/database/verify-empty-db-migrations.ts`）：
  夹具改为**按实际存在的列**构造 INSERT（新增 `readExistingColumns()` + `readText()`），
  逐列按 CHECK 语义补值：`publication_status='ONLINE'`、`ownership_status='CONFIRMED'|'PENDING'`（无归属组织时取 PENDING）、`source_kind='MATERIAL'`。
- 修复后：②③ 全绿，且 **14 基线回归仍绿**。

## 3. 历史 ACTIVE 冲突：合成隔离数据实测（本项发现并修复 1 处缺陷）

### 3.1 口径来源

计划第 12 项第 2 点：「若需要历史 ACTIVE 冲突样例，用合成隔离数据验证修复／失败关闭，不能操作真实旧库。」

事实基础：`local_write_hold` 的范围索引 `idx_local_write_hold_scope` **不是唯一索引**
⇒ 同（本机安装 × 公司）可以并存多条 ACTIVE 冻结（这正是旧实现"先查后写"并发下的遗留形态）。
`core/local-runtime/policy/local-write-hold.policy.ts` 的既定口径是：
同范围多条 ACTIVE ⇒ **无法判定归属 ⇒ 失败关闭，不静默挑一条**。

### 3.2 实测脚本

新增 `backend/scripts/task12-write-hold-active-conflict-check.ts`：
默认拒绝（需 `TASK12_ACTIVE_CONFLICT_ALLOW=1`）＋ 目标库名必须含 test/drill/ci；
作用域取库内**真实存在的隔离测试组织** `PEER_ALT`（外键要求），并要求该范围**当前无任何冻结**；
只写本轮创建的合成行，**按精确 `hold_id` 回收**，非目标行不动。

### 3.3 缺陷：`forceReleaseForRecoveryIncident` 的归属判定取到了无关行（已修）

**修复前的实现**（`local-write-hold.service.ts`）：

```ts
const verdict = decideWriteHoldReleaseVerdict({
  ownerRestoreId: active[0]?.restoreId ?? null,   // ← 取范围里的任意一行
  requestedRestoreId: input.incidentRestoreId,
  hasActiveHold: active.length > 0,
});
```

**复现**（合成两条并存 ACTIVE，分别属 `restore-A`／`restore-B`）：

| 场景 | 修复前实测 | 期望 |
| --- | --- | --- |
| 本人持有者**排在前面** | 释放成功（released=1） | ✅ 一致 |
| 本人持有者**排在后面** | ❌ **被误拒**：`RELEASE_NOT_PERMITTED_NOT_OWNER`，提示"该恢复期冻结由其它恢复持有（restore-B）"，released=0 | 本人应能释放自己那条 |
| 声明一个**并不持有**该范围的恢复 ID | ✅ 被拒、零释放、两条保持 ACTIVE | ✅ 一致 |

**生产后果**：历史库遗留多条并存 ACTIVE 冻结时，恢复现场运维**无法解除自己持有的那条**
⇒ 该公司数据区**永久停写**，只能人工改库；且行为随数据库返回行序**翻转**（不可解释、不可复现）。

**修复**：
- `core/local-runtime/policy/local-write-hold.policy.ts` 新增纯裁决 `decideIncidentForceReleaseVerdict()`
  —— 归属判定只看**请求方自己持有的条数**（与行序无关），为 0 ⇒ 失败关闭（`RELEASE_NOT_PERMITTED_NOT_OWNER`）；
- `local-write-hold.service.ts` 的 `forceReleaseForRecoveryIncident()` 改为按
  `restore_id = incidentRestoreId` 过滤出**自己持有的行**后释放（释放动作本来就按该条件 UPDATE，
  别人的冻结**永远不受影响**）。

### 3.4 修复后结果

- 实库脚本：**9/9 通过**（S1 结构可表达历史冲突 / S2 冻结期写入被拒 / S3 建立冻结失败关闭 /
  S4 按归属释放只解自己那条 / S5 本人排序在前可释放 / S6 声明不持有者被拒且零释放 /
  S7 **本人排序在后也可释放** / 收尾零残留）。
- 定向单测：`local-write-hold.policy.spec.ts` ＋ `local-write-hold.service.spec.ts` **24/24 通过**
  （新增策略 4 例 + 服务 3 例，含"两种行序口径一致"与"不得按范围一刀切"）。
- 收尾核对：`local_write_hold` 表 **0 行残留**（本轮合成 4 行全部按精确 `hold_id` 回收）。
