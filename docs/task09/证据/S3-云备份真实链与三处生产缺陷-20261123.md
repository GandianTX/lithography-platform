## 1. 为什么用"受控云替身"而不是"单测替身"

任务书允许"生产云地址或凭据缺失时完成受控替身和生产适配可做部分，真实联调标未验证并记录提供方"。
本轮据此落地一个**受控云替身**：它是**本机真实 HTTP 服务**（`node:http`，随机端口），
扮演云端协议对端；而链路的其余部分全部走生产代码路径：

| 环节 | 谁执行 |
| --- | --- |
| 本机生成受保护包（组包 ＋ AES-256-GCM ＋ 清单自校验 ＋ 原件复制） | **生产代码**（`ProtectedBackupService`） |
| 凭据与用途判定（独立用途、可核验才可用） | **生产代码**（`hasCredentialPurpose` ＋ `decideBackupUploadAttempt`） |
| 上云请求（multipart 组包、请求头、字节读取） | **生产适配**（`HttpLocalBackupUploader` ＋ `HttpLocalBackupCloudClient`） |
| 回执形态校验与落库 | **生产代码**（`parseUploadReceipt` ＋ `LocalBackupUploadService`） |
| 清理授权判定与本机包删除 | **生产代码**（`findManualRunCloudReceipt` ＋ `cleanupManualPackages`） |
| 云端清单与下载 | **生产适配**（`HttpLocalBackupCloudProvider` ＋ 两个用例） |
| **只有"云端对端"是替身** | 收包、给回执、列包、给字节、故障注入 |

断言全部落在**真实副作用**上：DB 行的状态字段、**本机磁盘上包目录是否真的消失**、
云端是否**真的收到字节**（`received=21569B`）、下载字节数。

## 2. 协议（与生产适配一致，云端照此实现即可）

| 方向 | 约定 |
| --- | --- |
| 上云 | `POST {baseUrl}/backup-packages`，`multipart/form-data`：字段 `backupId`／`organizationId`／`installationId`／`manifestChecksum`／`byteSize`；部件 `manifest`、`payload`、`files/<相对路径>` |
| 上云回执 | `200 {"cloudReference":"...","receipt":"<JSON 文本>"}`；**回执必须是可解析为 JSON 且带明确成功语义**（`received:true` 或 `status ∈ {SUCCEEDED,SUCCESS,OK,RECEIVED,ACCEPTED}`），否则本机判"回执不完整"⇒ 零清理 |
| 清单 | `GET {baseUrl}/backup-packages?organizationId=X` → `{"packages":[{packageId,organizationId,backupId,createdAt,byteSize,checksumSha256}]}` |
| 下载 | `GET {baseUrl}/backup-packages/{packageId}/content?organizationId=X` → 二进制字节 |
| 鉴权 | `authorization: Bearer <凭据>` ＋ `x-cloud-purpose: CLOUD_BACKUP`（缺任一 ⇒ 401） |

环境变量：`LOCAL_BACKUP_CLOUD_BASE_URL`／`LOCAL_BACKUP_CLOUD_CREDENTIAL`／`LOCAL_BACKUP_CLOUD_TIMEOUT_MS`。

## 4. 真实链暴露的三个生产缺陷（均已修复并复跑）

### 4.1 受保护包生成在真实库上直接失败（P0）

- **现象**：`Unknown column 't.id' in 'order clause'`
- **根因**：`ProtectedBackupService.collectCompanyRows` 用 `ORDER BY t.id` 排序列，
  但备份范围里的 `maintenance_report_version_attachment` 是**复合主键**（`version_id` ＋ `attachment_id`），
  `stored_file` 的主键是 `file_id` —— **两者都没有 `id` 列**。
  该表是前几轮才被纳入备份范围的，所以此前在真实库上从未跑通；单测用桩仓储，**看不见**。
- **影响**：**受保护包生成整体不可用** ⇒ 手动备份与 72h 自动备份都产不出包 ⇒ 备份功能形同虚设。
- **修复**：排序列口径集中到 core 策略 `BACKUP_TABLE_DESCRIPTORS[table].orderColumns`
  （缺省 `['id']`，`stored_file` 声明 `['file_id']`，`maintenance_report_version_attachment` 声明 `['version_id','attachment_id']`）；
  服务层按口径排序列，**不再写死 `id`**。
- **回归**：`protected-backup.service.spec.ts` 5 passed；真实链重新跑通（生成步骤由 FAILED 变 SUCCEEDED）。

### 4.2 凭据用途永远不可核验 ⇒ 上云永远被跳过（P0）

- **现象**：真实链里上云轮次 `skipped=10 / attempted=0 / receiverMissing=0` —— 云端口已注册，却一个都不尝试。
- **根因**：**写口径与读口径矛盾**：
  - 写入侧（`validateAuthorizationRenewalInput`）要求"签名凭据**必须是对象**"，
    `local_account_authorization.signed_claims` 是 `json` 列，读回来就是**对象**；
  - 读取侧（`resolveCredentialPurposes`）只认 **JSON 文本**（`typeof signedClaims !== 'string'` 即不可核验），
    调用点还用 `typeof x === 'string' ? x : null` 提前丢弃对象形态。
  - 结果：**任何按生产形态写入的凭据都判为"用途不可核验"** ⇒ `hasCredentialPurpose` 恒 false
    ⇒ `decideBackupUploadAttempt` 恒判 `AUTHORIZATION_INVALID` ⇒ **上云永远跳过**；
    业务同步侧的用途读取同样拿不到用途。
- **修复**：`resolveCredentialPurposes`／`hasCredentialPurpose` 改为接受 `unknown`，
  **同时认"对象"与"JSON 文本"**两种载体；四个调用点（`local-backup-upload.service`、
  `backup-schedule.service`、`queries/sync-status.query.service`、`queries/local-runtime.query.service`）
  直接传 `signedClaims`，不再按类型提前丢弃。
  **纪律不变**：两种形态都解析不出受控用途时，仍按"不可核验"处理（不猜、不放宽）。
- **回归**：用途策略单测 5 passed（原有 JSON 文本用例仍绿）；真实链上云由 `attempted=0` 变为 `attempted=8 succeeded=8`。

### 4.3 资产行缺 `installation_id` ⇒ 手动清理永远不可用（P0）

- **现象**：有完整回执时清理仍返回 `available=false reason=CLOUD_RECEIPT_MISSING`。
- **根因**：`recordBackupAsset` 登记 `backup_asset` 时**没写 `installation_id`**（历史行为为 NULL），
  而清理侧按 `(organization_id, installation_id)` 找资产（`listAssets`）⇒ 永远找不到本次资产
  ⇒ `findManualRunCloudReceipt` 恒返回 null ⇒ **"有完整回执 ⇒ 清理本机包"这条链永远走不通**，
  本机包永远不被清理（备份包无限堆积）。
- **修复**：`recordBackupAsset` 增加 `installationId` 入参，写入本机安装标识（来源已是同一方法内读到的安装身份）。
- **回归**：真实链清理断言由 `available=false` 变为 `available=true cleaned=1`，且**本机包目录真实消失**。

## 6. 夹具与副作用边界（诚实交代）

- 夹具写在**可丢弃的隔离库** `lithography_task09_dev`：`local_company_setting`（本公司、两个开关打开）与
  `local_account_authorization`（本公司、`CLOUD_BACKUP` 用途、ACTIVE）。两者按
  `(installation_id, organization_id)`／`(installation_id, account_id, organization_id)` 幂等写入，**可重复执行**。
- 脚本只操作**目标公司（org 1）**的数据区；其他公司、其他安装的资产与包**未被触碰**。
- 脚本会新建备份运行与包（业务动作的真实副作用），并按生产语义清理**本机本公司**的过期/已上传包；
  残留的 `RUNNING` 行按生产口径（`BackupScheduleService.compensateInterruptedRuns`，60 分钟补偿时限）
  改判 `INTERRUPTED`——只动"超过补偿时限"的行。
- 受保护封包密钥：本机 env 里的占位值不是合法 AES-256 密钥，脚本改用**固定测试密钥**；
  它只用于隔离库本地包封包，**不进任何回执、日志或 API 响应**。
