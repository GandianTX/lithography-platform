## 1. 缺陷确认：原实现只靠外键兜底

| 项 | 事实 |
| --- | --- |
| 位置 | `backend/src/usecases/maintenance-report/record-package-item-writer.ts` |
| 原写法 | 直接把包内 `request.sourceAccountId` 写成 `createdByAccountId` / `updatedByAccountId` / `maintenanceEngineerAccountId` / `submittedByAccountId` |
| 唯一的"校验" | 数据库外键（`fk_maintenance_report_*_account`）——**只能证明账号行存在** |
| 证明不了的 | 账号是否**已停用**、是否**仍是本公司在职成员**（归属变更／已退出）、导入者对它**有没有当前权限** |
| 既有"伪造账号"用例的真相 | `record-package-item-writer.spec.ts` 用 `insertError: new Error('外键约束失败')` 让 mock **无条件 reject**——它验证的是"库层兜底生效且失败路径不回退成导入人"，**没有验证应用层拒绝了一个不可信账号** |
| 既有"同公司他人"用例的真相 | 断言 `createdByAccountId === 900202`（**成功写入**），并未证明"拒绝" |

**结论**：交接文档第 2 条的判断成立——"仅依赖包内 `sourceAccountId` 与数据库外键"不构成授权。

## 2. 口径设计（唯一实现）

新增 core 纯函数策略：
`backend/src/core/local-runtime/policy/record-package-source-identity.policy.ts`

判定顺序（任一不满足即拒绝，并给出可读原因）：

| # | 条件 | 拒绝原因（节选） |
| --- | --- | --- |
| 1 | 包内未携带来源账号 | 包内未携带来源账号，原作者不可核验（不以导入人冒充原作者） |
| 2 | 包内归属公司 ≠ 导入目标公司 | 包内归属公司与导入目标公司不一致 |
| 3 | 来源账号本机**不存在** | 包内来源账号在本机不存在，原作者不可核验 |
| 4 | 来源账号**已停用**（`base_user_account.status` ≠ ACTIVE） | 包内来源账号已停用（`<status>`） |
| 5 | 来源账号**资料缺失或已停用**（`base_user_info.user_state` ≠ ACTIVE） | 包内来源账号的资料已停用（`<state>`） |
| 6 | 来源账号**不是目标公司在职成员**（`organization_membership` / `organization` 当前状态） | 不是本公司的在职成员（归属已变更或从未归属本公司）／已离开本公司／本公司已停用 |
| 7 | 导入者**没有当前权限** | 工程师只能导入本公司当前有权记录（包内来源账号为同公司他人） |

### 需求依据（逐条可核对）

| 依据 | 原文 |
| --- | --- |
| V5.6 R072-01 权限结论 | **工程师只能导入本公司当前有权记录** |
| V5.6 R072-01 操作流程 | 复核包版本与**当前权限**→逐条去重／冲突处理→保存实际结果 |
| V6.5 §11.3 确认导入 | 仅对检查合格范围执行，仍**复核当前权限**与删除下架事实 |
| V6.5 §9.2 / R052（任务 07 页面口径） | 工程师只展示**本人创建且本人有权访问**的记录 |
| 任务书第 09 项 | 工程师和二级管理员按本机本公司访问有权元数据与包，一级按当前授权范围 |

### 第 7 条的分支说明（为什么不是"一律要求同一账号"）

- **本人导入本人同公司记录** → 允许（任务书"工程师已有本公司有权业务记录"的常态场景）；
- **二级管理员按本公司范围** → 允许（任务书"二级管理员按本机本公司访问有权元数据与包"）；
- **一级管理员** → 拒绝（平台级角色、没有业务所属公司；且导入编排本来就因
  `facts.import.organizationId !== scope.organizationId`（一级管理员 `scope.organizationId=null`）拒绝该包）；
- **工程师导入同公司他人记录** → 拒绝。

> 该分支集中在策略函数 `evaluateImporterAuthority` 一处，如维护者认为管理员也须仅本人，
> 改一处即可，不散落在调用点。

## 3. 落点（两处闸门，一份口径）

| 位置 | 角色 | 做什么 |
| --- | --- | --- |
| `usecases/maintenance-report/record-package-source-identity.verifier.ts`（**新增**） | **来源域的裁决实现** | 读本机事实（`AccountQueryService` 账号/资料状态 + `admin_level`；`OrganizationMembershipQueryService.listMembershipsForBinding` 成员关系全集）→ 调 core 策略 |
| `usecases/common/ports/record-package-item-writer.contract.ts` | 跨域边界契约 | 新增 `verifySourceIdentity(params)`；放行时**带回已核验的来源账号 id** |
| `usecases/maintenance-report/record-package-item-writer.ts` | 来源写入链的**最后一道闸** | 写业务**之前**先核验；拒绝即 `FAILED`＋原因，**不写任何业务行** |
| `usecases/local-runtime/import-record-package.usecase.ts` | 导入编排 | 在**暂存原件之前**先向来源域请求一次核验；拒绝即该条 `FAILED` |

### 为什么把裁决放在来源域（而不是编排侧）

端口契约原文：「**写入必须走来源业务既有的受控入口**（身份、公司范围、版本条件都由来源域裁决），
任务 09 不另立第二套权限口径」。因此**编排侧不自己判账号状态**，只向来源域请求结论——
避免出现"编排判一套、写入方判另一套"的双口径。

### 为什么编排侧还要再问一次

原件暂存的「上传者」必须等于包内来源账号（任务 11 的绑定约束）。若账号不可信却先暂存，
会留下**指向不可信账号的孤儿暂存行**（TEMPORARY，可追踪但无业务归属）。
因此**先核验、后暂存**；编排侧不重复实现判定，只消费来源域的结论。

## 5. 核对中发现的真实缺陷（已修）

### 5.1 09 侧把"已正式提交"的报告判成可写

- 位置：`backend/src/modules/lithography/queries/sync-source-record.query.service.ts`（`toReportFact`）
- 事实：09 的只读事实只把 `PENDING_REVIEW` 记为 frozen、`APPROVED` 记为 closed；
  **`SUBMITTED`（R051 正式提交后的冻结态）两者都不是 → 被判成"可写"**。
- 与 06 冲突：06 的写守卫 `EDITABLE_STATUSES = [DRAFT, RETURNED]` —— `SUBMITTED` 明确**不可编辑**。
- 后果：冲突页会对已正式冻结的报告给出"保留本地"动作，真正写入时才被 06 拒绝
  （任务书"只读／结单／冻结内容不能保留本地反写"、V6.5 §11.2"已结单只读、正式冻结及原始历史不允许覆盖"）。
- 修复：`frozen` 增加 `SUBMITTED`，与 06 写守卫口径对齐；新增用例 2 例
  （`SUBMITTED`→frozen；`APPROVED`→closed；`DRAFT`／`RETURNED`→可写）。

### 5.2 存量前端门禁失败（与本轮改动无关，但上一窗口的"门禁全绿"结论不成立）

- 事实：`frontend/src/features/local-runtime/ui/local-runtime-settings-panel.tsx` 直接

  被 `boundaries/dependencies` 拦截（`frontend/docs/dependency-rules.md`：正式区 `features -> entities, shared`）。
- 影响：**上一窗口交接文档记录的"frontend eslint → 0"不成立**（该结论为执行 AI 自报、未经独立复验）。
- 修复（不改判定语义）：会话事实上移到**页面层**（`pages -> features` 合法），
  面板改为接收 `writable` 属性；删除面板对 `auth-session` 的特性级依赖；
  面板用例去掉跨特性 mock 并补"管理员可写形态渲染两个开关"；页面用例补"未认证会话下传只读"。

## 8. P2-3 工单总结范围核对（详细结论）

### 8.1 关联工单事实（本机权威来源）

| 语义 | 字段 | 位置 |
| --- | --- | --- |
| 工单总结必须绑定工单 | `chk_maintenance_report_request_source`（`WORK_ORDER_SUMMARY ⇒ repair_request_id IS NOT NULL`）＋ `fk_maintenance_report_repair_request`（物理外键 RESTRICT） | `modules/lithography/entities/maintenance-report.entity.ts` |
| 接单人的权威事实 | `repair_request.accepted_by_engineer_account_id` | `modules/lithography/entities/repair-request.entity.ts` |
| 工单归属公司 | `repair_request.owner_organization_id` | 同上 |
| 工单结单状态 | `repair_request.closure_status`（`OPEN` / `CLOSED` / NULL） | 同上 |
| 工单撤回 | `repair_request.deprecated` ＋ `deleted_at` | 同上 |
| 报告责任工程师 | `maintenance_report.maintenance_engineer_account_id`（＝接单人本人，由 `assertWorkOrderSummaryPreconditions` 强制） | `usecases/maintenance-report/maintenance-report-work-order.constants.ts` |
| 可作为总结来源的工单口径 | 本人接单 ＋ 同公司 ＋ 未撤回 ＋ 已结单 ＋ 尚无报告或仅有 DRAFT／RETURNED 草稿 | `modules/lithography/queries/maintenance-report.query.service.ts` `listWorkOrderSummaryCandidates` |

### 8.2 为什么本机**无法**核验（关键阻断点）

包内（`content_snapshot.payload`）只有**源机**的数字外键：

- `payload.repairRequestId`＝**源机自增 id**（不是跨端稳定编号）；
- `source_account_id` 与 `payload.maintenanceEngineerAccountId`＝**源机账号 id**
  （本机账号自增 id，跨机不可移植）；
- 包内**没有**工单条目，也**没有** `repair_request.record_uuid`（全仓检索
  `repair_request_uuid` 0 命中，工单的跨端稳定编号未随包携带）；
- 工单快照里也**没有** `closure_status` / `accepted_by_engineer_account_id` / `owner_organization_id`
  （只有 `record_id` / `request_no` / `fault_description` / `content_md` / `current_revision_no` /
  `maintenance_version_no` / `handling_result` / `handling_status` / `created_at`）。

⇒ 目标机**无法**确认"关联工单存在且属于目标公司""接单人与包内来源账号一致"。
按数字 id 猜工单会把报告挂到**另一张**工单上（且可能违反"一工单一份总结"），
或因物理外键直接失败——两种都不是"导入成功"。

### 8.3 处置：保持逐条明确拒绝（原因写明阻断点）

写入侧拒绝原因由
「工单总结来源的报告需核对关联工单事实与接单人规则，当前不导入」
改为
「**工单总结来源的报告无法在本机核验关联工单事实与接单人（包内无工单跨端稳定编号、账号 id 跨机不可移植），该条未导入**」。

这是 P2-3 要求的"不满足时逐条明确拒绝"——拒绝是结论，**原因必须指向真实阻断点**，
而不是笼统的"需核对"。

### 8.4 放行所需的前置条件（未来解法清单）

**前置（缺一不可）**

1. 工单总结的冻结 payload 增键携带**关联工单的跨端稳定编号**（`repair_request.record_uuid`）；
2. 账号具备**可移植标识**（随包携带），或明确接受"接单人一致性仅在同账号 id 体系内可核验"这一受限口径并写进文档。

**导入侧逐条判定（短路顺序）**

3. `payload.sourceType === 'WORK_ORDER_SUMMARY'` ⇒ `payload.repairRequestId` 必须为正整数，
   **禁止**用该数字直接查本机工单；
4. 按 `payload.sourceRepairRequestUuid` 定位本机工单，查不到 ⇒ 该条 FAILED
   （不得按数字 id 猜、不得创建空壳工单）；
5. 工单归属公司一致：`repair_request.owner_organization_id === 目标公司`；
6. 工单未撤回：`deprecated === false` 且 `deleted_at IS NULL`；
7. 工单已结单：`closure_status === 'CLOSED'`；
8. 工单已接单且接单人为包内来源账号：`is_accepted === true` 且
   `accepted_by_engineer_account_id === 已核验的来源账号 id`；
9. 一工单一份总结：目标机该工单无既有报告；
10. 报告状态不降级：`source_status ∈ {SUBMITTED, PENDING_REVIEW, APPROVED, RETURNED}`；
11. 版本一致：`currentVersionNo = 清单 version_no`；冻结版本行按同 `versionNo` 写入；
12. 内容一律取包内冻结 payload（**不得在本机重新派生**）；
13. 原件：工单总结报告源机不登记原件 ⇒ 包内 `files` 应为空。

**另需同步的口径**：第 5.1 条已把 `SUBMITTED` 纳入 09 侧只读事实，
否则导入后的正式事实在 09 侧仍会被判"可写"。
