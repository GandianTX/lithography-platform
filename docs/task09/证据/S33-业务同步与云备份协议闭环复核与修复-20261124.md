### 1.3 D2 复核：S30 的登记与事实不符（更正登记）

S30 §4 登记“D2：业务同步派发链不校验凭据用途（备份侧有 `hasCredentialPurpose`）”。
**复核结论：该登记不成立。**

- 派发链的授权事实来自 `SyncStatusQueryService.readAuthorizations`
  （`modules/lithography/queries/sync-status.query.service.ts`），该处**已**按
  `hasCredentialPurpose(row.signedClaims, LOCAL_CREDENTIAL_PURPOSE.BUSINESS_SYNC)` 过滤；
- 备份侧另有独立校验（`local-backup-upload.service.ts` 的 `CLOUD_BACKUP` 用途校验）；
- 两处**各自**按用途过滤 ⇒ “两用途凭据互串”在读侧已被挡住。

**但“读侧已挡”不等于“端到端已证”**，故本轮补**端到端回归**（用**真实** `SyncStatusQueryService`
接**真实**派发用例，不再用替身）：

- 原账号只有 `CLOUD_BACKUP` 用途授权 ⇒ 任务**取消**、**不发**（`AUTHORIZATION_INVALID`）；
- 原账号有 `BUSINESS_SYNC` 用途授权 ⇒ 正常派发。

⇒ D2 记为**已闭环**（结论更正登记，不计作本轮新增修复）。

### 1.4 D10 的事实依据

`http-business-sync-receiver.ts` 此前手工写 `Content-Type: multipart/form-data`（**没有 boundary**）。
本仓 axios 1.18 的 http 适配器会在 `formDataToStream` 里用**自算的 boundary** 覆盖该头
（`node_modules/axios/lib/helpers/formDataToStream.js`），因此“当前能跑通”**依赖客户端覆盖我方手写值**
这一隐式约定；一旦换成别的客户端或 axios 行为变化，对端将无法解析请求体。
本轮改为**不写**该头，由客户端按请求体实际形态生成 `Content-Type: multipart/form-data; boundary=…`。

### 2.3 E1：本轮在跑真实链时发现的生产回归（第 09 项引入）

**现象**：备份真实链脚本在“手动清理”这一步**整条崩溃**：

```
PessimisticLockTransactionRequiredError: An open transaction is required for pessimistic lock.
  at LocalBackupCleanupService.listAssets (local-backup-cleanup.service.ts:581)
  at LocalBackupCleanupService.findManualRunCloudReceipt (local-backup-cleanup.service.ts:558)
```

**根因**：第 09 项提交 `b7f2a36`（清理执行事务化）把 `listAssets` 改成**带悲观写锁**的读取，
但 `findManualRunCloudReceipt`（手动清理的**授权来源**）仍在**事务外**用同一个读取方法
⇒ TypeORM 直接拒绝无事务的悲观锁 ⇒ **手动清理入口 100% 报错**。

> 说明：S30 的备份真实链证据是在 `b7f2a36` **之前**取的
> （`97247c6` 09:02 < `b7f2a36` 10:28），因此该回归不在 S30 的观测面上；本轮跑真实链才暴露。

**修复**：`findManualRunCloudReceipt` 的资产读取改到**清理事务内**（`runInCleanupTransaction`），
锁语义与清理执行一致，不再出现“无事务悲观锁”。

**验证**：修复前脚本崩溃；修复后 35/35 全绿（“正常闭环：有完整回执 ⇒ 手动清理可用”、
“清理后本机包真实消失”两项均通过）。
