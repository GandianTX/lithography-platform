## 1. 本轮新增：混合导出的前端正式入口

### 1.1 交互形态（`frontend/src/features/record-package/ui/record-package-export-panel.tsx`）

| 形态 | 输入 | 提交参数 | 适用 |
| --- | --- | --- | --- |
| **单一类型**（默认） | 一条记录类型 ＋ 多个记录 ID | `resourceType` ＋ `recordIds` | 来源页"导出我的 X"（旧口径，行为不变） |
| **混合导出** | 逐行"记录类型 ＋ 记录 ID"，可增删行 | `entries: [{ resourceType, recordId }]` | 一次导出跨工单／报告／资料 |

要点：

- 形态切换用受控 `Radio.Group`（**不置于表单字段名下**，避免与 `Form.Item` 的值注入互相覆盖）；
- 切换形态时**清掉另一形态的残留字段**（`resourceType`／`recordIds`／`entries`），不提交"形态不符"的字段；
- 结果表格新增 `resourceType` 列、`rowKey` 改为 `${resourceType}-${recordId}`
  （同一包内"同 id 不同类型"不会撞行）；
- **失败关闭**：混合形态下没有条目时**禁用导出按钮**；条目非法（缺类型／非正整数 ID）在提交前被过滤，
  填了 ID 但归一化后为空时**不发请求**。

### 1.2 数据链路

| 层 | 改动 |
| --- | --- |
| `record-package.types.ts` | 新增 `RecordPackageExportEntry = { resourceType; recordId }` |
| `record-package-adapter.ts` | mutation 增加 `$entries: [RecordPackageExportEntryInput!]` 并透传；**未提供时传 `null`**（旧客户端不受影响） |
| `use-record-package-export.ts` | `run(input)` 增加可选 `entries` |
| GraphQL | 沿用既有契约（`entries` 可空；提供时服务端以它为准）——本轮**未改后端契约** |

## 2. 本轮在接线过程中抓到并修复的 4 个真实缺陷

| # | 缺陷 | 影响 | 修复 |
| --- | --- | --- | --- |
| 1 | 导出面板把 `InputNumber` 包在 `<div>` 里，`Form.Item` 的值注入落到 `div` 上 | **公司数据区永远收集不到值** ⇒ 必填校验恒失败 ⇒ 该面板的导出功能实际不可用 | `InputNumber` 直接受管（`className="w-full"`） |
| 2 | 记录 ID 来自多值（tags）输入控件，值是**字符串** | GraphQL 变量 `$recordIds: [Int!]!` 不接受字符串 ⇒ 请求会被服务端拒绝 | 在 adapter 边界统一归一化为**正整数**（`normalizeRecordIds`），面板层复用同一函数做失败关闭 |
| 3 | 前端测试 mock 使用了后端**从不产出**的 `NO_FROZEN_VERSION` | 违反"受控原因码不臆造"纪律，容易误导后续实现 | 改为服务端真实产出的 `STRUCTURE_INVALID`（"报告尚无冻结版本"落在该码） |
| 4 | 用 `Form.useWatch('entries', form)` 监听 `Form.List` 变化 | 监听不到 ⇒ 混合形态的导出按钮**恒为禁用**，入口等于没做 | 改为由增删入口**显式维护条目计数** |

## 3. 逐类导出授权与只读工单口径（明确口径）

### 3.1 逐类授权矩阵（策略：`record-package-export-authorization.policy.ts`）

| 角色 | 资料 REFERENCE_DOCUMENT | 报告 MAINTENANCE_REPORT | 工单 REPAIR_REQUEST |
| --- | --- | --- | --- |
| 工程师 | **作者本人** ＋ 本公司 | **作者本人或责任工程师** ＋ 本公司 | **本公司全部工单**（不要求本人） |
| 二级管理员 | 本公司 | 本公司 | 本公司 |
| 一级管理员 | 全局授权范围 | 全局授权范围 | 全局授权范围 |

口径来源是**来源域真实读取权限**（任务 07「我的资料记录」＝作者本人＋本公司；工程师工单列表＝本公司全部），
不是本任务自创；跨公司一律拒绝（`FOREIGN_COMPANY`），"非本人"拒绝（`NOT_AUTHORIZED`），
归属未知一律拒绝（**失败关闭，不猜归属**）。混合导出时**逐条按该条自己的资源类型判定**
（早期实现沿用命令级单一类型会导致"工单被按资料口径授权"，已在 S13 修掉）。

### 3.2 本轮补齐的服务层集成用例

`backend/src/modules/lithography/record-package-export.service.spec.ts` 新增
`混合导出：逐类授权在同一包内逐条生效（工程师：本公司工单放行、他人资料拒绝）`：

- 同包两条：他人资料（`createdByAccountId=99`，导出人=16）＋ 本公司工单（受理人/客户均非导出人）；
- 断言：`itemExported=1`、`itemFailed=1`；资料条目 `REJECTED` 且 `rejection='NOT_AUTHORIZED'`、
  `message` 含"本人创建"；工单条目 `EXPORTED`；**清单里只有放行条目**（拒绝条目不进包）。

### 3.3 只读工单口径（导出路径）

- 导出是**只读快照带出本机**：只读已授权数据与原件，**不写正式业务表**、不改源端任何状态；
- 因此导出路径**不引入"写回"语义**。与同步冲突裁决里的"只读采用"是两件事：
  - **只读采用**（`sync-conflict-readonly.policy.ts`）针对**把云端视图写回本机**：
    已结单（`SOURCE_CLOSED`）允许**只读采用**（可读可呈现、但不写业务、不改历史、不获得写权），
    删除/下架（`SOURCE_WITHDRAWN`）与冻结（`SOURCE_FROZEN`）一律拒绝；
  - **记录包导出**只把**本机已有内容**按授权带出，不产生"采用"动作，故**不套用**上述写回准入；
- 导出侧对"可读性"的既有事实判定（逐条拒绝，失败关闭）：
  - 资料：`deprecated`（撤回/下架）拒绝；`currentRevisionNo < 1`（尚无生效修订版本）拒绝；
  - 工单：`deprecated` 拒绝；`currentRevisionNo < 1`（尚无生效修订版本）拒绝；
    工单的 `handling_status`（处理中/已结单）**只作为快照字段随条目写入清单**，不参与导出准入；
  - 报告：`currentVersionNo < 1`（尚无冻结版本）拒绝；报告的 `status`（草稿/待审/已批准）
    **只作为 `source_status` 随条目入包**，不参与导出准入；
- 受控原因码（导出逐条拒绝）：`FOREIGN_COMPANY`、`NOT_AUTHORIZED`、`PATH_ESCAPED`、`FILE_MISSING`、
  `FILE_CHECKSUM_MISMATCH`、`STRUCTURE_INVALID`（含"尚无生效版本/冻结版本"等结构性拒绝）。
  **本轮未新增原因码，也未编造原因码**（前端 mock 里原有的 `NO_FROZEN_VERSION` 已改为真实码）。

## 5. 剩余缺口（本轮**未**处理，如实登记）

1. **导出准入不按工单状态分级**：已结单（只读）与处理中（冻结）工单当前都允许导出快照。
   本轮**未**擅自改变该语义（导出不改源端，现状无安全缺口），但"是否要按状态分级"属于**需求裁定**，
   需维护者明确后再落地（改动会变更既有基线行为，不臆造）。
2. **汇总字段 `resourceType` 在混合导出时取首个条目类型**：逐条结论各自带类型，
   汇总值不能表达"混合"⇒ 前端展示混合类型须读逐条结论（本轮前端表格已按逐条展示）。
3. **跨安装双机反例本轮未复跑**：需要第二套隔离库与 `CREATE DATABASE` 权限（沿用 S13 §4 的环境结论）。
4. **导出用例层无用例**：`export-record-package.usecase.ts`（组织范围归一化、恢复期冻结
   `assertCompanyWritable`）尚无用例级测试。
