## 1. 跨安装身份反例矩阵（`task09-identity-counterexample-matrix.ts`）

**为什么必须做**：上一轮把"跨安装只覆盖同公司同账号"记为未取证缺口。跨安装时
`source_account_id` 是**源机自增 id**，在目标机毫无意义；若实现按数字 id 选作者，
源机工程师的报告就会被记到目标机**另一个人**名下。这条只能靠反例证伪。

**做法**：单进程内连接 A（源）／B（目标）两套隔离库 →
在 A 上为每个变体造"来源账号 ＋ 报告"并导出包 → 复制到 B 的"介质"目录 →
在 B 上布置该变体的**本机事实** → 走**生产导入链**（`CheckRecordPackageUsecase`
→ `ImportRecordPackageUsecase`，导入者为**二级管理员**，确保拒绝原因来自身份事实而非权限）。

| 变体 | 目标机本机事实 | 期望 | 实测 |
| --- | --- | --- | --- |
| V1 同人不同号 | `account_uuid` 命中、数字 id 不同 | 放行，作者落**目标机本机 id** | ✅ 落 `902011`（非包内数字 id） |
| V2 同号不同人（账号名相同） | 数字 id 与包内**相同**、uuid 不同、姓名不同 | 拒绝 | ✅ "包内来源账号姓名快照与本机同账号名账号的姓名不一致" |
| V3 同号不同人（账号名不同） | 数字 id 与包内**相同**、uuid 与账号名均不同 | 拒绝 | ✅ "本机不存在可核验的来源账号" |
| V4 来源账号停用 | uuid 命中但 `status=SUSPENDED` | 拒绝 | ✅ "包内来源账号已停用" |
| V5 来源资料停用 | uuid 命中但 `user_state=INACTIVE` | 拒绝 | ✅ "包内来源账号资料已停用" |
| V6 已离职 | 成员关系 `LEFT` | 拒绝 | ✅ "包内来源账号已离开本公司" |
| V7 换公司 | 成员关系在**另一公司** | 拒绝 | ✅ "包内来源账号不是本公司的在职成员" |
| V8 包内无可移植身份 | 只有数字 id（无 uuid、无账号名） | 拒绝（不得冒用导入人） | ✅ "包内缺少跨端可移植的来源账号标识（稳定账号标识与账号名均未携带），原作者不可核验，该条未导入" |

**结果**：**38/38 断言全通过（exit 0）**。

关键守卫（缺一即假通过）：
- **错归属守卫**：V2／V3 的目标机账号 id 与包内 `source_account_id` **完全相同**；
  断言"目标机不存在该 `record_uuid` 的报告"⇒ 只要实现按数字 id 选作者即失败。
- **导出侧退化守卫**：断言包内清单确实携带 `source_account_uuid`／`source_account_login_name`
  （V8 除外）⇒ 导出侧退化为"只带数字 id"时，矩阵不会静默变成"V8 那样看起来正确"。
- **幂等**：脚本开头按**本脚本固定 id 段**预清理 ⇒ 上一次未收尾不会把矩阵打断在写入阶段。

收尾：来源库与目标库夹具按精确清单删除（账号／资料／成员关系／报告／版本／
记录包批次与条目），核对两库**零残留**。

## 2. 恢复链并发竞态（`task09-restore-concurrency-race.ts`）

**为什么必须做**：上一轮只说"并发执行只有结构保证"，属未验证。本轮用**生产服务**
（`LocalWriteHoldService`）在隔离库上直接复现竞态窗口。
断言写的是**期望行为**，失败即**复现缺陷**（脚本 exit 1），不改断言粉饰。

| 场景 | 期望行为 | 实测 | 根因（代码位置） |
| --- | --- | --- | --- |
| S1 同一范围**并发建立冻结**（8 路） | 只应存在一条 ACTIVE 冻结 | 🔴 **失败：产生 8 条 ACTIVE** | `hold()` 是"先查后插"，无行锁；`local_write_hold` 上只有**非唯一**索引 `idx_local_write_hold_scope` |
| S2 释放冻结的边界 | 不得带走同范围"他人恢复"的冻结 | 🔴 **失败：他人哨兵被一起释放** | `release()` 按 `installation_id × organization_id × status` 更新，**不带 `restore_id`** |
| S3 "先读后写"的冻结可见性 | 冻结建立后写前守卫必须拒绝 | ✅ **通过：守卫拒绝** | 守卫读的是**事务外最新已提交**数据，不受事务快照影响 ⇒ 该窗口**未穿透** |
| S5 再次建立冻结的归属 | 不得改写既有 `restore_id` | 🔴 **失败：归属被覆写** | `existing.restoreId = input.restoreId ?? existing.restoreId` |

**结论（3 项并发缺陷，已登记 G31–G33）**：恢复链的写传冻结在**并发**下不成立——
同范围可出现多条冻结、结束一条会误释放别人的、再次建立会篡改归属。
根因是冻结表**缺唯一约束**＋`hold/release` **不带归属条件**。
建议修复（需维护者确认，涉及增量迁移与并发语义）：
① `local_write_hold` 增加"仅 ACTIVE 唯一"的生成列 ＋ 唯一索引；
② `release()` 改为按 `restore_id` 限定；③ `hold()` 再次建立时**不覆写**既有归属。

**已知未取证**：同一 `restore_id` 的**两次并发恢复执行**（需完整备份＋预检＋受理链，
本轮未做）；恢复写入**未落进事务**（`local-restore-record.writer.ts:347` 回调未接收
`transactionContext`）⇒ 中断即半截状态（与"进程中断"用例结论一致，并发叠加未单独取证）。

收尾：按 `hold_id` 精确删除本轮冻结行，核对目标范围**零 ACTIVE 残留**、外公司哨兵不被误伤。

### 8.3 收敛过程中踩到并修掉的两个 Playwright 坑（**都是真实失败，不是推测**）

1. `page.evaluate` 的回调在**浏览器上下文**执行，**不能引用 Node 作用域的常量**
   ⇒ 直接写 `TASK09_TABLE_OVERFLOW_JUDGE_GLOBAL` 会 `ReferenceError`（实测 3 个用例失败）；

   （此前双参数写法导致一致性用例失败）。
