## 1. 缺口确认（动手前的事实核对）

| 项 | 事实 |
| --- | --- |
| 暂存表 | `stored_file`：`status`∈`STAGING/VALID/FAILED`、`binding_status`∈`TEMPORARY/BOUND`、`business_id`（可空）、`upload_context_id`（**UNIQUE，per-file 一次性 UUID**）、`created_at`（**无 `updated_at`／无 `deleted_at`**） |
| 现有写入口 | `StoredFileService` 只有 `insertStagedFile` / `lockForBinding` / `bindIfTemporary` / `unbindIfBoundTo` —— **没有任何删除／作废／释放方法**；REST 无 Delete 端点；`storage.delete` 在 stored_file 链路上从未被调用 |
| 一次导入尝试的聚合键 | **不存在**。`upload_context_id` 是 **per-file** 的随机 UUID（1:1 指向一行），一次导入产生 N 个原件就有 N 个互不相关的 context id；`record_package_import` / `record_package_item` 都没有原件关联列 |
| 精确反查手段 | 只有**内存中的 fileId 列表**（编排侧 `importOne` 手里就有）⇒ **就地逐 fileId 补偿**即可，不需要任何聚合键或新列 |
| DB 口径 | `data-contracts.md` §4.1：只清理「超时且 `binding_status=TEMPORARY` 且**无任何业务引用**」的 STAGING/FAILED；「业务侧删除／下架**不物理删** `stored_file`」 |
| 关键陷阱 | 附件行**退役**（`status='RETIRED'`）后**仍保留 `file_id` 外键**（FK RESTRICT）⇒ **`TEMPORARY` + `business_id IS NULL` ⇏ "无引用"**，清理必须做入边引用检查 |
| 定时任务范式 | 仓库**无 `@nestjs/schedule`**；既有范式是 `bootstraps/worker/*.runtime.ts` 的 `setInterval` ＋ 单飞标志 ＋ 每日一次按**本地日期**判定（`local-backup-schedule.runtime.ts`） |

## 2. 口径与落点

### 2.1 精确补偿（导入链，零迁移）

| 层 | 文件 | 做什么 |
| --- | --- | --- |
| 原语 | `modules/lithography/stored-file.service.ts` `releaseTemporaryFiles` | **条件 UPDATE**：`WHERE file_id IN (名单) AND status='VALID' AND binding_status='TEMPORARY' AND business_id IS NULL` → `SET status='FAILED'`。行保留（可追踪）、不改绑定关系（满足既有 CHECK）、不删字节 |
| 任务 09 侧封装 | `usecases/local-runtime/record-package-original-staging.service.ts` `release(staged)` | 与 `stage()` 对称：只释放**本次尝试自己登记**的 fileId |
| 编排 | `usecases/local-runtime/import-record-package.usecase.ts` | 写入失败（FAILED／CONFLICT／DUPLICATE）**与写入抛错**两条路径都先补偿再登记逐条结果；补偿失败**不掩盖**主失败 |

**"不删除既有原件或其他公司的对象"的三重保证**：

1. 只按**调用方指名的 fileId** 更新（不按条件批量扫）；
2. 条件要求**未被业务绑定**（`business_id IS NULL` 且 `TEMPORARY`）→ 不动已绑定的既有原件；
3. 条件要求 `status='VALID'` → 不动他人／他公司已在用或已失效的对象。

### 2.2 结果未知时先核对再重试

复核本机来源事实（`SyncSourceRecordQueryService.listFacts`）：

| 本机事实 | 判定 |
| --- | --- |
| 已删除／下架（`withdrawn`） | `FAILED`（导入不得复活已删除下架内容）—— 既有行为 |
| `currentVersion >` 包内版本 | `CONFLICT`（不覆盖更高版本）—— 既有行为 |
| `currentVersion ==` 包内版本 **且 `identityPersisted=true`** | **`SKIPPED`（同一事实）** ＋ 补记回执 —— **本轮新增** |
| `currentVersion ==` 包内版本 但 `identityPersisted=false` | 继续正常导入（派生 UUID 不是跨端稳定身份，不能当同一事实）—— **本轮新增的边界** |

> `identityPersisted` 是关键闸门：本机历史行的 UUID 是按**本机自增 id 派生**的（UUIDv5，跨设备不一致），
> 只有**持久化**的 UUID 才能证明"上次写入已生效"。补记回执让后续重试直接命中回执去重
> （本机与同步共用同一把键：组织 ＋ 资源类型 ＋ 记录 UUID ＋ 版本）。

### 2.3 过期暂存清理（后台任务，零迁移）

| 层 | 文件 | 做什么 |
| --- | --- | --- |
| 纯策略 | `core/stored-file/policy/stored-file-retention.policy.ts` | 保留窗口常量（30 天）＋ `decideStoredFileRetentionTargets`：**保留优先**（被引用 → 保留；已绑定 → 保留；未到期 → 保留）后才判清理目标 |
| 事实层 | `modules/lithography/stored-file-retention.service.ts` | 组装候选（公司范围 ＋ 未绑定）＋ **四张引用表入边检查**（`maintenance_report_attachment` / `repair_request_intake` / `repair_process_entry` / `repair_request.maintenance_attachment_file_id`）＋ 执行（释放 ＋ 字节回收） |
| 用例层 | `usecases/stored-file/cleanup-expired-stored-files.usecase.ts` | 扫描 → 裁决 → 逐项执行 → 逐项记 `CLEANED`／`RETAINED`／`FAILED` 与原因 |
| 运行时 | `bootstraps/worker/stored-file-retention.runtime.ts` | 随 Worker 常驻；启动跑一轮（重启补偿）＋ 每小时唤醒、**每日一次**执行（本地日期判定）＋ 单飞 ＋ 异常只记日志 |

**"不误删他人对象"的三道闸门（清理侧）**：

1. **公司范围**：只处理**本机安装映射公司**的文件；未映射 ⇒ 不清理（不猜公司、不跨公司清理）；
2. **业务引用守卫**：四张引用表任一命中 ⇒ 保留（含退役但仍持外键的附件行）；
3. **绑定守卫**：`BOUND` 或已有 `business_id` ⇒ 保留（活件不是孤儿）。

**为什么"零迁移"可行**：`status` 的既有 CHECK 已允许 `FAILED`，`chk_stored_file_binding_pair` 要求
`TEMPORARY ⇒ business_id IS NULL`（本次不改 `business_id`，仍满足），
`chk_stored_file_verified` 只约束 `VALID ⇒ verified_at NOT NULL`（`FAILED` 行保留 `verified_at` 无妨）。
⇒ 把暂存行标记 `FAILED` **不需要新增列或改约束**，不触碰已接受的基线迁移 `1775501200000`。

## 6. 本轮未闭合的缺口

| # | 缺口 | 事实 | 影响 |
| --- | --- | --- | --- |
| G6 | **清理只覆盖"本机安装映射的公司"** | `local_installation.organization_id` 为空时无法确定清理范围 → 不清理 | 一级管理员跨公司上传的原件不会被本机清理任务回收（安全优先，代价是可能残留） |

| G9 | **真实并发与真实文件链未验证** | A5 双设备／双公司隔离库与独立文件根缺失 | 补偿与清理在真实并发／真实文件下的表现仍未验证（受控替身只覆盖逻辑面） |
